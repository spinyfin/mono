# strip-video-metadata

A small macOS tool that **removes camera telemetry and debug data tracks from
video files without altering a single byte of picture or sound**, via a Finder
right-click → Quick Action. Companion to [`concat-videos`](../concat-videos).

Cameras interleave private data streams alongside the audio and video. On DJI
hardware there are two, and one of them is enormous:

| track  | rate       | contents                                                                    |
| ------ | ---------- | --------------------------------------------------------------------------- |
| `djmd` | ~28 kbit/s | focus distance, white-balance colour temperature, a microsecond frame clock |
| `dbgi` | ~25 Mbit/s | a per-frame dump of the image processor's internal state                    |

`dbgi` is factory diagnostic output that ships enabled on retail units:
sensor register banks, tone-map meshes, lens-shading grids and gamma curves,
re-serialised for **every single frame**. On a 4K60 clip it is roughly a third
of the file, and nothing consumer-facing reads it. Across a 14-clip shoot it
came to 3.35 GB.

## How it works

The video and audio packets are copied through untouched (`-c copy`) into a new
container that simply never mentions the data streams. No re-encode, no
generation loss, no quality change — it is a container edit, and it runs at
gigabytes per second.

Every video stream (including the embedded thumbnail) and every audio stream is
preserved. The 4-byte `tmcd` timecode track is regenerated by the muxer, so
files carrying only that are reported as already clean rather than rewritten
forever.

### Replacing a file in place is safe here

The default is an in-place replacement, which is only defensible because it is
verified rather than assumed:

1. Every video and audio stream of the original is hashed **before** anything
   is written.
2. The stripped copy goes to a temp file next to the original.
3. Each stream is hashed again and must match, and the duration must line up.
4. Only then is the original replaced, via an atomic `mv`, carrying the
   original's permissions and modification time across so library sort order
   doesn't shift.

If any check fails the temp file is deleted and **the original is left exactly
as it was**. An interrupted or failed run can't leave a truncated file behind,
and can't leave one half-swapped.

## Install

```sh
./install.sh
```

You'll also need `ffmpeg`:

```sh
brew install ffmpeg
```

Restart Finder if the Quick Action doesn't appear right away:

```sh
killall Finder
```

To remove everything later:

```sh
./install.sh uninstall
```

## Use

1. Select **one or more** video files in Finder — multiple selection is the
   normal case, and each file is processed independently.
2. Right-click → **Quick Actions** → **Strip Video Metadata**.
3. Each file is replaced in place once verified. A macOS notification reports
   how many were stripped and how much was reclaimed.

Files that carry nothing worth removing are skipped, so running it twice over
the same folder is harmless and cheap.

### CLI usage

```sh
strip-video-metadata FILE [FILE ...]          # replace in place, verified
strip-video-metadata -n FILE [FILE ...]       # dry run: what would be reclaimed
strip-video-metadata -o ~/Movies FILE ...     # write stripped copies elsewhere
strip-video-metadata -f FILE                  # strip even if the file is open
```

| flag              | effect                                                                |
| ----------------- | --------------------------------------------------------------------- |
| `-o`, `--out-dir` | Write stripped copies to a directory and leave the originals alone.   |
| `-n`, `--dry-run` | Report each file's data tracks and reclaimable bytes. Writes nothing. |
| `-f`, `--force`   | Replace a file even if another process has it open.                   |

Inputs are sorted by name before processing, so a Finder multi-selection
behaves the same regardless of the order you clicked.

## What it deliberately does not do

- **It does not touch container metadata tags.** Creation time, camera make and
  model, and the rotation display matrix all survive. Only data _streams_ go.
- **It does not re-encode.** If a file's picture would change, the tool refuses
  rather than accepting the change.

## Troubleshooting

- **"open in another process".** Something has the file open — commonly
  QuickTime. Replacing a file out from under a player leaves it showing one
  thing while the disk holds another. Close it, or pass `--force`.
- **"stream changed, not replacing".** The remux would not have been lossless,
  so it was abandoned and your original is intact. The usual cause is a source
  with an **edit list** — a previously trimmed file, where the frames before
  the first keyframe are present in the container but not meant to be shown.
  Remuxing drops them, which is a real content change, so the tool declines.
  Camera-original files don't have this.
- **Quick Action doesn't appear in the menu.** Restart Finder
  (`killall Finder`), or check System Settings → Privacy & Security →
  Extensions → Finder / Quick Actions and make sure _Strip Video Metadata_ is
  enabled.
- **"ffmpeg not found" notification.** Install Homebrew ffmpeg
  (`brew install ffmpeg`). The Quick Action probes `/opt/homebrew/bin`,
  `/usr/local/bin`, and `/opt/local/bin` directly, so you don't have to fix
  `PATH` for Automator.
- **What got logged?** `~/Library/Logs/strip-video-metadata/strip-video-metadata.log`.

## Recovering the telemetry you dropped

`djmd` is small and occasionally interesting — it is where a focus-pull or a
white-balance drift is recorded. If you want it, take it off the camera
original before stripping:

```sh
ffmpeg -i INPUT.MP4 -map 0:d:0 -c copy -f data djmd.bin
```

It is protobuf. `dbgi` is not worth keeping.
