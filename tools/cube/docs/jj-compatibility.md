# jj compatibility: 0.26 through 0.46

Cube and the Boss engine run the host's `jj`. They support jj 0.26.x through 0.46.x and refuse anything else before running a command. This page records what changed between those releases, how each invocation was adapted, and what an upgrade of the host binary involves.

## How the supported range is enforced

`lib/rust/git_utils/src/jj_compat.rs` owns the version logic:

- `detected_version` runs `jj --version` once per executable per process and fails outside 0.26 to 0.46 with a message that names the supported range and how to install a supported release. Pre-release and development builds are refused.
- `arguments` takes an argument vector written for jj 0.26 and respells it for the jj about to run it. A removed flag is never sent to a jj that lacks it, and no jj error is caught and ignored.
- `unmatched_name_error` and `interdiff_files` restore two output contracts that newer jj changed.

Every transport that runs jj calls it: cube's `RealCommandRunner` (all cube invocations), the engine's `LocalJj`, and the engine's `SshHostAdapter`, which probes the remote host's own jj. Code above the transports, and every scripted test, keeps one vocabulary.

To raise the ceiling, read the upstream changelog for the new releases against the inventory below, add the release to `tools/boss/engine/recovery/jj_repository.bzl`, point `jj_upgrade_test_tools` at it in `MODULE.bazel`, run the suites in [Tests](#tests), and then change `MAX_MINOR`.

### Git import and export

From 0.44, `jj git import` and `jj git export` print `No import needed in colocated workspaces.` and return when the workspace shares its working copy with Git, unless `--ignore-working-copy` is given. A plain `jj git export` in the colocated store therefore no longer exports a bookmark that a secondary workspace created. The behaviour chosen for each call site:

- Engine legacy cleanup (`recovery/src/execution_bookmark/legacy_cleanup.rs`) runs `--ignore-working-copy git import` against the store. That form forces the import on 0.46 and is unchanged on 0.26.
- Cube `pr_head.rs` (`git import` after fetching a pull ref) and `pr.rs` (`git export` after `bookmark set`) run in the caller's workspace. A cube workspace is not colocated, so both still synchronise explicitly. In a colocated checkout the same jj command, or the `bookmark set` just before it, has already synchronised.
- Test fixtures that export from a colocated store pass `--ignore-working-copy`.

### Configuration

- **User configuration on macOS.** jj 0.26 reads `~/Library/Application Support/jj/config.toml` and ignores `~/.config/jj`. jj 0.36 and newer read `~/.config/jj/config.toml` (or `$XDG_CONFIG_HOME/jj`) and ignore the old directory. Both read `~/.jjconfig.toml` and `JJ_CONFIG`. A host that only has the old file loses its identity on upgrade. `ui.diff.format` was also removed in 0.37 in favour of `ui.diff-formatter`.
- **Scoped worker homes.** Grok and Antigravity workers get a per-run `HOME`. The delegate now links the host's jj configuration at both locations, prefers the XDG file once it exists, and links `~/.config/jj/repos`.
- **Per-repository configuration.** From 0.38 it lives in `~/.config/jj/repos/<id>/config.toml`, found through `HOME` or `XDG_CONFIG_HOME` and not through `JJ_CONFIG`. The first 0.46 command in a repository moves `.jj/repo/config.toml` there and leaves a symlink, so 0.26 keeps reading it. A process with a different `HOME` sees an empty repository configuration, and if it is the first to touch the store it moves the configuration into its own home. That is why the scoped-home delegate links the `repos` directory, creating it if needed. The mono store's repository configuration sets `trunk()`, `snapshot.max-new-file-size` and the now-ignored `git.subprocess`.
- **Copied repositories.** jj 0.46 notices a copied repository, gives the copy its own configuration and warns once. Test fixtures that copy a template store rely on this.

### Store GC

Cube's store GC refuses to collect with a jj newer than the oldest client declared for the store (default 0.26), because a newer collector prunes predecessors that 0.26 still walks. After the host is upgraded, the daily store upkeep therefore fails with a message naming `cube repo declare-oldest-jj`, and the operation log is not trimmed.

Collection supports jj through 0.46, with an independent collector ceiling enforced both when declaring the oldest client and when starting GC. Declare 0.46 only after every client sharing the store has upgraded; collection can remove history 0.26 needs.

Every collector newer than 0.26 rewrites the operation log the same way, whether or not that release was tested, so a host stopped at an intermediate Homebrew version cannot fall back to the in-place abandon that newer jj makes too slow to bound. Only 0.26 and 0.46 are exercised end to end.

The rewrite is prepared using private operation heads and the shared content-addressed store while leases continue, and the collector warms the rewritten index before taking exclusivity. Preparation takes minutes on a large log, so live operations usually advance the head meanwhile. The collector therefore prepares again from the new head, up to three more times, before giving up. Once the host is quiet, it snapshots the store's primary working copy (an unsnapshotted edit would otherwise be snapshotted at the pre-rewrite operation by the refresh and merge the old history back in), checks that the live head still matches the prepared snapshot, records the owed working-copy refresh durably beside the quarantine marker, publishes the prepared head and refreshes the working copy with `workspace update-stale`. jj cannot pin that command to an operation and merges multiple heads when it loads, so the head set is verified before it runs (exactly the prepared head) and after it (one head that is the prepared head or safely descends from it). Neither the quarantine nor the refresh record is lifted until that verification passes. If the refresh fails or the process dies after publication, both stay: the next reader that meets the quarantine redoes and verifies the refresh before it is admitted, and a store whose refresh keeps failing stays closed rather than letting `workspace add` fail against a stale primary working copy.

The rewrite gives every kept operation a new id, so each pooled workspace's working copy is left recorded at an operation the new head does not descend from. jj 0.26 does not mind: it compares the working copy's tree with the view. jj 0.46 walks both the rewritten log and the one it replaced, then refuses the command with `seems to be a sibling of the working copy's operation`. On the 22,566-operation test store that takes 4.4 seconds for `jj status` and 3.0 seconds for `workspace update-stale` on the dev Mac, and longer on CI, which is more than the two seconds a lease gives one candidate. A lease therefore timed out on every such workspace, passed it over and provisioned a cold one, for as long as the old log existed. After publishing, and with only the shared gate held, the collector now runs `workspace update-stale` in every free workspace that is not recorded dirty, conflicted or quarantined (`repo.store_gc.workspace_refresh` in the audit log). A workspace that is leased at that moment is left to its holder, and a lease that arrives before the collector reaches a workspace still passes it over once.

Collection with `--expire now` relies on jj sparing commits written after the collector started, which it decides from the modification time of each commit's loose `refs/jj/keep` file. jj newer than 0.26 fetches through a `git` subprocess, and git 2.54 ends a fetch with maintenance that packs every loose ref (git 2.48 does not). A lease that fetched during collection therefore removed that protection: `util gc` deleted the keep refs of commits written since it loaded the store, git pruned the ones written in the collector's first second, and the operation log then named a commit that no longer existed. Before collecting, the pass sets `maintenance.auto = false` in the store's git config and leaves it set; the store's packing is the pass's own `git gc`. If the setting cannot be written, the pass collects with jj's default two-week expiry instead of `--expire now`.

A pass that still finds the head advanced after its retries ends as a concurrent skip. That outcome counts toward the failure count that `cube workspace list` reports as needing attention, and the next upkeep is due within the hour rather than the day.

## Tests

`tools/boss/engine/recovery/jj_repository.bzl` pins the release archives by checksum. `@jj_test_tools` is 0.26.0 and `@jj_upgrade_test_tools` is 0.46.0.

- `//tools/cube:cube_lib_test`, `//tools/boss/engine/recovery:recovery_test` and `//tools/boss/engine/core:engine_lib_test` run on 0.26.0. Their `_jj_046_test` twins run the same tests on 0.46.0.
- The other jj-dependent targets (`app`, `work-db`, `completion`, `host-execution`, `test-git`) run on 0.26.0 in CI. To run them, or anything else, on 0.46.0, substitute the repository on the command line:

  ```sh
  bazel test --override_repository="+jj_test_repository+jj_test_tools=$(bazel info output_base)/external/+jj_test_repository+jj_upgrade_test_tools" //tools/boss/engine/... //tools/cube/...
  ```

- The additional packages do not have separate 0.46 twins because their jj transport is already exercised by the recovery and core twins: host-execution uses `LocalJj`; work-db stores recovery records without invoking jj; completion uses `LocalJj` for recovery and the shared `test-git::JjRepo` fixture for setup. Completion also directly runs `diff --from main@origin --to @ --summary`, covered by the cube twins. The app review-terminal helper directly runs only `git fetch` and `new <branch>@origin`, unchanged forms covered by the cube twins. The `test-git` helper itself is exercised by those twins. This covers the shared argument adaptation on every CI run; package-specific business logic remains covered by their default-version tests.

- Cube's mixed-version GC tests need a 0.26 client and a newer one whichever jj is under test. They take them from `CUBE_OLDEST_JJ_BIN` and `CUBE_NEWER_JJ_BIN`. The lease-during-collection test leases against the 0.26-written fixture store with the jj under test; it declares that version as the oldest client and exercises the full collection and concurrent-lease scenario on both versions (see [Store GC](#store-gc)).
- A test must never start jj from the Bazel working directory. On a developer machine that directory is inside the checkout, and jj 0.38 or newer would try to migrate the live shared store's configuration. Fixtures run jj inside the fixture repository.

## Upgrading the host

The upgrade procedure for [mono#3726](https://github.com/spinyfin/mono/pull/3726) follows. Measurements below came from private fixture stores, not the live mono store.

1. Pause dispatch and drain all workers and leases. Then **stop the engine completely before upgrading jj**: pausing dispatch leaves recovery and cleanup running, with cached version detection and short command deadlines. Keep it stopped through migration and reindexing.
2. Preserve a runnable jj 0.26 binary and a copy of the store metadata for rollback. Copy the macOS jj configuration from `~/Library/Application Support/jj/config.toml` to `~/.config/jj/config.toml`, preserving the original. In the new file replace `ui.diff.format = "git"` with `ui.diff-formatter = ":git"`.
3. Run `brew upgrade jj`; verify jj is 0.46.x and Git is at least 2.42. From a shell under the real user home, run `jj -R <store> --ignore-working-copy log --no-graph -r trunk() -T commit_id` (quote the revset in the shell). Let this first migration and reindex finish without a timeout. Then run `jj -R <store> workspace update-stale` under the real user home, with the engine still stopped. Earlier 0.26 collections can leave the primary working copy pointing at a deleted operation; migration alone does not refresh it. Check `jj -R <store> --ignore-working-copy config list --repo` for the expected trunk and snapshot settings. Repeat for each store.
4. Start the updated engine only after those commands finish. Provision a fresh scratch workspace (do not reuse a pooled workspace), position it on a PR, make a small commit and publish a disposable branch through `cube pr create`. Check that new workspaces have `.jj` and no `.git`, then close the smoke-test PR and release the lease.
5. Resume dispatch. Once every client has upgraded, `cube repo declare-oldest-jj <repo> 0.46` enables GC with the tested collector. Keeping the default declaration leaves GC refused safely.
6. To roll back, pause and drain again, stop the engine, restore the old binary first on PATH and verify its version. Complete any required index repair below before starting the engine. After 0.46 GC, restore the pre-upgrade metadata backup while all clients are stopped; this loses operations since that backup. Do not run 0.26 against a store collected by 0.46.

Version-specific observations:

- **First command.** The first 0.46 command in a store moves the repository configuration (see [Configuration](#configuration)) and rebuilds the commit index, because 0.39 dropped the index files 0.26 writes. On cube's 22,577-operation GC fixture store that took 5 to 10 seconds. The mono store's index is about 1.1 GB, so expect the first command there to take correspondingly longer; it runs once per store.
- **Evolution history.** jj 0.46 does not read predecessors recorded by jj older than 0.30, so `jj evolog` shows a commit written by 0.26 as having no history. Recovery uses evolution only to prove that a preserved commit is a rewrite of a recorded one, and treats missing proof as "not proven". Draining running executions before the upgrade avoids needing that proof across the version change.
- **Going back to 0.26.** After ordinary 0.46 use, 0.26 opened the same store again and re-indexed the new operations in about 2 seconds. Three things make it harder: `jj debug reindex` under 0.46 removes `.jj/repo/index/operations`, after which 0.26 fails with `Failed to associate commit index file with an operation` until that directory is recreated (0.26 then rebuilds its index, 14 seconds on the fixture); a store GC under 0.46 prunes history 0.26 needs (see [Store GC](#store-gc)); and workspaces created by 0.46 have relative pointers, which the engine and cube now read on either version.
