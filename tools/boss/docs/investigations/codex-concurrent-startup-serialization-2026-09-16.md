# Why concurrent Codex worker startups serialized on 2026-09-13, and why they do not in general

**Status:** answered. No repo change is proposed by this note; the one Boss-side option it identifies (turning off Codex plugins in the per-run config) is a capability decision for the operator, and admission pacing is already being handled in mono#2961.

**One-line answer:** there is no serialization point in Codex startup. Every lock the binary takes lives under the per-run `CODEX_HOME` or is an in-process semaphore, and launching 8 and 12 Codex sessions at once through Boss's exact pane shape, on this host at load averages between 58 and 321, created every rollout within 3 s and 8 s respectively. The 75–126 s delays on 2026-09-13 came from the host itself: the laptop woke from sleep at 21:38:12 UTC, its user session restarted at 21:38:31, the Boss app auto-launched into that restart storm at 21:39:18, and the engine admitted the whole ready backlog 65 s later. Everything on the host was starved in that window, including the engine (30 s to provision a home, 15–34 s to acknowledge a spawn) and the one Claude worker (117 s to its first record). Starved processes finish in the order the kernel gets to them, not the order they started, which is what produced the "last spawned, first rollout" signature that looked like a queue.

## What Codex does between `exec` and the rollout file

Measured on codex-cli 0.153.4 from the per-run `logs_2.sqlite` that Codex writes into each `CODEX_HOME`, for runs Boss started on 2026-09-16, and from the upstream source at tag `rust-v0.153.4`. Times are from the first log row of the process.

| Step                                                                                                                                                              | On the path to the rollout? | Network                                                                  | Solo timing                       |

| Binary load, config layers, macOS managed-preference lookups, log DB open                                                                                         | yes                         | none                                                                     | 0.2–0.7 s ¹                       |

¹ The shell figure comes from the reproduction harness below; the binary-load figure is the gap between the shell reaching the `exec` line and Codex's first log row.

`bootstrap_ms` in Codex's own `tui startup initial frame scheduled` log line covers everything from process start to the point the TUI can draw, and it was 320–500 ms in every solo Boss run on disk. The rollout is written a few milliseconds after that. So a rollout that appears two minutes after the pane was acknowledged means the process spent two minutes either before its first log row or inside a 400 ms bootstrap.

### The retry policy cannot stretch this to two minutes

The `models` request uses the provider's default `RetryConfig`: at most 4 attempts, base delay 200 ms, exponential backoff with ±10 % jitter (`codex-rs/model-provider-info/src/lib.rs`, `codex-rs/codex-client/src/retry.rs`). Total added delay is at most ≈3 s. If every attempt fails, `bootstrap` returns an error and the TUI exits (`shutdown_on_startup_error` in `codex-rs/tui/src/app/startup.rs`); a worker that later produced a rollout did not take that path. Auth refresh is also ruled out: the operator's `auth.json` token was issued 2026-09-07 16:50 UTC with a 10-day lifetime, and no per-run home on disk has ever rewritten its snapshot.

### The 120-second coincidence is a red herring

Four incident rollouts landed 123–126 s after activation, and `codex-rs/core-plugins/src/manager.rs` has `REMOTE_INSTALLED_PLUGIN_SYNC_WAIT_TIMEOUT = 120 s`. That gate is a `tokio::sync::Semaphore` inside one process, and only the `plugin/reconcile` app-server RPC and the background bundle sync take it. `thread/start` does not: in every run on disk the rollout was written 1–3 s **before** "completed remote installed plugin bundle sync" was logged. The 120 s figure that does matter is Boss's former discovery deadline, and the incident note already covers why those four missed it.

## Lock inventory: nothing is shared across per-run homes

Boss gives every run its own `CODEX_HOME` under `$TMPDIR/boss-codex-homes/<execution id>/`, with a byte-copied `auth.json`, a Boss-rendered `config.toml`, and `sessions` symlinked into that execution's own durable transcript directory. Nothing in it points at the operator's `~/.codex`. The lock-like paths compiled into the 0.153.4 binary, and where each one lives:

| Path or primitive                                                 | Scope                | Used at startup?                                                                              |
| ----------------------------------------------------------------- | -------------------- | --------------------------------------------------------------------------------------------- |
| `$CODEX_HOME/.tmp/plugins.sync.lock` (flock)                      | per home             | only for the git-based curated sync, which Boss homes do not run (no `.tmp/` is ever created) |
| `$CODEX_HOME/thread-writer-locks/`                                | per home, per thread | yes, uncontended                                                                              |
| `pid.lock` for the `app-server --listen` daemon                   | per home             | not on the TUI path                                                                           |
| `remote_installed_plugin_bundle_sync_gate` (semaphore)            | in process           | yes, off the rollout path                                                                     |
| `loaded_plugins_load_semaphore`, `non_curated_cache_refresh_lock` | in process           | yes, off the rollout path                                                                     |
| SQLite state/logs/history databases                               | per home             | yes                                                                                           |

The only things two concurrent Codex processes on one host genuinely share are the host (CPU, memory, disk), the network link and the ChatGPT backend, and the macOS daemons that TLS and preferences go through (`trustd`, `cfprefsd`). The unified log shows `trustd` idle apart from a 0.1 s trust-store asset lookup at 21:39:20 and 21:40:47 UTC, and no TCC prompt was raised in the window.

## Reproduction: concurrency alone does not do this

`codex-concurrent-startup-serialization-artifacts/repro-concurrent-codex-startup.sh` mirrors the worker launch shape one step at a time: a fresh `CODEX_HOME` per session with a byte-copied `auth.json` and a Boss-shaped `config.toml`; one detached tmux session per worker; each session runs `$SHELL -l -i -c <runner>` so the operator's interactive zsh init runs exactly as it does in a pane; the runner `exec`s `codex --strict-config --no-alt-screen -a never` with a one-word prompt so the startup thread is created immediately, as Boss's prompt-on-the-command-line does. It records four timestamps per worker: tmux launch, the shell reaching `exec`, Codex's first log row, and the rollout file appearing.

Run on this host on 2026-09-16 while Boss's own workers were running builds:

| Run        | Load average at launch | Launch → shell at `exec` | Shell → first Codex log | First log → thread start | Launch → rollout | `bootstrap_ms` |
| ---------- | ---------------------- | ------------------------ | ----------------------- | ------------------------ | ---------------- | -------------- |
| 1 solo     | ≈58                    | 2.2 s                    | 0.6 s                   | 0.4 s                    | ≈11 s ²          | 346            |
| 8 at once  | ≈58                    | 1.3–1.4 s                | 0.2–0.3 s               | 0.7–1.3 s                | 2.6–3.1 s        | 653–1240       |
| 12 at once | ≈321                   | 3.3–4.1 s                | 2.6–2.9 s               | 0.5–1.1 s                | 7.1–8.3 s        | 340–1054       |

² The solo run's rollout was detected late because the harness polled `find` over the sessions tree; the filename timestamp puts the rollout 11 s after launch, of which 5.8 s was zsh init on that particular start.

Contention is visible and it is the ordinary kind: `bootstrap_ms` roughly doubles or triples at 8- and 12-way, and the pre-log stage (binary load plus config) grows from 0.3 s to 2.8 s under a load average over 300. Nothing serializes. Twelve simultaneous fresh-home starts, twice the incident's concurrency on a far busier host, all had rollouts within 8 s. Boss's own homes on disk agree: three workers started within two seconds of each other at 22:38:08–10 UTC on 2026-09-16, and the two whose log rows survived reached `thread/start` in 0.7 s and 1.0 s.

The Codex rollouts landed in exactly the interval in which the host stopped being saturated. Every process measured in the incident was slow by the same order of magnitude: the engine's own file writes, the tmux spawn, the Claude driver and the Codex driver. That is the signature of a shared host resource, not of a lock in one binary.

### About the ordering argument

The brief's premise was that a machine short of CPU would serve processes roughly in start order, so the worker whose pane spawned last (21:40:42) having its rollout first (21:42:21) pointed to a queue. It points the other way. A queue or lock with a per-holder cost would space the rollouts out by that cost; instead six rollouts landed in a 15 s band with one 40 s earlier, and the band coincides with the end of the storm. Under starvation, the order in which sleeping processes get CPU, page-ins and disk I/O back depends on where each one was in its own backoff, page-fault or I/O wait when the resource freed up, and start order does not survive that. The reproduction shows the same non-monotonic completion order at 12-way (w2, w3 and w6 finished first, w4, w7 and w9 last) with no lock present.

What this note cannot say is which host resource bound first (CPU, memory pressure after wake, or disk), because the per-run homes and their `logs_2.sqlite` were reclaimed before that could be checked, and the unified log records neither `memorystatus` events nor per-process CPU at the default level. The two figures that would settle it on the next burst are Codex's own `tui startup initial frame scheduled … bootstrap_ms=` line and the gap between the pane's shell reaching `exec` and that first log row; both are in the home for as long as the home exists.

## Is any of it in `spinyfin/mono`?

The serialization itself is not: Codex has no cross-process lock on this path and the reproduction shows none. Two things Boss does are relevant to how badly that window hurt, and both are already in Boss's hands.

1. **Admission timing after an engine restart.** The engine resumed dispatch 65 s after the user session restarted and admitted six executions within 7 s into a host that was still initialising every user agent and streaming an App Store update. mono#2961 already paces resumed dispatch on live driver-start proof, which is the right signal: a canary that reaches its first driver signal quickly proves the host is ready in a way no slope model can. One correction for that work: its discovery-deadline formula, `min(240, 120 + 9 × (peak − 1))`, is calibrated on the incident's "78–84 s alone, 119–120 s at six-way" first-driver-signal numbers as if they were a per-worker concurrency cost. They were not: 8-way and 12-way starts here reach the rollout in 3 s and 8 s. The longer deadline is harmless, but nobody should read the slope as a measured property of Codex, and "first driver signal" for a Codex worker includes the first model turn, which is a different quantity from rollout creation.

2. **Per-worker startup cost that Boss's fresh homes impose.** Because every run starts from an empty `CODEX_HOME`, every worker start re-downloads the 21.4 MB remote plugin catalog, the 1.5 MB apps manifest and six curated plugin bundles it never uses, and runs the operator's interactive zsh init (`compinit` twice, `jj util completion zsh`, `nvm.sh`). Six workers at once is ≈140 MB on the link during the startup window. None of it is on the rollout path, and at the 31 MB/s measured here it is a few seconds, but on a slower link or a busy host it competes with the one `models` request that is on the path, and the first model turn appears to wait for the bundle sync to finish (turn dispatch followed "completed remote installed plugin bundle sync" by 0.6–1.0 s in the two runs where both were visible).

   Verified option: adding `plugins = false`, `remote_plugin = false` and `recommended_plugins = false` to the `[features]` table Boss already renders loads cleanly under `--strict-config` on 0.153.4, removes the catalog fetch and the bundle sync entirely (`cache/` shrinks from 23 MB to 1.4 MB, no `plugins/` directory is created), and leaves `bootstrap_ms` at 265 ms. The cost is that workers lose Codex plugins. Boss workers are given `gh`, `cube` and `boss` on the command line rather than plugins, so this is likely free, but it is a capability decision and this note does not make it.

Pre-seeding `cache/` and `plugins/` from a warm home would keep plugins while avoiding the downloads, but the catalog cache is keyed by a content hash with a TTL that was not verified, so that route is untested.

## Heads-up: the shared auth snapshot is the next startup-time shared resource

Every worker home carries the same byte copy of the operator's `auth.json`. The access token in it was issued 2026-09-07 16:50:10 UTC and expires 2026-09-17 16:50:10 UTC. The first burst after expiry will have every Codex process refresh at once with the same refresh token, and Codex's auth manager treats a reused refresh token as a hard error ("your refresh token was already used"). Whether OpenAI's token endpoint tolerates concurrent reuse within a grace window is unknown; the SnapshotWithRefreshAdoption policy in `tools/boss/codex_auth` exists for exactly this and has not yet been exercised by a burst.

## Method

- **Startup anatomy:** `sqlite3 "$CODEX_HOME/logs_2.sqlite" 'select datetime(ts,"unixepoch"), ts_nanos, level, target, feedback_log_body from logs order by ts, ts_nanos, id'` on Boss homes under `$TMPDIR/boss-codex-homes/`. The log DB prunes rows while the session runs; copy `logs_2.sqlite*` out first.
- **Lock inventory:** `strings -n 8 ~/.codex/packages/standalone/current/bin/codex | rg -i 'lock|flock|\.sock'`, cross-checked against `codex-rs/core-plugins/src/{startup_sync,manager,remote}.rs`, `codex-rs/thread-store/src/local/writer_lock.rs` and `codex-rs/tui/src/app/startup.rs` at `rust-v0.153.4` (`042fb41b7c81`).
- **Host timeline:** `log show --start … --end … --info` with predicates on `com.apple.TCC`, `process == "powerd"`, `process == "trustd"`, the network daemons, and the App Store install daemons; volume per 10 s from the raw dump.
- **Reproduction:** the harness in the artifacts directory; see its header for usage. It uses the operator's real `auth.json` exactly as Boss does and runs one one-word model turn per session.
