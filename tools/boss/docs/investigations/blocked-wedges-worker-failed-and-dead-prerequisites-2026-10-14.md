# Why work items wedge in `blocked`: worker-declared blocked is terminal, and dependents queue behind dead prerequisites

- **Date:** 2026-10-14
- **Kind:** investigation (doc only; no code changed)
- **Code revision examined:** `main` at `db4d0333` ("boss: worker names and portraits from the 56-character crew grid", mono#3176). All `file:line` references below are against that revision, rooted at `tools/boss/`.
- **Evidence:** the engine log excerpts, the worker's `run_done` proposal, and the read-only DB snapshot inlined in the work item brief. The live DB and logs were not opened. Where a claim needs a DB check the owner can run, it is called out as such.
- **Trigger:** a project task with an open PR (spinyfin/mono#3170) shows as blocked on the board although it is `in_review`. Three revisions under it form the wedge described below.
- **Related docs:** [`designs/revision-tasks.md`](../designs/revision-tasks.md) (chain-tail gate), [`designs/work-dependencies.md`](../designs/work-dependencies.md) (satisfaction rules), [`designs/worker-proposal-api-replace-fragile-worker-to-engine-seams.md`](../designs/worker-proposal-api-replace-fragile-worker-to-engine-seams.md) (ancestry attribution), [`postmortems/incident-004-live-revision-workers-reaped-mid-turn.md`](../postmortems/incident-004-live-revision-workers-reaped-mid-turn.md) (why retired spawning attempts settle to `blocked`), [`attention-lifecycle.md`](../attention-lifecycle.md).

## Plain-language summary

A worker ran a Boss command a few seconds too early, the engine did not yet recognise the worker, and the command failed with an error that reads as "engine unavailable". The worker gave up and told the engine it was blocked. The engine treats "a worker said it is blocked" as final: it parks the task, switches off automatic restart, and never looks at it again. Nothing tells you this happened. Later, the engine created a follow-on revision and, by rule, made it wait for the most recent revision in the chain, which was the parked one. Waiting on something that will never finish is waiting forever, and the parent task shows as blocked on the board for as long as that lasts.

A second incident needs no worker mistake: a flunge conflict-resolution worker correctly found its PR obsolete, but declaring blocked failed the revision and stranded its parent chore in merge_conflict. Obsolete work needs a distinct resolution that settles the parent or an actionable decision on its kanban card (sections 1.1 and 7, PR 7).

Three separate rules each did what they were written to do. Put together they produce a state nothing leaves. The fixes are to stop treating engine-side failures as a worker's final word, to never make a new revision wait on a sibling that has already died, and to make a dead prerequisite loud instead of silent.

## Verdict

- **(a) Attribution.** The `boss pr status` refusal was a transient engine-side gap, not a codex process-tree problem. The same worker's `propose done` call was attributed fine 36 seconds later through the same code path. The code admits a registration window at spawn: the worker starts running before the engine registers its pane pid, and the registration waits behind a round trip to the macOS app of up to 30 seconds (`engine/core/src/spawn_flow.rs:933-1018`). Codex's tree is 4 to 5 hops deep against a walk limit of 8, so depth is not the cause. A second compounding bug: the CLI reports every attribution refusal as exit 5 "engine unavailable" (`cli/src/propose.rs:1014-1020`, `cli/src/main.rs:210`), which is what led the worker to declare blocked.
- **(b) Worker-declared blocked is terminal by construction.** `run_done outcome=blocked` is auto-applied with no inspection of the reason (`engine/core/src/work/proposal_apply.rs:94-117`), writes `status=blocked, blocked_reason=worker_failed, autostart=0` in one statement (`engine/core/src/work/pr_flow.rs:535-552`), and every automatic path refuses to mint another execution for that reason (`engine/core/src/work/exec_status_helpers.rs:241-249`, `engine/core/src/work/dispatch_helpers.rs:507-516`). The only exit is a human explicit start (`engine/core/src/work/dispatch_helpers.rs:1389-1397`). No attention item is filed: the kind reserved for it has no production writer.
- **(c) Dependents queue behind dead prerequisites.** The chain-tail gate picks the newest revision whose status is `todo`, `active` **or `blocked`**, with no look at `blocked_reason` (`engine/core/src/work/revision_helpers.rs:55-89`), so a `worker_failed` revision is chosen as the tail and the new revision is gated on it (`:208-213`). A `blocked` prerequisite never satisfies a gate (`engine/core/src/work_dependencies.rs:365-396`), and nothing propagates a prerequisite's failure to its dependents. The "A ran despite C" half is almost certainly a retroactive edge: when a merge-conflict revision is minted it re-gates every unfinished sibling behind itself, explicitly including failed rows (`engine/core/src/work/revision_sequencing.rs:138-142`). The dispatch gate is enforced on every path, so A could not have dispatched with that edge already present.

## 2. Root cause (a): the attribution refusal

### 2.1 How attribution works

Every worker-scoped verb (`get_pr_status`, `submit_proposal`, `get_worker_context`, `get_pr_body`) resolves the caller through one function, `attribute_caller` (`engine/core/src/app/proposals.rs:197-258`). It takes the Unix-socket peer pid and walks the process tree upward looking for a pid the engine registered at spawn: `WorkerRegistry::lookup_with_ancestor_walk` (`engine/core/src/worker_registry.rs:262-273`), capped at `ANCESTOR_WALK_DEPTH = 8` (`:22`). `BOSS_RUN_ID` is only a cross-check and "never grants anything" (`proposals.rs:215-228`). There is no fallback: when the walk finds nothing the verb is refused with `attribution_unresolved` (`:204-213`). The "keeps `User` tier" wording in `engine/core/src/app/trust.rs:85-92` only means an unclassified peer escapes the verb allowlist; it does not make these verbs succeed.

The registered pid is the tmux `#{pane_pid}`, the login shell that runs `. .boss/initial-input.sh` (`spawn_flow.rs:96-102`, `runner/pane_spawn.rs:462-471`). Codex is launched as a child of that shell with no `exec` and no wrapper (`engine/driver/src/codex.rs:1103-1117`). With the `codex_sandbox_enforced` flag off, which is the default, codex runs at `danger-full-access`, so there is no `sandbox-exec` layer either (`codex.rs:529-544`). The `boss` launcher is a one-line `exec` (`engine/worker-bin/src/lib.rs:417-427`). The tree for a codex tool call is therefore `boss` → `zsh -lc` → `codex` → pane shell: 3 hops, 4 to 5 under the sandboxed configuration, against a cap of 8. Depth is not the problem in the normal configuration.

### 2.2 Why this instance was transient, and the specific condition

The decisive fact is in the brief itself: the rejected `get_pr_status` at 20:15:15 and the accepted `run_done` at 20:15:34 went through the same `attribute_caller` from the same worker. Whatever broke the walk at 20:15:15 had healed 19 seconds later. That rules out a persistent tree-shape problem and points at the registry.

There are exactly three production call sites that register a pid, and none that unregister (`WorkerRegistry::unregister` at `worker_registry.rs:234` has only test callers):

1. **Spawn** (`spawn_flow.rs:1018`). This is the leading candidate and the one the code already admits. The order inside `start_worker_armed` is: create the tmux session, which starts the login shell and codex immediately (`:383-392`); read `#{pane_pid}`; then **await** `send_to_app_request(AttachWorkerPane, spawn_timeout)` (`:964-1012`) with `spawn_timeout = 30 s` (`runner/pane_spawn.rs:1240`); and only then `register(shell_pid, run_id)` (`:1018`). A comment at `spawn_flow.rs:696-698` says it plainly: "the CLI is running, and its hooks can land, before the pane-attach await returns." The comment at `engine/core/src/app.rs:2305-2311` claims the opposite ("registers the real tmux-reported shell pid synchronously, before the pane's first `boss` call") and is wrong. Codex reads its prompt and issues its first tool call within tens of seconds. The worker brief tells it to check `boss pr status` before deciding anything. Under load, with the app slow to answer the attach request, those two intervals overlap. The scheduler heartbeat warnings minutes earlier show the engine and app were busy at exactly that time.
2. **Boot adoption after an engine restart** (`engine/core/src/tmux_adoption.rs:899`). The registry is in memory only. The boot pass re-registers live tmux sessions, and the husk-pane sweep repeats the pass every 60 s. Several skip conditions leave a worker unregistered until a later pass succeeds (tmux owner mismatch, `#{pane_pid}` unreadable, pane judged not live). There is no evidence of a restart in this incident, so this is a condition for other occurrences, not this one.
3. **Readoption of a run the engine wrongly finalised** (`engine/core/src/app/readoption.rs:440-442`). It registers only when it observed a positive `shell_pid`; a `shell_pid == 0` row is readopted with no pid, so every attributed call from that worker fails for the rest of the run.

A fourth, non-registry condition exists but does not fit this instance: `parent_pid` returns `None` at ppid 0 and the walk also aborts on any `proc_pidinfo` error (`worker_registry.rs:263-272`), so a `boss` process whose parent exited (reparented to launchd) or whose intermediate parent died mid-walk resolves to nothing. Codex's `exec` runs tool commands as direct children and nothing in Boss detaches them, so this would need codex itself to reparent, which the repo cannot show either way. The design already names this edge case and chose "strictly closed" (`designs/worker-proposal-api-replace-fragile-worker-to-engine-seams.md:253`).

**How to confirm which condition fired here (owner DB and log check):** compare the timestamp of the `"attached tmux-hosted worker pane"` info line for A's execution (`spawn_flow.rs:983`) with the 20:15:15 rejection. If the attach line is at or after 20:15:15, condition 1 is proven. The same window also explains why hooks are buffered at spawn but RPC calls are not: `start_worker` arms a hook buffer for exactly this race (`spawn_flow.rs:696-704`) and nothing equivalent exists for the frontend socket.

### 2.3 The compounding bug: the error is mislabelled "engine unavailable"

`render_proposal_rejection` maps `NoLocalPeer`, `AttributionUnresolved`, `AttributionMismatch` and `UnknownExecution` all to `CliError::engine_unavailable` (`cli/src/propose.rs:1014-1020`), which exits 5 (`cli/src/main.rs:210`), the same code a dead socket gets. The client's transport retry policy does not apply to a typed rejection, so the call fails once and immediately. The worker saw "exit 5, engine unavailable, cannot be attributed", read its brief ("a `$BOSS_BIN` command that fails to run at all is a finding"), and declared blocked with a summary asking the coordinator to "restore worker-session attribution". That is a reasonable reading of a misleading signal. The three-of-64 attribution mentions in blocked declarations over the last 14 days are most likely the same shape: an early first `boss` call hitting the registration window, then an exit code that looks infrastructural.

## 3. Root cause (b): worker-declared blocked is terminal and silent

### 3.1 The path

1. `submit_proposal` attributes the caller, then applies by kind. `apply_policy` maps `RunDone` (and `Blocked`) to `AutoApply` (`engine/core/src/work/proposal_apply.rs:94-117`); `decided_by=policy` means "auto-applied by kind", not that anyone judged the content. The summary text is never parsed for meaning. The only text inspection anywhere is the queue-CI evidence gate for Trunk eviction attempts (`engine/core/src/work/queue_ci_evidence.rs:363-403`), which can refuse a declaration but never retries.
2. `finalize_declared_blocked` (`engine/core/src/completion/run_done_declaration.rs:295-316`) builds the fixed text "This attempt will not be retried automatically" and calls `finalize_worker_failure_or_question`.
3. `record_worker_failure_or_question` (`engine/core/src/work/pr_flow.rs:453-606`) marks the execution `failed`, releases lease and workspace columns, and for a task in `active`/`todo` runs a single update: `status='blocked', blocked_reason='worker_failed' (or 'awaiting_operator_answer' when a question was attached), blocked_detail=<summary>, autostart=0, last_status_actor='engine'` (`:535-552`). If the task was already blocked for a domain reason (CI, conflict), only the detail is appended (`:554-567`).

Note that `autostart=0` is set here deliberately, not merely consumed at run start (run start also clears it, `engine/core/src/work/executions_runs.rs:1274-1295`). Either way the row ends with the flag off.

### 3.2 Why nothing leaves it

- `task_accepts_execution` refuses `worker_failed` and `awaiting_operator_answer` outright: "A worker failure is not a dependency wait: only an explicit retry may start another attempt" (`exec_status_helpers.rs:241-249`).
- `reconcile_work_item_execution` returns early for the same two reasons before it even evaluates prerequisites (`dispatch_helpers.rs:507-516`), so dependency cascades cannot wake it.
- The dispatch-failure recovery sweep selects only `todo`/`active` rows (`engine/core/src/work/dispatch.rs:421-433`). The dependency unblock sweep handles only `dependency`. Transient recovery handles live idle workers, not finished runs.
- The sole exit is a human explicit start: a board drag to Doing or `bossctl work start`, which reaches `request_execution_in_tx_with_live_check` and clears the reason (`dispatch_helpers.rs:1389-1397`, comment: "Automatic reconciliation cannot reach this clear"). A manual status change off `blocked` also nulls the reason (`engine/core/src/work/updates.rs:599-605`) but leaves `autostart` off.

### 3.3 Why nobody is told

`RUN_DONE_BLOCKED_ATTENTION_KIND` (`"run_done_declared_blocked"`, `engine/core/src/completion.rs:301`) is read by the attention lifecycle and the dispatch-admission facts, and is constructed in tests, but **no production code files it**. A test comment claims "Production always files an open `run_done_declared_blocked` attention item alongside the column stamp" (`engine/core/src/work/dispatch_admission.rs:474-477`); that is stale. Contrast the delivered-without-PR path, which does file `run_done_audit_flagged` (`run_done_declaration.rs:270-284`). The only attention a blocked run can raise is `worker_blocked`, and only if the worker separately ran `boss propose blocked`. Even then, as the brief states, an attention item is not a notification the owner reads. The visible residue is a Backlog card (`engine/board-gesture/src/lib.rs:86-99`), its `blocked_detail` tooltip, and `work_runs.error_text`.

### 3.4 What workers are told

The run-done directive says `blocked` "fails the execution, releases its resources, and records the explanation on the task; it does not park a live worker or automatically retry the same attempt. Fix recoverable failures first." (`engine/core/src/runner/prompt.rs:1130-1134`). It never defines what counts as recoverable, and the worker CLAUDE.md fragment tells workers a failing `$BOSS_BIN` command "is a finding, not noise" (`engine/core/src/worker_setup.rs:445-449`) without saying to retry it. A worker that hits an engine-side refusal has no instruction that would lead it anywhere but `blocked`.

### 3.5 Classifying blocked declarations

The brief reports 64 `run_done outcome=blocked` proposals in 14 days, 3 of them mentioning attribution. Two proposal bodies are now in evidence, including flunge supplied separately. They establish two classes, not a revised distribution of the original snapshot.

Never park.                                                         | The mono instance. The other two attribution mentions almost certainly belong here. |
| **Engine fault, persistent** | Same surface, but the condition will not clear without an engine fix: readopted run with no registered pid, missing control token, broken launcher.                  | Park with a distinct reason (`engine_fault`), file for the engine owner, do not count against the task.                                              | Not distinguishable from the summaries alone; needs the execution's run log.        |

Also separate candidate obsolete/superseded declarations and verify their replacement evidence; do not treat everything else as a human decision. Flunge shows that engine faults are not the whole problem. Text grouping is an investigation aid, not a production decision rule.

## 4. Root cause (c): dependents behind dead prerequisites

### 4.1 Where the B→A edge is minted

Every revision producer (review verdict apply at `engine/core/src/work/review_verdict_apply.rs:449-467`, CI watch, conflict watch, the CLI) goes through `assert_parent_revisable_and_insert` (`revision_helpers.rs:109-248`). Step 5 snapshots the chain tail with `find_latest_active_revision_in_chain` (`:55-89`), whose predicate is:

```sql
WHERE t.status IN ('todo', 'active', 'blocked')
  AND NOT EXISTS (... a 'blocks' successor in the chain with status IN ('todo','active','blocked'))
ORDER BY c.id DESC LIMIT 1
```

There is no `blocked_reason` filter. The doc comment at `:45` assumes "blocked" means "waiting on a prerequisite". A `worker_failed`, `spawning_attempt_retired_unsuccessfully`, `execution_recovery_failed` or human-parked revision is therefore chosen as the tail. Step 8 then inserts the edge and auto-blocks the new row (`:200-213`), and step 9 births its execution as `waiting_dependency` (`:240-243`). Conflict revisions skip the tail (`:174-178`) and use their own sequencing instead.

### 4.2 Why a dead prerequisite blocks forever

`gating_prereqs_for` (`engine/core/src/work_dependencies.rs:365-396`) treats a prerequisite as satisfied only at `done`/`archived`, plus `in_review` for a same-chain revision dependent (`:268-273`, `:383-393`). Every other status, including `blocked` for any reason, gates (`:395`). The unblock cascade fires only when a prerequisite moves to a status that "might satisfy" (`engine/core/src/work/dep_helpers.rs:786-789`), so a move to `blocked` triggers nothing. `dep_unblock_sweep` and `promote_waiting_writers` (`revision_sequencing.rs:175-208`) both promote only when the gate set is empty. No code path propagates a prerequisite's terminal failure to its dependents, marks them stuck, or files an attention item. The dependent's execution sits in `waiting_dependency` with only the queued-wait reason and a stale-seconds gauge as evidence.

The engine already knows how to do better for one case. A **conflict** revision waits for a same-chain writer to _stop_, not to _succeed_: `conflict_writer_gate` (`revision_sequencing.rs:61-79`) is consulted first in `gating_prereqs_for` (`work_dependencies.rs:370-380`, comment: "A failed writer must not strand the branch's rebase"). Review revisions get no such treatment.

### 4.3 How A came to "depend on" C yet ran first

The dispatch gate is enforced at mint (`dispatch_helpers.rs:995-1000`), at explicit start (`:1313-1319`), at the dispatcher rescan (`engine/core/src/work/dispatch.rs:748`), and once more at spawn, where a `ready` row with an unmet gate is downgraded and skipped (`engine/core/src/coordinator/execution.rs:796-842`). The only hole is a DB error during that last check, which proceeds "rather than blocking all dispatches" (`:844-849`). So A could not have dispatched while an A→C edge existed. Two orderings fit the evidence:

1. **The edge is retroactive (most likely).** C was created after A had already failed. `prioritize_conflict_revision` (`revision_sequencing.rs:114-167`) walks every chain member: a member with a live writer becomes C's prerequisite; any other revision that `can_still_change_pr()` (which includes `blocked`, `protocol/src/types/task.rs:65-67`) or has a pending writer gets the reverse edge, member→C, with the comment "Every queued row also waits for the conflict fix, including a failed row that a human may retry while the fix is in flight" (`:138-142`). A, in `blocked/worker_failed`, matched and received A→C. The edge then looks like an unmet prerequisite that A "ignored", when in fact it did not exist when A ran. `maybe_engine_block_dependent` leaves A's reason alone because the row is already `blocked` (`dep_helpers.rs:474-476`).
2. **C existed first and counted as satisfied.** If C had a retired spawning attempt that succeeded, `reconcile_revision_execution` settles it straight to `in_review` (`dispatch_helpers.rs:938-954`), which satisfies a same-chain gate; a later explicit start can reopen it (`:932-937`). A would then have been born ungated at 20:12:53 and C's later 20:56 run would be a reopen.

**Owner DB check:** compare `work_item_dependencies.created_at` for the A→C edge with A's execution `started_at`. Ordering 1 predicts the edge is newer than the run; ordering 2 predicts C has an earlier retired attempt row. Either way the fix is the same: the gate is working as designed, and the defect is the edge being pointed at a dead row (section 4.1) and the dead row never releasing it (section 4.2).

### 4.4 Why the root shows as blocked

`attach_in_progress_revision_flag` (`revision_helpers.rs:390-446`) marks a root `in_revision_blocked_only` when every open revision under it is `blocked`, and `classify_review_section` maps that to the Review lane's Blocked section ahead of InRevision, AiReview and Ready (`engine/core/src/work/review_section.rs:64-70`). The root's own `status` and `blocked_reason` do not change; the badge is purely derived, and it will stay "blocked" for as long as B waits on A.

## 5. Taxonomy of `blocked_reason`

`blocked_reason` is free text with no enum. The values the engine writes today, what leaves each, and what should:

| Reason                                    | Set by                                                                                    | Leaves it today                                                                                                                                         | Should                                                                                                                                                                                  |
| ----------------------------------------- | ----------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |

## 6. Reading the scale snapshot

The snapshot lists 135 non-deleted `blocked` rows. Most are not wedges:

- **`dependency` rows (107: 94 project tasks, 6 investigations, 4 revisions, 3 chores).** The ordinary planned-work shape. A project task waiting on a sibling is correct unless the sibling is itself terminal. The snapshot's second list is the filter that matters: dependents whose prerequisite is blocked for a non-dependency reason.
- **`merge_conflict` (9) and `ci_failure_exhausted` (2).** Have conditional automatic or documented human exits; inspect repair revisions before calling these healthy waits. The two conflict prerequisites that each hold several project tasks ("Guarded action executor" with 5, "Engine metric-series query surface" with 3) are the live cost of one unresolved conflict fanning out; the separately supplied flunge evidence shows a conflict ladder can itself wedge. It does not identify which of these nine rows share that cause. The fan-out is invisible for the same reason as section 4.2.
- **`worker_failed` (12: 6 revisions, 4 chores, 2 project tasks) and `spawning_attempt_retired_unsuccessfully` (5 revisions).** These are the terminal-by-construction rows. Every dependent behind one of them is a wedge by this doc's definition. The snapshot shows four such chains: the review revision B of this incident; a revision behind a retired CI-fix revision; a revision behind a retired revision whose own prerequisite is also retired (a two-deep dead chain); and a project task behind a `worker_failed` row.

**Separating stale-by-design from live:** a dependent whose chain root (or project) is itself `done`, `archived`, or belongs to a project with no activity in 30 days is stale and should be archived with its prerequisite, not unblocked. A dependent whose chain root is `in_review` with an open PR, or whose project has recent activity, is live. By that rule the incident's chain is live (open PR, review cycles still running), and the two revision-behind-retired-revision chains need the same check against their PRs' state. The owner can apply it with one query joining `work_item_dependencies` to the chain root's status and the PR's `pr_state_polled_at`.

## 7. Recommended fixes, as separate PRs

Ordered by how much of the wedge each removes. Each is small enough to review alone.

### PR 1. Register the pane pid before anything can call in (fixes a, root)

In `start_worker_armed` (`spawn_flow.rs:933-1018`), call `worker_registry().register(shell_pid, run_id)` immediately after `start_tmux_worker` returns the pid and before the `AttachWorkerPane` await. The abort path on `SlotBusy` must then unregister, which is the first production use of `WorkerRegistry::unregister` (`worker_registry.rs:234`) and the reason it should keep a unit test. Fix the stale comment at `app.rs:2305-2311`. Add a test in the spawn-flow suite that asserts the pid is registered while the attach future is still pending (a fake spawner whose `send_to_app_request` blocks until the test releases it). This is the whole fix for the reported occurrence and most likely for the other two attribution mentions.

### PR 2. Make attribution refusals look like what they are (fixes a, worker behaviour)

Give `AttributionUnresolved` its own CLI exit code and message in `cli/src/propose.rs:1014-1020` instead of folding it into `engine_unavailable`, and have the worker-facing text say "retry this command; if it fails three times in a row, report it in your final response as a finding" rather than nothing. In the engine, when `attribute_caller` fails for a peer pid that the registry has **no** entry for anywhere up the chain, log the walked pid chain (pid, ppid pairs) at warn level so the next occurrence is diagnosable from the log alone. Optionally, make `attribute_caller` retry the walk once after a short sleep when the registry is non-empty, which covers the mid-walk `proc_pidinfo` race without changing semantics.

### PR 3. Engine-side blockers are not a worker's final word (fixes b, policy)

Introduce a classification step in `finalize_declared_blocked` (`run_done_declaration.rs:295-316`) that reads the execution's own evidence, not the free text: whether any `boss`/`cube` command in the run's tool stream ended with an attribution or engine-unreachable rejection, and whether the run's recent `boss` calls were all refused. When the declaration matches the engine-fault class and the execution has not already been retried for that reason, finalise as a _retryable_ failure: mark the execution `failed`, keep the task in `todo` with `autostart` intact and a `retry_after` stamp, and let the ordinary dispatcher mint a fresh attempt once. If the second attempt also declares blocked, fall through to today's `worker_failed`. The budget is one retry, keyed on the execution id, which is what makes this not a blanket auto-retry loop. The prompt at `prompt.rs:1130-1134` should name the engine-fault case explicitly: "If a Boss command is refused with an attribution or engine-unavailable error, that is not a blocker; retry it, and if it keeps failing, deliver what you have and report it."

### PR 4. A genuine blocked stop notifies the owner (fixes b, visibility)

Wire a production writer for `RUN_DONE_BLOCKED_ATTENTION_KIND` (`completion.rs:301`) in `finalize_declared_blocked`, so the test contract at `dispatch_admission.rs:474-477` is true again, and route that kind (and `awaiting_operator_answer`) through whichever channel the owner actually reads. The brief says attention items are not that channel; the engine already has a push-notification seam for the macOS app and a coordinator probe path, and either is better than a Backlog card. The item must carry the worker's summary and a one-click "retry" that calls the explicit-start path (`dispatch_helpers.rs:1389-1397`).

### PR 5. A new revision never takes a dependency on a terminal sibling (fixes c, mint)

Change `find_latest_active_revision_in_chain` (`revision_helpers.rs:55-89`) so `blocked` counts as live only when `blocked_reason IN ('dependency', 'merge_conflict', 'ci_failure', 'ci_flaky_retriggered')`, mirroring `conflict_fix_in_flight` (`revision_sequencing.rs:49-57`), and apply the same predicate to the `NOT EXISTS` successor clause. A `worker_failed`, `spawning_attempt_retired_unsuccessfully`, `execution_recovery_failed` or human-parked sibling is then skipped and the new revision is born `ready` (or gated on the next live sibling up the chain). Do the same in `prioritize_conflict_revision` (`revision_sequencing.rs:131-147`) so a conflict fix does not re-gate a dead row, which today creates an edge that is inert for the dead row but misleading in every listing. Add the test the existing one at `app/tests/board_drag_gated_revision.rs:218-231` is the inverse of: "a review revision minted after a `worker_failed` sibling is not gated on it."

### PR 6. A terminal prerequisite surfaces its dependents as stuck, loudly (fixes c, existing rows)

In the status-change cascade (`dep_helpers.rs:786-789`), when a prerequisite enters a terminal non-dependency `blocked` reason, enumerate its `blocks` dependents and, for each one that is `waiting_dependency` or `blocked/dependency`, file one attention item of a new kind (`prerequisite_terminal`) naming the prerequisite, its reason, and the two sanctioned actions: retry the prerequisite, or remove the edge deliberately. Add a sweep over existing rows at startup so the four chains in the snapshot are surfaced on the first boot after the change. Make the queued-wait reason (`engine/core/src/work/queued_wait.rs:23-28`) say "waiting on a failed prerequisite" instead of "waiting_dependency" so the card and `bossctl` show the difference. This PR changes no edges and no statuses; it only makes the state visible.

### PR 7. Give obsolete work a resolution that settles its parent (fixes b, flunge)

Add a typed `superseded` outcome for work that is no longer needed, distinct from delivery, worker failure, and a revision-only no-op. Require structured evidence identifying the parent PR, replacement PR/commit, observed base/head, and which acceptance requirements are already satisfied or invalidated. Extend protocol validation, CLI, worker guidance, finalization, and parent reconciliation together. Do not classify obsolescence by matching summary text or claim a merge that never happened.

Automatic closure avoids unnecessary owner decisions when complete replacement can be independently verified, but an agent’s semantic judgment can discard requirements that still matter. **Recommend owner confirmation for semantic obsolescence, with automatic settlement reserved for an explicit policy that verifies complete replacement.** Accept the claim as a non-failure proposal; the flunge evidence should become a resolution decision, not a failed worker to retry.

Reuse the durable question and inline kanban pattern in [Needs Attention](../designs/needs-attention-blocked-workers-ask-the-operator-a-typed-question-on-the-kanban.md). Put “Close this work because it has already been replaced?” on the parent card with the replacement evidence in its details, including for chores. That design explicitly omits chore question presentation, so its task-only path is insufficient here. Use a distinct resolution action: today's Yes restarts a worker and No returns to `worker_failed`. For supersession, Yes should authorize closing the obsolete PR and settling the parent chain; No should reject the claim and offer explicit continuation/retry. An unanswered question stays visible on the card. An attention item, notification, or PR comment alone is insufficient.

On confirmation (or policy-verified automatic settlement), close the obsolete GitHub PR without merging, terminalize the parent with a recorded superseded resolution, clear its conflict blocker, and settle obsolete queued revisions while retaining history. Coordinate remote closure and local settlement through durable, idempotent retry; a GitHub failure must remain visible and recoverable. Recheck the PR head and chain before applying a decision: new requirements, a changed head, or an active writer invalidate stale evidence. Reconcile dependents by their requirements, not just by the parent's terminal status: cancellation must not masquerade as delivery merely because `archived` currently satisfies a gate. Unproven dependents need a visible decision.

Proposed acceptance tests must reproduce the flunge parent/conflict-revision pair and verify settlement of both without another conflict revision; chore card visibility before confirmation; deliberate continuation after rejection; and safe handling of duplicate declarations/answers, changed heads, active siblings, remote-close failure, and unsatisfied dependent requirements. This is an implementation plan; this investigation changes no runtime outcome or UI.

### Forbidden band-aids

- **No blanket auto-retry.** PR 3 retries once, only on engine-fault evidence, keyed on the execution id. An unbounded loop turns a genuine blocker into a worker-slot leak.
- **No hiding blocked cards.** The board's Blocked section is correct; what is missing is that the parked row never changes and nobody is told.
- **No deleting dependency edges to "unblock".** PR 5 stops bad edges from being created and PR 6 makes existing ones visible with the removal as a named human action, never an automatic one.
- **No relabelling.** Rewriting `worker_failed` to `dependency` so the sweep picks it up would make the dependency sweep mint executions for rows that failed for a reason.
- **No special-casing by summary text.** Matching "attribution" in a free-text summary is brittle; PR 3 keys on the run's recorded command outcomes.
