# Investigation: a hub-and-spoke distributed engine for Boss

- **Date:** 2026-10-21
- **Kind:** investigation (writeup only; no code changes)
- **Scope:** Parts 1 to 3 of the brief: baseline with citations, a hub-and-spoke design worked through concretely, cheaper alternatives, and a phased recommendation
- **Related:** [`designs/distributed-agent-execution-register-and-dispatch-to-remote-ssh-hosts.md`](../designs/distributed-agent-execution-register-and-dispatch-to-remote-ssh-hosts.md) (the shipped ssh mode), [`designs/fleet-scaling-dynamic-panes-and-team-semantics.md`](../designs/fleet-scaling-dynamic-panes-and-team-semantics.md) (the 22-worker saturation experiment), [`designs/host-suspension-engine-side-sleep-awareness-and-clocks-that-do-not-count-suspended-time.md`](../designs/host-suspension-engine-side-sleep-awareness-and-clocks-that-do-not-count-suspended-time.md), [`designs/make-tmux-the-only-pane-hosting-mode.md`](../designs/make-tmux-the-only-pane-hosting-mode.md), [`worker-liveness-contract.md`](../worker-liveness-contract.md), [`work-tree-scale-measurement.md`](../work-tree-scale-measurement.md)
- **Citations:** every `file:line` below was read at the `main` this workspace was positioned on (`721f4d34`, "Include attention lists in work-tree snapshots and deltas (#3220)"). Paths are relative to `tools/boss/` unless they start with another top-level directory.

Boss's engine today runs every worker on the laptop, and its one remote mode drives a detached process on another host through per-operation `ssh` invocations over a ControlMaster, with no control channel and no remote-side supervisor. This document maps that baseline, designs a hub-and-spoke replacement in which a small `boss-spoke` binary on each host owns local execution while the hub stays the single decision point, and recommends a phased path that lands capacity on other hosts first and builds offline autonomy on top of the same journal and protocol.

## TL;DR

**Recommendation: build the spoke, as a separate small binary speaking length-prefixed protobuf frames over an ssh-carried stream, and land it in the order "spoke runs tmux workers; hub stays on the laptop" first.** That first increment alone removes the laptop CPU ceiling (the binding constraint today), replaces per-operation `ssh` with one session per host, and replaces stderr text-scraping with typed messages. The spoke's crash-recovery journal and durable execution records are the same mechanism that later lets the hub move to an always-on host (the offline-autonomy end state) and lets a spoke finish assigned work while the hub is unreachable. A "better ssh mode" (persistent stream plus a structured helper) is roughly two thirds of a spoke anyway, meets the scalability goal, and cannot meet offline autonomy; it is not worth building as a separate stop.

The hub bottleneck is not per-worker supervision (small, bounded) but the per-product board assembly, roughly 1.3 s of product-wide SQLite work per invalidation, and the single-writer state DB. Spokes do not change that, so the estimate below is that spokes can carry on the order of 50 to 100 concurrent workers before the hub needs its own work (delta-only invalidation at the DB layer, batching hook-event writes).

## Part 1: baseline at current `main`

### 1.1 Remote execution today, end to end

**Host registration and the enable flag.** Hosts live in a `hosts` table with `id`, `ssh_target`, `pool_size`, `enabled`, `last_seen_at`, `last_error_text`, `created_at` and `consecutive_failures` (`engine/core/src/work/schema_baseline.rs:404-412`). Capability tags are a separate `host_capabilities` table keyed on `(host_id, capability)` with a `source` of `auto` or `user` (`schema_baseline.rs:397`). The `local` row is seeded on every engine start (`engine/core/src/host_registry.rs:75-76`). The flag is written by `set_host_enabled` (`host_registry.rs:339`), reached from the `SetHostEnabled` RPC (`engine/core/src/app/hosts.rs:154`) and from `bossctl hosts enable|disable`, which writes `state.db` directly rather than going through the engine (`bossctl/src/hosts.rs:377`). A circuit breaker auto-disables a host after three consecutive cube-over-ssh failures (`host_registry.rs:50`, `host_registry.rs:408`, fed from `engine/core/src/host_adapter.rs:758`), and a provisioning failure disables it too (`app/hosts.rs:322`). Dispatch checks the flag in `select_host` (`engine/core/src/host_scheduling.rs:104`) and up front for an explicitly requested host (`engine/core/src/coordinator/execution.rs:89`).

**Provisioning and the wrapper.** `provision_remote_host` opens the ControlMaster, pushes the wrapper, checks `cube --help`, then discovers capabilities (`engine/core/src/host_provisioning.rs:56`, `:64`, `:71`, `:84`, `:100`). The only artefact pushed is a POSIX shell script, `boss-remote-run`, placed at `~/.boss-remote/bin/` (`engine/core/src/remote_wrapper.rs:67`) and embedded in the engine with `include_str!` (`remote_wrapper.rs:30`). Its version stamp is the engine's own binary fingerprint (`remote_wrapper.rs:47`); the engine runs `<wrapper> --version` and re-pushes on any mismatch, lazily before every remote spawn (`engine/core/src/wrapper_distribution.rs:251`, `host_adapter.rs:1218`). `cube`, `boss-event`, `gh` and the driver binaries are not pushed; they must already be on the remote's non-interactive `PATH` (`host_adapter.rs:58-61`), and the wrapper preflights each with `command -v` and a sentinel exit code (`engine/core/remote/boss-remote-run.sh:86-118`). The capability probe runs `uname -s`, `uname -m`, `gh auth status` and `command -v <driver>` (`engine/core/src/host_capability_probe.rs:147`, `:155`, `:167`, `:242`) and runs only at registration and on a manual `bossctl hosts probe` (`bossctl/src/hosts.rs:67`); there is no periodic remote probe.

**Scheduling.** `select_host` filters disabled hosts, full hosts, pinned mismatches and missing capabilities, then ranks by branch affinity, free slots and id (`host_scheduling.rs:98`, `:157-173`). Free slots are `pool_size - active_runs` where `active_runs` counts `work_runs` rows with `status = 'active'` per host (`host_scheduling.rs:43`, `host_registry.rs:592`); the local host is forced to zero active runs so it is never slot-gated (`coordinator/execution.rs:322-326`), and the branch-affinity input is hard-wired `false` (`execution.rs:335`). The chosen host is persisted on `work_runs.host_id` (`schema_baseline.rs:889`) together with `remote_pid` (`schema_baseline.rs:891`), and `work_executions` carries `pinned_host_id` and `host_id` (`schema_baseline.rs:865`). Only `local` is tmux-hosted (`execution.rs:1867`); the adapter provider returns `LocalHostAdapter` for `local` and a cached per-host `SshHostAdapter` otherwise (`host_adapter.rs:1979-2006`).

**Spawn.** `SshHostAdapter::spawn_worker` composes the prompt through the same `compose_worker_spawn` the local path uses (`host_adapter.rs:1243`), probes the remote for `MODULE.bazel` and for `ARG_MAX` (`host_adapter.rs:843`, `:909`), ships the prompt file, its `.gitignore` and the rendered hook settings JSON by `scp` (`host_adapter.rs:1428`, `:1393`), then calls `perform_remote_launch` (`host_adapter.rs:1476`). The launch removes any stale socket, adds a reverse forward with `ssh -O forward -R /tmp/boss-events-<run>.sock:<engine events.sock>` on the existing master, and runs `env BOSS_RUN_ID=… BOSS_EVENTS_SOCKET=… ~/.boss-remote/bin/boss-remote-run` (`engine/core/src/ssh_spawn.rs:319`, `:323`, `:339`, `:135`, `:190-212`). Drivers with no hook wiring are refused on the remote path because the run would produce no events at all (`host_adapter.rs:1382`).

**The wrapper and its handshake.** The wrapper validates seven required env vars (`boss-remote-run.sh:68-75`), then launches the driver detached: `nohup sh -c` runs a supervisor shell that itself runs `nohup sh -c "exec $BOSS_DRIVER_COMMAND" &`, writes the direct child's pid to `<workspace>/.boss/worker.pid`, waits for it and appends `worker exited with status=<n>` to `<workspace>/.boss/worker.log` (`boss-remote-run.sh:205-213`). The wrapper then polls for the pid file up to 300 times at 0.1 s (`boss-remote-run.sh:222`), exits 83 if it never appears (`:226-230`), and otherwise prints one stderr line, `boss-remote-run: starting run_id=… version=… pid=… driver=…`, and exits 0 (`:245-246`). The engine parses only `pid=` out of that stderr (`ssh_spawn.rs:216`), maps the sentinel exit codes to failure reasons (`ssh_spawn.rs:109`), records `remote_pid` (`host_adapter.rs:1492`), then runs a second ssh command, `sleep 2; kill -0 <pid>` with echoed sentinels, to catch immediate death (`ssh_spawn.rs:83`, `:571`). A no-sentinel probe is treated as inconclusive and the launch is kept (`ssh_spawn.rs:580-588`). After that the engine waits up to 45 s for a hook or a transcript path before declaring the turn started (`engine/core/src/runner/spawn_confirmation.rs:83`); failure runs `reap_failed_remote_turn`, which is a plain `kill <pid>` plus `-O cancel` of the forward (`host_adapter.rs:1536`, `ssh_spawn.rs:450`, `:408`).

**No tmux on the remote.** The remote path never creates, names, adopts or inspects a tmux session; liveness over ssh is `kill -0` with sentinels (`ssh_spawn.rs:571`). The tmux-only design records this split explicitly: remote workers "remain detached on their separate lifecycle" (`docs/designs/make-tmux-the-only-pane-hosting-mode.md:3`).

**Transcript and live status readback.** There is no remote JSONL discovery and no local copy. The transcript path is whatever the worker's own hook reported through the forwarded socket, a path on the remote filesystem (`host_adapter.rs:1596`), and each transcript-tail RPC runs `tail -c <max_bytes> -- '<path>'` over the master (`engine/core/src/remote_transcript.rs:34`, `host_adapter.rs:1599`). `worker.log` is read the same way, 4 KiB at a time (`host_adapter.rs:1629`), and structured output is pulled with `scp` via a descriptor file under `~/.boss-remote/runs/` (`host_adapter.rs:1651`, `:1733`).

**Cube on the remote.** Lease, heartbeat and release are the same cube commands run through `ssh <target> cube --json …` (`engine/core/src/cube_commands.rs:249-262`, `:335`, `:310`, `:348`) behind one `CubeJsonTransport` trait (`cube_commands.rs:97`). The heartbeat loop runs every 300 s against a 24 h TTL and auto-reaps after three consecutive failures (`engine/core/src/cube_lease_heartbeat.rs:366`, `:378`, `:305`), routed to the owning host's cube (`cube_lease_heartbeat.rs:292`). Remote slots carry `shell_pid == 0`, so they always take the DB-fallback heartbeat path and never the local death-evidence gate (`cube_lease_heartbeat.rs:716`, `:570`).

**Probe, interrupt and stop.** Not forwarded. The trait doc still describes the control channel as a later phase (`host_adapter.rs:144-145`), the transport lists it as a non-goal (`engine/ssh-transport/src/lib.rs:22-23`), and the only remote kill is the failed-launch reaper above.

**Disconnect, engine restart, host reboot.**

- _ssh disconnect mid-run:_ the transport has no reconnect; the first failure surfaces as `host_unreachable` (`ssh-transport/src/lib.rs:18-21`). The detached worker keeps running, but the reverse forward dies with the master, so every later hook event is lost. Nothing re-adds a per-run forward in-process; the only re-forward is the startup reattach below. Failed cube calls also count against the host breaker (`host_adapter.rs:780`).
- _engine restart:_ `reattach_remote_runs` lists live remote runs, rebuilds each adapter (reopening the master), and re-issues `-O forward` (`engine/core/src/remote_reattach.rs:120-121`, `ssh_spawn.rs:609`); failures are counted and logged as "run may strand" (`remote_reattach.rs:152`). Stale control sockets are swept at startup (`ssh-transport/src/lib.rs:581`).
- _host reboot:_ no dedicated detection. `remote_lease_reconcile` runs every 60 s (`engine/core/src/remote_lease_reconcile.rs:75`) and probes `kill -0` for live executions that have a `remote_pid` (`:183`, `:213`); an `Err` from the probe is inconclusive and skipped (`:251`), so a host that is down is never reaped, and once it is back the stale pid reads as dead, the run is orphaned, the lease force-released and a `remote_worker_died` attention raised (`:328`, `:373`, `:71`). A recycled pid after reboot would read as alive; nothing guards that.

**Honest status.** The remote path's own comments say "Remote SSH execution has never worked end to end" and every worker-proposal seam flag is forced off on it (`host_adapter.rs:1250-1286`). Review-guide submissions require a local worker (`coordinator/execution.rs:400-404`). The `cfg` injected into `SshHostAdapter` is "not yet read" (`host_adapter.rs:673`).

### 1.3 What is laptop-bound, and what has to move for work to continue with the lid closed

Everything under the state root `~/Library/Application Support/Boss` (`log-files/src/paths.rs:121`):

- `state.db`, SQLite, one engine at a time, enforced by a flock on `engine.pid` taken before the DB opens (`paths.rs:20`, `:29`; `engine/core/src/app/server.rs:620`), hourly `VACUUM INTO` backups kept locally (`engine/core/src/database_backup.rs:101`, `:24`), settings in `settings.toml` (`engine/core/src/settings.rs:3`).
- `engine.sock` (app and CLI), `events.sock` (hook events), `tmux.sock` (private tmux server), `engine-control.token` (`paths.rs:26`, `:23`, `:35`, `:38`).
- `engine.log` (100 MiB × 20), `engine-trace.jsonl`, `engine-audit.log`, `dispatch-events/current.jsonl`, `diagnostics/spawn-*.jsonl` (`engine/core/src/main.rs:23`; `paths.rs:14`, `:17`, `:41-44`, `:47`).
- Per-task cost exists only in Claude's own `~/.claude/projects/...` transcripts on the worker host, not in `state.db` (`docs/forensic-surfaces.md:97-109`).
- The coordinator session is a local tmux session `boss-coordinator` (`engine/core/src/coordinator_tmux.rs:30`).
- The engine is started by the app with `nohup`, not launchd (`app-macos/README.md:184`); the engine ships inside the app bundle and has no separate update channel (`docs/designs/automatic-boss-updates.md:45`).

For work to continue while the laptop sleeps, the decision loop (dispatch, completion, merge polling, CI watch, sweeps) and the DB they write must run somewhere that stays up, or the executing side must be able to run to a safe boundary without them. Section 2.3 works through both. What never has to move is the app: it is already only a client of `engine.sock` and a viewer of tmux panes.

### 1.4 Engine IPC today

All three sockets speak newline-delimited JSON via serde. The frontend socket carries `FrontendRequestEnvelope { request_id, payload }` and `FrontendEventEnvelope` lines (`protocol/src/wire.rs:113`; `client/src/lib.rs:464`, `:508`), with internally tagged enums (`protocol/src/wire/events.rs:9-11`). The events socket takes one JSON hook payload per connection, read to EOF, with a text rejection prefix as the only reply (`events_socket.rs:37`, `:406`). Peer identity on both is `LOCAL_PEERPID` (`events_socket.rs:3`; `server.rs:2703`). Nothing in `tools/boss` uses protobuf today; the frontend wire has a `#[serde(default)]` discipline for additive fields (`wire/events.rs:58-69`) but no explicit version negotiation.

Concurrency is capped today at 16 worker slots, 8 automation, 16 review, with interactive dispatch defaulting to 8 after the 22-worker saturation experiment (load average ~152) (`engine/core/src/coordinator.rs:169-250`, `:236-240`; `docs/designs/fleet-scaling-dynamic-panes-and-team-semantics.md:7-13`).

**Reading of the table.** Per-worker supervision on the hub is cheap and bounded: a few subprocess spawns and `kill(0)` calls per minute, one LLM call per minute at most, and a DB read per hook. The two super-linear terms are `stale_worker_sweep`'s per-worker `list-sessions` (O(N²) tmux output per minute) and the board assembly, which is driven by lifecycle events and so grows with the number of workers producing them. The laptop's own CPU is the binding constraint long before either, which is why moving execution off the laptop is the first increment regardless of what else is built.

## Part 2: the hub-and-spoke design

### 2.1 Split of responsibilities

The rule: **a spoke owns everything whose truth is a fact about its own host; the hub owns everything whose truth is a fact about the work.** Concretely:

| Spoke owns (moves out of `engine/core`)                                                                                                                                             | Hub keeps                                                                                                         |
| ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------- |
| tmux server, session create/adopt/kill, `BOSS_SPAWN_TOKEN` identity, `#{pane_dead}` observation (`tmux/` crate, `tmux_adoption.rs`, `tmux_session_options.rs`, `tmux_preflight.rs`) | dispatch, `select_host`, pool and slot accounting (`coordinator/`, `host_scheduling.rs`)                          |
| local hook-event ingestion (`events_socket.rs` listener; `boss-event` keeps writing to a Unix socket, now the spoke's)                                                              | `completion/`, `run_reconcile.rs`, `worker_readoption.rs`, all status transitions in `work/`                      |
| transcript tail and discovery (`transcript-tail`, `agent_jsonl_discovery.rs`, `agent_jsonl_progress.rs`, `remote_transcript.rs`)                                                    | live-status summarisation (`live_status.rs`, `live_status_loop.rs`) over transcript deltas the spoke sends        |
| driver provisioning on disk and spawn (`driver/` crate's `provision_workspace` and `SpawnPlan`, `worker_setup.rs` rendering, `spawn_flow.rs` pane half)                             | prompt composition (`runner::compose_worker_spawn`, `prompt_fragments.rs`)                                        |
| local cube lease/release/heartbeat execution (`cube_commands.rs` local transport)                                                                                                   | lease policy and the 3-strikes reap decision (`cube_lease_heartbeat.rs` policy half, `remote_lease_reconcile.rs`) |
| process and pane liveness facts (`kill(0)`, `dead_pane_sweep.rs`, `dead_pid_sweep.rs`, `husk_pane_sweep.rs` observation halves)                                                     | liveness verdicts and attention items (`stale_worker_sweep.rs` classification, `attention_lifecycle.rs`)          |
| capacity report (free slots, load, disk)                                                                                                                                            | host registry, enable flag, breaker (`host_registry.rs`, `host_reconcile.rs`)                                     |
| crash-recovery journal of its own panes (new)                                                                                                                                       | execution bookmarks and recovery (`recovery/`, `execution_bookmark_recovery.rs`)                                  |
| the per-host `boss-event`, `cube`, driver preflight (`boss-remote-run.sh:86-118` becomes spoke startup checks)                                                                      | merge poller, CI watch, GitHub, planner, automations, app socket, audit log                                       |

**Same binary or a separate one?** A separate, smaller binary, `boss-spoke`, built from a new crate `tools/boss/engine/spoke`. The reasons are the repo's own: bazel incrementality is per crate and the crates-over-modules convention already pulled `claude_client` out for the same reason; the spoke must never link `work/` (the DB) or `coordinator/`, and a separate crate makes that a visibility rule rather than a discipline; and the spoke should be deployable and restartable without the app bundle, which the engine is not (`automatic-boss-updates.md:45`). The split forces the one-way edges the convention asks for: `spoke → tmux, driver, transcript-tail, cube_commands (transport), event-shim contract, protocol-spoke`; `engine/core → protocol-spoke`. The local host runs a spoke too, as a child of the engine, so there is one execution path rather than a "local" special case (the twelve `host_id == "local"` sites in 1.1 collapse to "the spoke whose host id is local").

### 2.2 Protocol

**Message set** (hub → spoke unless marked):

| Message                           | Direction   | Payload                                                                                                                       | Reply                                                                           |
| --------------------------------- | ----------- | ----------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------- |
| `Hello`                           | both        | binary fingerprint, protocol version range, host id, capabilities (os, arch, drivers, cube version, tmux version, free slots) | `HelloAck` with the negotiated version                                          |
| `Spawn`                           | hub → spoke | execution id, run id, driver, rendered prompt and settings bytes, env allowlist, workspace path or lease request, spawn token | `Spawned { pane id, pane pid, session name }` or `SpawnFailed { typed reason }` |
| `Adopt`                           | hub → spoke | execution id, spawn token                                                                                                     | `Adopted { pane state }` or `Absent`                                            |
| `Lease` / `Release` / `Heartbeat` | hub → spoke | cube args                                                                                                                     | cube JSON result as a typed message                                             |
| `Deliver`                         | hub → spoke | pane id, bytes, delivery kind (probe, interrupt, nudge, answer)                                                               | `Delivered` or `PaneGone`                                                       |
| `Stop`                            | hub → spoke | pane id, spawn token, grace                                                                                                   | `Stopped { exit status }`                                                       |
| `Event`                           | spoke → hub | journal sequence, run id, normalised `WorkerEvent` (today's `boss_protocol::WorkerEvent` shape), observed-at                  | acked by sequence in `Ack`                                                      |
| `PaneState`                       | spoke → hub | pane id, `pane_dead`, exit status, pid, last activity                                                                         | acked                                                                           |
| `TranscriptDelta`                 | spoke → hub | run id, byte offset, bytes (bounded)                                                                                          | acked                                                                           |
| `Capacity`                        | spoke → hub | free slots, load average, free disk, awake-time ledger since last report                                                      | none                                                                            |
| `Ack`                             | both        | highest contiguous sequence seen                                                                                              | none                                                                            |

Every spoke → hub message carries a per-spoke monotonic sequence written to the spoke's journal before it is sent; the hub acks the highest contiguous sequence, and the spoke resends from the last ack on reconnect. That one rule is what makes section 2.3 and 2.5 work.

**Why protobuf, and the evolution rules.** The hub and spokes will routinely be different builds: the laptop updates the app bundle on its own schedule (`automatic-boss-updates.md`), and a spoke on an always-on host is updated by the hub (2.6) but may be mid-rollout. Protobuf's rules are designed for exactly that and the serde-JSON wire has none of them. The rules to adopt, written into `protocol-spoke/README.md` and enforced by a `buf breaking`-style check in CI:

- Field numbers are permanent; never reuse or renumber. Removed fields are marked `reserved`.
- Every new field is optional with a documented default; a reader must behave correctly when it is absent.
- Enums carry an `UNSPECIFIED = 0` member and readers treat unknown values as "a newer peer sent something I do not understand" and fall back to the most conservative behaviour, never panic.
- Messages are extended, never semantically repurposed; a changed meaning is a new field or a new message.
- `Hello` negotiates a `[min, max]` protocol version; the hub refuses a spoke below its minimum and tells it to upgrade (2.6), and keeps talking to a spoke above its maximum at the hub's own version because unknown fields are preserved and ignored.

This is the compatibility property the serde wire does not have: `#[serde(default)]` handles additive fields in one direction, but a renamed variant or an unknown enum tag is a decode error, and the events-socket path already had to guard "unrecognized hook shape" with a text prefix (`events_socket.rs:25-37`).

**Transport.** Two options were weighed on concrete grounds.

- _gRPC (tonic) over a TCP port with mTLS._ Pros: bidirectional streaming, deadlines, built-in versioned services, the natural shape once the hub lives on a server. Cons: a listening port on every host, a certificate story Boss does not have today, a new dependency (`tonic`, `prost`, `hyper`) in the Bazel Rust setup, and it does not reuse the ssh trust the current design relies on (`distributed-agent-execution…md:36-37`, "the user configures SSH out of band").
- _Length-prefixed protobuf frames over an ssh-carried stream._ The hub runs `ssh <host> boss-spoke serve` once per host and speaks over its stdin/stdout, exactly like a tmux-less version of today's ControlMaster, but as one long-lived channel rather than one `ssh` process per operation. Pros: no new listening surface, no new credentials, no port, ssh already gives the authenticated, encrypted, multiplexed stream; reconnect is "re-run the command". Cons: the hub is the only side that can initiate, and the stream dies with the ssh session (which is fine, because the spoke and its tmux workers do not).

**Chosen: protobuf frames over an ssh-carried stream now, with the `.proto` service written so a tonic server can be dropped in front of the same messages later.** The current code already demonstrates that ssh-as-transport works for everything but per-operation cost and text parsing; the frame layer removes both without changing the trust model. When the hub moves to an always-on host (2.3 option A) and spokes need to dial in, the same messages go over gRPC with mTLS, and `Hello` is unchanged.

**How it fits existing IPC.** The app and CLI sockets stay JSON over `engine.sock`; nothing in the app changes. `boss-event` keeps writing JSON to a Unix socket, now the spoke's; the spoke normalises it into `WorkerEvent` and forwards it as an `Event` frame. The driver-neutral `WorkerEvent` enum in `protocol/src/worker_event.rs` is the first message to get a protobuf twin.

**Auth and identity.** The spoke's identity is the host id in `Hello` plus the ssh identity that reached it. The hub issues each spoke a random spoke token at provisioning, stored in `hosts` (new column) and in `~/.boss-spoke/token` on the host; `Hello` must present it, so a spoke reachable by ssh but never provisioned cannot join. Revocation is deleting the row (2.7).

**Mixed versions during a rolling upgrade.** The hub is upgraded first (it ships with the app). On its next `Hello` each spoke reports its fingerprint; if below the hub's minimum the hub pushes the new binary (2.6) and asks the spoke to re-exec, and the spoke's running workers survive because they live in tmux sessions owned by the host's tmux server, not by the spoke process, exactly as local workers survive an engine restart today (`app/shutdown.rs:9`; `server.rs:2657`). A spoke newer than the hub (the laptop skipped a release) keeps serving at the hub's negotiated version.

### 2.3 Offline autonomy

Two end states were worked through; the recommendation is A, built in an order where B's prerequisites come for free.

**Option A: the hub moves to an always-on host; the laptop becomes a client.** `state.db`, the sweeps, the merge poller and the coordinator session run on a machine that does not sleep; the laptop's app connects to `engine.sock` over an ssh-forwarded socket (the app already finds its socket via `BOSS_SOCKET_PATH`, `client/src/lib.rs:99`) and the laptop runs a spoke like any other host. Consistency is trivial: there is one authority and it is up. What has to change: the app's engine autostart and the pid-file flock assumption (one hub per state root, now on the server), the audit log's `launched_by` semantics, and the coordinator session being on the hub host (the operator attaches to it over ssh). The attention items, questions and kanban all keep working because they are DB rows served over `engine.sock`.

**Option B: spokes run assigned work to completion while the hub is unreachable, and reconcile on reconnect.** The hub stays on the laptop. When the stream drops, a spoke continues: its workers keep running in tmux, hook events and pane states are journaled with sequence numbers, cube heartbeats continue locally (the spoke owns the lease on its host), and a worker's turn boundary, PR URL capture and `propose done` are journaled as events. The spoke never decides anything the hub decides today: it does not start new executions, does not transition status, does not merge, does not redispatch.

_Consistency rules for B._ While the hub is unreachable, the spoke is authoritative for **observations** about its panes (alive, dead with exit status, events in order) and nothing else; the hub remains authoritative for **status**, and status simply does not advance until reconnect. On reconnect the spoke resends from the last acked sequence; the hub replays the journal through the same completion path it would have run live (every consumer already keys off `IncomingHookEvent` and `turn_boundary`, `events_socket.rs:112-156`), stamping `observed_at` from the spoke's timestamps rather than arrival time. Nothing is guessed: a pane the spoke reports dead with an exit status is terminal evidence (the liveness contract's existing rule, `worker-liveness-contract.md:133`), a pane it reports alive is re-adopted, and a run the journal shows reached `propose done` finalises as if the hub had been present. Horizons (stale, spawn-ack, backstop) are measured against the spoke's awake-time ledger carried in `Capacity`, which is the same clock-pair idea the host-suspension design already proposes for the engine host, applied per spoke rather than declared out of scope (`host-suspension…md:41`).

_What B cannot do._ It cannot start the next task when one finishes, cannot run review or merge, and cannot answer a worker's question. "The laptop lid can close and work keeps running" is met for work already dispatched, not for the pipeline. That is why A is the end state and B is the resilience layer under it.

**Why the order is B's journal first, then A.** The sequence-numbered journal and the replay path are required anyway for hub restart (2.5) and for the local spoke; they are not an offline-autonomy feature. Once they exist, A is mostly deployment: a hub binary on a server, a forwarded app socket, and a documented way to attach to the coordinator session. Building A without B would leave every hub restart and every network blip as a lost-event risk, which is today's remote-mode behaviour (1.1, disconnect).

### 2.4 Scalability, incrementally

**How far spokes get before the hub is the bottleneck.** Using 1.5: per worker the hub does roughly 2 hook-frame decodes plus one DB write per tool call, one LLM call per minute, and a handful of `kill(0)`-equivalents per minute delivered as `PaneState` frames instead of subprocesses. At 100 workers each making a tool call every 10 s that is about 20 frames/s and 10 small writes/s, well inside SQLite WAL and a tokio loop. The terms that do not scale are:

1. Board assembly: ~1.3 s product-wide DB work per invalidation (`work-tree-scale-measurement.md:110`). Lifecycle events per worker are perhaps one every few minutes, so 100 workers produce an invalidation every second or two, which would saturate one core and the single DB writer. This is the first hub-side limit, somewhere between 30 and 60 concurrent workers unless the invalidation path becomes genuinely delta-scoped at the DB layer.
2. The live-status summariser's utility-model budget (one HTTP call per working worker per minute).
3. The serial dispatch drain the fleet-scaling note already flagged (`fleet-scaling…md:10`).

None of these is touched by spokes, and none needs to be solved before the first increment, because the laptop's 8 to 16 slot ceiling is far below them.

**Increments, in order, each shippable alone:**

1. **Spoke runs tmux workers on another host; hub stays on the laptop.** Unlocks: capacity beyond the laptop's cores (the saturation experiment showed added local concurrency is negative-sum, `fleet-scaling…md:9-13`), typed liveness instead of stderr matching, one connection per host, probe/interrupt/stop on remote workers for the first time, remote workers that survive hub restart by adoption rather than re-forwarding. Needs: `protocol-spoke`, `boss-spoke`, the hub-side `SpokeHostAdapter` replacing `SshHostAdapter`, and the journal with sequence acks (cheap to add at the same time as the stream).
2. **Local spoke.** The engine spawns `boss-spoke` for `local` and stops calling tmux itself. Unlocks: one code path, deletion of the `host_id == "local"` branches and of `stale_worker_sweep`'s per-worker `list-sessions`, the panic hook's emergency-kill filter becoming dead code (2.5).
3. **Capacity-driven scheduling.** `Capacity` frames replace `pool_size - active_runs`; the fleet-scaling note's "capacity as budgets, not seats" lands here.
4. **Hub on an always-on host (option A).** Unlocks offline autonomy in full.

Increment 1 is the shortest path to real capacity and is independent of everything offline autonomy needs beyond the journal.

### 2.6 Upgrade and deployment

- The spoke binary is built by the same release pipeline as the app and published as a per-platform asset next to `Boss-1.0.N.zip` (`automatic-boss-updates.md:10` describes the release shape); the hub also carries the spoke binaries for its own version inside the app bundle so a fresh host can be provisioned with no network fetch.
- Provisioning (`bossctl hosts add`) does what `provision_remote_host` does today (`host_provisioning.rs:56`) but pushes `boss-spoke` plus a launchd (macOS) or systemd user unit, installs the spoke token, and starts the unit. The engine already has the push-to-`.new`-then-`mv` primitive (`wrapper_distribution.rs:10-13`) and the fingerprint handshake (`remote_wrapper.rs:47`); both are reused for a binary instead of a script.
- On every `Hello` the hub compares fingerprints and, below minimum, pushes the new binary and sends `Upgrade`; the spoke execs the new binary in place and the unit keeps it alive. Workers are unaffected (tmux). Nobody installs anything by hand after `hosts add`, and the hub's own update (the app's existing updater) triggers the fleet's on its next connection.
- The engine's current inability to update independently of the app (`automatic-boss-updates.md:45`) is unchanged for the laptop hub; for option A the hub binary on the server is updated by the same push mechanism from the laptop's app, or by a tiny `bossctl hub upgrade`, because the server has no app.

### 2.7 Security

- **Credentials on spokes.** The spoke holds none of Boss's secrets. It inherits the host user's `gh`, `jj`, `claude` and `codex` credentials exactly as workers do today (`spawn_flow.rs:48`; `boss-remote-run.sh:102`), and the hub's GitHub OAuth token stays on the hub (`KeychainTokenStore`). A worker on a spoke can therefore only do what that host's user can do.
- **Listening surface.** None in increment 1: the spoke serves on stdin/stdout of an ssh session the hub opened, plus a Unix socket for `boss-event` with mode 0600 as today (`events_socket.rs` creates it 0600). Option A adds one TLS port on the hub host for spokes that dial in, with client certificates issued at provisioning; the laptop app still reaches the hub over an ssh-forwarded Unix socket.
- **Authorisation and revocation.** A spoke is authorised by its `hosts` row and its spoke token; `bossctl hosts remove` deletes the row, which makes the next `Hello` fail, and the hub sends `Stop` for the host's executions first when it can reach it. The hub also refuses `Spawn` for any host whose `enabled` is false, as today (`host_scheduling.rs:104`).
- **Blast radius of a compromised spoke.** It can lie about its own panes and events; it cannot write `state.db`, cannot dispatch, cannot touch another host, and cannot reach the hub's socket. That is the same trust boundary workers have today, moved one process out.

### 2.8 Observability

- **Logs.** The spoke writes `spoke.log` and `spoke-trace.jsonl` under `~/.boss-spoke/` on its host with the same rotation crate (`log-files`), and the hub exposes `bossctl hosts logs <host> --tail` by asking the spoke for a bounded tail over the stream, replacing today's `tail -c` over ssh (`remote_transcript.rs:34`).
- **Audit and dispatch events.** Unchanged in location: they are hub decisions and stay in `engine-audit.log` and `dispatch-events/` on the hub. Each dispatch event gains `host_id` and the spoke's journal sequence so an incident can be joined across the two logs by `(host_id, sequence)`.
- **Transcripts and cost.** The spoke streams `TranscriptDelta` frames; the hub appends them to a per-run file under the state root, which for the first time gives Boss a transcript copy that does not evaporate with Claude's 30-day cleanup (`forensic-surfaces.md:115-126`). Per-task cost becomes computable on the hub.
- **Existing CLI surfaces.** `bossctl agents list` reads `LiveWorkerState`, which is fed from `Event` and `PaneState` frames, so it keeps working unchanged. `transcript` reads the hub's copy. `probe`/`interrupt`/`stop` become `Deliver`/`Stop` frames, which makes them work on remote workers for the first time (1.1). The app's pane viewer attaches to local tmux today; for a remote pane the viewer runs `ssh -t <host> tmux -S … attach` in the same Ghostty surface, or the spoke streams `capture-pane` snapshots as a read-only view. The latter is the increment-1 answer; the former is a follow-up.

### 2.9 Damage containment

- **Process argv.** The brief is expanded into the driver's argv on both paths today (`claude.rs:859-862`; `boss-remote-run.sh:197`, `:206`), which is why `pkill -f 'cube.*pr update'` matched nine workers. The spoke launches the driver with the prompt on stdin or through the driver's prompt-file flag where one exists, and never as a positional argument, so no worker's command line contains another worker's text. This is a driver `SpawnPlan` change that could ship before the spoke and should.
- **Signals cannot cross hosts.** A worker on spoke A can only signal processes on A. Containment by host is automatic; the remaining question is containment _within_ a host, which is the per-user sandbox the hermetic test wrapper already applies to tests and which the worker sandbox audit (`worker_sandbox_audit.rs`) only observes. A worker should run as a per-host dedicated user when the host is not the operator's laptop; the spoke's unit file can do that without engine changes.
- **Disk and load.** `Capacity` includes free disk and load average; the hub stops dispatching to a host below thresholds instead of discovering the problem as a `disk_full` scp failure (`ssh-transport/src/lib.rs:58-60`). This investigation was itself slowed by the engine host's disk reaching 100%, which is the failure the hub should see coming.

## Part 3: cheaper alternatives and the recommendation

### 3.1 How far a better ssh mode gets without spokes

"Better ssh" means: one persistent `ssh` session per host instead of one process per operation, and a small helper on the host that answers structured liveness (pid, pane state, exit status as JSON) instead of `kill -0` with echoed sentinels and stderr `pid=` parsing.

| Goal                                      | Better ssh mode                         | Why                                                                                                                                                            |
| ----------------------------------------- | --------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Capacity beyond the laptop                | **Met**                                 | Workers already run elsewhere; the laptop's CPU stops being the limit                                                                                          |
| Probe/interrupt/stop on remote workers    | **Met** if the helper is tmux-based     | The helper would need to own a tmux server on the host, which is most of a spoke                                                                               |
| Typed liveness instead of text scraping   | **Met**                                 | That is what the helper is for                                                                                                                                 |
| Fewer handshake flakes                    | Partly                                  | One session removes per-operation connection setup, but the launch handshake is still a stdout line from a short-lived process unless the helper is long-lived |
| Survive hub restart without re-forwarding | Not met unless the helper is long-lived | Reverse forwards still die with the ssh session; events fired meanwhile are lost unless something on the host buffers and resends                              |
| Offline autonomy                          | **Not met**                             | Nothing on the host journals or resends; the hub is still the only thing that can observe a turn boundary, so a closed lid loses completion reports            |
| Automatic upgrade                         | Partly                                  | The existing fingerprint push extends to a helper binary                                                                                                       |

The honest cost comparison: a long-lived helper that owns tmux, buffers events and answers structured liveness over a persistent stream **is** a spoke with a JSON wire format and no journal sequence. The gap between it and increment 1 of 2.4 is the protobuf schema and the ack protocol, perhaps a fifth of the work. Building the helper first and the spoke second means building the host-side supervisor twice. A short-lived helper (invoked per operation) is cheaper but keeps every failure class in 1.1 except text scraping.

### 3.2 Recommendation and phased path

Build the spoke. Order the work so scalability lands first and offline autonomy builds on it:

1. **Prompt off argv.** `SpawnPlan` passes the prompt on stdin or via the driver's prompt-file flag; the wrapper's `"$(cat …)"` goes away. One PR, driver crate plus `boss-remote-run.sh`, independent of everything else and closes incident 2 immediately.
2. **`protocol-spoke` crate.** The `.proto` files, prost build in Bazel, the evolution rules in a README, a breaking-change check in CI, and a Rust twin of `WorkerEvent`. No behaviour change. Forces the dependency decision (prost/prost-build in `rules_rust`) early and alone.
3. **`boss-spoke` binary: serve mode over stdio.** Tmux session create/adopt/kill, `boss-event` socket ingestion, journal with sequences, `PaneState` and `Capacity` reporting, cube local transport, driver provisioning on disk. Tested against a fake stream. Depends on 2.
4. **Hub `SpokeHostAdapter` and stream manager.** Replaces `SshHostAdapter`; one `ssh <host> boss-spoke serve` per host with reconnect and replay-from-ack; `Deliver`/`Stop` wired into the existing probe/interrupt/stop paths; `remote_reattach`, `remote_transcript`, `remote_lease_reconcile` and `ssh_spawn` retired. Depends on 3. **This is increment 1: real capacity on other hosts.**
5. **Provisioning and upgrade.** `hosts add` pushes the binary and a unit file; `Hello` fingerprint comparison triggers push-and-reexec. Depends on 4; needed before a second host is worth registering.
6. **Local spoke.** The engine spawns `boss-spoke` for `local`; `tmux_adoption`, `stale_worker_sweep`'s tmux half, `dead_pane_sweep` and the panic hook's kill filter are deleted or reduced to consumers of `PaneState`. Depends on 4. Removes the `local` special cases.
7. **Capacity-driven scheduling and host `unreachable` state.** `Capacity` frames replace `pool_size - active_runs`; the unreachable horizon and the operator-driven host removal of 2.5. Depends on 4.
8. **Offline replay hardening.** Awake-time ledger per spoke in `Capacity`, horizons measured in spoke awake time, replay path tests for every journaled event kind including `propose done`. Depends on 4 and on the host-suspension crate if it has landed; otherwise it carries its own clock pair. This is option B complete.
9. **Hub on an always-on host.** Hub binary deployable without the app, app connects over a forwarded `engine.sock`, coordinator session reachable over ssh, pid-file and `launched_by` semantics adjusted. Depends on 5 through 8. This is option A and the full offline-autonomy goal.
10. **Hub-side scale work** (separate from the spoke stack, needed somewhere past ~50 workers): DB-layer delta invalidation for the board, batched hook-event writes, parallel dispatch drain.

Steps 2 and 3 can run in parallel with step 1; steps 6 and 7 can run in parallel after 4; nothing in 8 or 9 blocks capacity.

## Open questions and follow-ups

- **Prost in Bazel.** Whether `rules_rust`'s prost support builds cleanly with the repo's pinned toolchain was not verified here (the host's disk was full during this investigation, so no build was attempted). Step 2 exists to answer it in isolation.
- **Per-host worker user.** 2.9 proposes running workers as a dedicated user on non-laptop hosts. Cube's shared jj store and the driver's credential files are per user, so this needs a provisioning story for cube and `gh` under that user before it is more than a note.
- **Remote pane viewing in the app.** Increment 1 ships a read-only `capture-pane` stream; whether the operator wants a live attached terminal for remote panes decides whether the `ssh -t … tmux attach` viewer is worth the Ghostty plumbing.
- **Follow-up code changes for the user to file** (this document makes none): steps 1 through 10 above, with step 1 the only one that is a bug fix rather than architecture.
