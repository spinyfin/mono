# Fully isolated second Boss instance for end-to-end agent testing

- **Date:** 2026-10-09
- **Kind:** investigation (doc only, no code changes)
- **Question:** can a second Boss (app + engine) run completely isolated from the production instance on the operator's laptop, and later on the remote macOS hosts, so agents can test Boss end to end without touching real products, work items, workers, or the main engine?
- **Related docs:** [`designs/test-instance-isolation.md`](../designs/test-instance-isolation.md) (mono#365), [`app-macos/README.md`](../../app-macos/README.md) "Agent capture", [`designs/distributed-agent-execution-register-and-dispatch-to-remote-ssh-hosts.md`](../designs/distributed-agent-execution-register-and-dispatch-to-remote-ssh-hosts.md), [`mac-toolchain-xcode-pinning.md`](../mac-toolchain-xcode-pinning.md)
- **Related PRs:** mono#365, mono#424, mono#756, mono#2206, mono#2479

The engine already has a supported "test-fixture mode": any non-production `--socket-path` makes it derive every runtime path from that socket's directory and stem, refuse to start if anything still resolves onto production, and reap itself when its parent dies. That machinery is real and was exercised in this investigation. What is missing is a thin layer on top of it: three engine paths that still resolve to the production state root, a worker path guard that breaks when the fixture socket lives directly in a shared temp dir, no rail at all against a test worker pushing to a real repo, and no one-command harness. Each gap is small and separately shippable.

## TL;DR

**Laptop: yes, today, with care.** An engine started with `--socket-path <private-dir>/engine.sock` and `BOSS_WORKER_POOL_SIZE=0` is isolated from production for the DB, both sockets, pid file, control token, tmux server, trace/audit/text logs, dispatch events, attachments, settings and backups (verified by a trial run, §7). The app can attach to it quietly with `BOSS_SOCKET_PATH` + `BOSS_ENGINE_AUTOSTART=0`. Three engine directories (`recovery/`, `diagnostics/`, `executions/`) and the coordinator session directory still land in the production state root; the first three have env overrides, the last does not. Every engine start also sweeps the shared `$TMPDIR/boss-worker-settings` directory and rewrites production workers' hook paths if they differ from what the fixture resolved. Worker dispatch from the fixture needs the socket in a short, dedicated directory (Unix socket path limit; data-dir path guard) and a PATH on which the driver binaries resolve.

**"Without affecting our main products": by construction, not by enforcement.** A fresh fixture DB holds only the products you create in it, and a product's `repo_remote_url` selects the cube pool and therefore the GitHub remote workers push to. Nothing in the engine or the worker guards refuses a push to a real repo; the only rails are the product you create and the operator's `gh` identity. A repo allowlist in the engine is the smallest hard rail (§3, §6).

**Remote hosts: two different asks.** Running test _workers_ on `anaplian` and `skaffen` works today through the existing SSH host adapter (headless, no display, no tmux on the remote). Running a whole second _instance_ (engine + UI capture) there is possible for the engine but the UI capture needs a logged-in Aqua session on the host; both hosts are also live Buildkite agents, which is the main practical blocker (§5).

Newer protections that did not exist when mono#365 was written and matter here:

- `boss_log_files::default_state_root` refuses to resolve the production state root from a Bazel _test_ process and panics instead of inventing a temp dir (`paths.rs`, `panic_refusing_production_state_root`).
- `app/agent_launch_guard.rs`: an engine that would touch production paths **and** is agent-owned (Boss session env markers, or a binary living in a cube workspace or agent scratchpad) refuses to start. A fixture passes clause 1 trivially.
- `boss-path-guard.py` (worker PreToolUse hook): blocks any tool call whose path resolves inside `BOSS_DATA_DIR`, with a substring belt on Bash command text.
- The PreToolUse hook in worker sessions blocks `open -a Boss`, `/Applications/Boss.app`, and bare `bazel run //tools/boss/app-macos:Boss`.
- The `boss`/`cube` launchers in worker panes are engine-owned binaries under `$TMPDIR/boss-worker-settings/bin/<workspace>/`; a bare PATH `cube` is refused by a hook.

### 2.1 The one structural wrinkle: siblings, not a root

Fixture derivation is "stem-prefixed siblings in the socket's directory": `/x/foo.sock` → `/x/foo.db`, `/x/foo.events.sock`, `/x/foo.tmux.sock`, `/x/foo.engine-trace.jsonl`. But everything the engine builds off the DB's _parent_ (row 9) is unprefixed: `/x/dispatch-events/`, `/x/attachments/`, `/x/backups/`, `/x/settings`. Two fixtures in the same directory would share those. And the worker path guard (row 26) guards the socket's parent directory, so a socket placed directly in `/tmp` or `$TMPDIR` turns the guard into a denial of the whole temp dir.

**Consequence:** a fixture must get its own directory, e.g. `/tmp/boss-e2e-<id>/engine.sock`. With that convention the engine's existing behaviour yields a clean per-instance tree and a correct guard. This is a usage rule today and should become an engine check (§6, PR 2).

Two more usage rules the trial run (§7) surfaced:

- **The root must be short.** macOS limits a Unix socket path to 104 bytes (`SUN_LEN`). A fixture rooted in an agent scratchpad (`/private/tmp/claude-501/-Users-.../scratchpad/...`) passes the isolation gate, writes its pid file, token and DB, and then dies at `bind` with `path must be shorter than SUN_LEN`. `/tmp/boss-e2e-<8 hex>/` is 34 bytes with the socket name and leaves room for `.events.sock` and `.tmux.sock`.
- **Unset `BOSS_APP_PID` too.** A fixture started from a worker pane inherits the production app's pid and logs `launched_by="app"` with that pid as its `RegisterAppSession` trust root. Harmless for an engine-only fixture (the production app never dials the fixture socket), but wrong, and the isolation guard does not cover it because it is not a path.

## 3. Not affecting the main products

What actually separates a test instance's work from production's:

1. **State.** The fixture DB starts empty. Products, projects, tasks, hosts, automations, attentions and PR observations all live in that DB. The merge poller, external-tracker sync, automation scheduler and stale-worker sweep all iterate their own DB, so with no production rows there is nothing for them to act on. There is no channel by which a fixture engine learns about production work items.
2. **Repos.** A product's `repo_remote_url` is the only thing that selects the cube pool (`cube repo ensure` by origin URL) and hence the origin every worker pushes to. Workers' PATH is sealed to engine-owned `boss`/`cube` launchers; the engine passes only an allowlisted env into panes; `gh` runs as the operator. So a product pointed at a throwaway repo cannot _accidentally_ reach a real repo through Boss's own plumbing. It can through a worker typing `gh pr create -R spinyfin/mono` or `git push` to a URL: nothing refuses that.
3. **Side channels that still reach real GitHub as the operator:** `boss shake` (files issues against Boss itself via the embedded GitHub App), the docs-repo path for investigation deliverables (`BOSS_USER_DOCS_REPO`, which on this machine points at the operator's real docs repo), GitHub issue tracking if the test product is bound to an external tracker, and Trunk/Buildkite reads (harmless).

**Model to copy: the `checkleft-sandbox` product.** It is a private throwaway repo (`brianduff/checkleft-sandbox`) with its own cube pool slug and its own Boss product, and workers dispatch into it the normal way (`tools/checkleft/docs/checkleft-sandbox.md`). For Boss end-to-end testing the equivalent is a dedicated `boss-e2e-sandbox` repo: tiny Rust+Bazel project, a root `CHECKS.yaml` so `checkleft run` has something to do, a minimal CI check so the merge poller's "effectively green" logic is exercised, branch protection on `main` so nothing merges without a PR, and a `README` stating it is disposable. The test instance's only product points at it, with `--worker-branch-prefix e2e/` so stray branches are identifiable, `--docs-repo` set to the same sandbox (or a second throwaway) so investigation deliverables never land in the real docs repo, and no external tracker binding.

**Hard rails worth adding (none exist today):**

- An engine-level allowlist, e.g. `BOSS_ALLOWED_REPO_REMOTES=<url>[,<url>]`, enforced at `product create`/`update`, at dispatch (`cube repo ensure` input), and on the docs-repo resolution. Unset = no restriction (production unchanged). This is the cheapest rail with real teeth because every Boss-driven push goes through a product's remote.
- A test-instance flag that disables `boss shake` (or routes it to the sandbox repo). Today `boss shake` from a sandbox worker files a real issue.
- Extending the existing worker PreToolUse push guard (`boss-checkleft-push-guard.py`) with the same allowlist so a worker's hand-typed `gh pr create -R` / `git push <url>` to a non-allowlisted remote is refused. Soft (workers could still script around it) but it catches the common case.

Spend: `BOSS_WORKER_POOL_SIZE`, `BOSS_AUTOMATION_POOL_SIZE` and `BOSS_REVIEW_POOL_SIZE` already bound the fixture's parallelism; `0` for all three gives a UI-only fixture. The coordinator Claude session (row 13) is the other spender and only starts when an app attaches.

## 4. Agent-driven testing

### 4.1 Launch

```sh
ROOT="/tmp/boss-e2e-$(uuidgen | cut -c1-8 | tr A-Z a-z)"; mkdir -p "$ROOT"   # short: SUN_LEN, see §2.1
env -u BOSS_EVENTS_SOCKET -u BOSS_DB_PATH -u BOSS_ENGINE_PID_PATH -u BOSS_ENGINE_CONTROL_TOKEN_PATH \
    -u BOSS_ENGINE_AUDIT_PATH -u BOSS_ENGINE_LOG_PATH -u BOSS_APP_PID \
    BOSS_RECOVERY_DIR="$ROOT/recovery" BOSS_ENGINE_DIAGNOSTICS_DIR="$ROOT/diagnostics" \
    BOSS_WORKER_TRANSCRIPTS_ROOT="$ROOT/executions" BOSS_RUNTIME_DIR="$ROOT/runtime" \
    BOSS_WORKER_OUTPUT_DIR="$ROOT/worker-output" BOSS_ATTACHMENT_PORT=0 \
    BOSS_WORKER_POOL_SIZE=1 BOSS_AUTOMATION_POOL_SIZE=0 BOSS_REVIEW_POOL_SIZE=0 \
    bazel run //tools/boss/engine/core:engine -- --socket-path "$ROOT/engine.sock" > "$ROOT/launch.log" 2>&1 &
```

The `env -u` list exists because a worker pane inherits production's `BOSS_EVENTS_SOCKET` and friends. mono#2206 made the engine derive over an inherited _production_ value anyway, so these unsets are belt-and-braces; the three `BOSS_*_DIR`/`ROOT` overrides are the ones that matter today (rows 10, 11, 12, 22). Wait for the audit line `test-fixture mode: resolved paths verified distinct from production state` in the launch log; that line is printed only after `ensure_isolated` passed.

### 4.2 Drive

- **CLI:** every `boss`, `bossctl` and `cube`-via-engine call takes `BOSS_SOCKET_PATH=$ROOT/engine.sock` (or `--socket-path`). Pass `--no-engine-autostart` so a typo in the path cannot start a stray engine. `boss product create --name e2e --repo <sandbox url> --worker-branch-prefix e2e/ --docs-repo <sandbox url>`, then `boss task create`, `bossctl work start`, `bossctl agents list`, `boss pr status` and `bossctl attachments list` all work against the fixture because they are plain RPCs over the socket.
- **UI:** `BOSS_SOCKET_PATH=$ROOT/engine.sock BOSS_ENGINE_AUTOSTART=0 bazel run //tools/boss/app-macos:Boss -- --capture-to $ROOT/shot.png --capture-after 3` renders the real board against the fixture and exits (mono#2479). Attaching an _interactive_ isolated app is also possible (same env, no `--capture-to`) but is the one path that creates a coordinator session in production's `boss-session` directory (row 13) and costs a Claude session; avoid until PR 1 in §6 lands.
- **Workers:** with a non-zero pool size the fixture leases real cube workspaces from the sandbox pool and spawns real driver sessions on the fixture's tmux server. Their hooks go to the fixture's events socket (row 3). Transcripts, probes, interrupt and stop go through the fixture's own `bossctl agents ...`.

### 4.3 Tear down

1. `kill $(cat "$ROOT/engine.pid")` after checking `ps -o command= -p <pid>` names `$ROOT/engine.sock`. The engine's `ControlTokenGuard` only deletes a token whose contents and inode it owns, so even a wrong pid could not clobber production's token.
2. `tmux -S "$ROOT/engine.tmux.sock" kill-server` if any worker panes outlive the engine.
3. Leases: the engine releases cube leases on completion; after a hard kill, `"$CUBE_BIN" workspace list` shows leases whose task text is the e2e task, release them with `cube workspace release --lease <id>`. These are sandbox-pool workspaces, so even a leaked lease never blocks production.
4. `rm -rf "$ROOT"`.

**What guarantees teardown never touches production:** every path the harness kills or deletes is under `$ROOT`, a directory the harness created. Production's pid file, sockets and token live under `~/Library/Application Support/Boss`, which the harness never names. The engine-side guarantees are `ensure_isolated` (refuses to start on a collision), the token+inode ownership check on delete, `bind_events_socket` refusing a live listener, and the orphan reaper (a fixture whose parent dies exits on its own within ~1 s, so an abandoned harness does not leave an engine running). What is **not** guaranteed today is covered by the four `BOSS_*` overrides above and by the coordinator-directory caveat; a harness that forgets an override leaks a directory, not a socket.

### 4.4 Recommended shape

A single `tools/boss/e2e/boss-e2e` script (Bazel `sh_binary`) with `up`, `env`, `shot`, `down` verbs that owns the root directory, the env list, the readiness wait, the pid-ownership check and the lease sweep. Workers would call it the way they call `"$BOSS_BIN"` today, and the launch guard already permits the underlying commands. Later it can grow `--host <id>` for §5.

## 5. Remote hosts (`anaplian`, `skaffen`)

The brief spells the first host `anaplain`; the repo's docs and the Buildkite queue spell it `anaplian`. Both hosts are macOS arm64 Buildkite agents in the `bazel-any` queue (`docs/investigations/checkleft-checks-ci-timing.md`), and `mac-toolchain-xcode-pinning.md` records a pinned-Xcode fix applied to both.

### 5.1 Model A: test engine on the laptop, test workers on the remote hosts (works today)

Boss already dispatches workers to SSH hosts (`bossctl hosts add`, `SshHostAdapter`, `remote/boss-remote-run.sh`). The remote needs only `cube`, the driver CLI, `gh` and the project toolchain; the wrapper runs the driver under `nohup` with no tmux and no display, and hook events come back over an SSH-forwarded Unix socket to the engine's events socket. A fixture engine registers hosts in its own DB, so the production engine's host registry is untouched.

What it takes:

- SSH alias to each host that connects without prompts, as the design assumes.
- On the host: `cube repo ensure` for the sandbox repo, `claude`/`codex`/`grok` logged in once interactively (Claude's OAuth lives in the host's keychain; `codex` and `grok` need their `auth.json`), `gh auth login`, the pinned Xcode state kept healthy.
- Two shared surfaces with the production engine if production also registers the same host: the ControlMaster socket path (row 22, fix with `BOSS_RUNTIME_DIR`) and the remote wrapper (row 23). If the fixture and production run the _same_ engine binary the wrapper fingerprint matches and nothing re-pushes; if they differ they fight. Treat "do not register a host in both engines with different binaries" as a rule until the wrapper path is per-engine.

Blockers: none in code. Practical: driver logins on the hosts, and sharing the machines with CI.

### 5.2 Model B: the whole instance on the remote host

- **Engine:** no display requirement. Needs `tmux` (local worker panes are tmux-hosted), `cube`, drivers, `gh`, and a Boss binary. Install options: the signed `.pkg` into `~/Applications` with `BOSS_INSTALL_ROOT` (the installed engine is then `Boss.app/Contents/Resources/bin/engine`), or `scp` a `bazel build`-produced engine. Everything in §4 then runs over `ssh host 'ROOT=... env ... engine --socket-path ...'`.
- **UI capture:** `cacheDisplay` draws offscreen and needs no visible window, but it does need a WindowServer connection and, for the libghostty panes, Metal. That means a user logged in at the console (auto-login or a persistent GUI session) and the app launched inside that session (`launchctl asuser <uid>` / `launchctl bootstrap gui/<uid>` from the SSH session, or a tmux server started from the console session). A locked screen does not stop offscreen rendering, but a host with no console login at all cannot run the app. This was not trialled here; it needs a probe on one host before being relied on.
- **Driving it:** the local agent runs the same recipe over `ssh`, copies the PNG back with `scp`, and calls `boss attach` against the _local_ engine it was spawned by. The remote instance's evidence server (row 21) is loopback-only and irrelevant.
- **Blockers:** the hosts are live CI agents, so a Bazel build of the engine there competes with CI for the same output caches and the Xcode pin; the GUI-session requirement is an operator setup step; and the `boss-session` directory (row 13) is the one production-shaped path that an interactive remote app would create under the host's own `~/Library/Application Support/Boss`, which is harmless on a host with no production Boss but still wrong.

Recommendation: do Model A first. It exercises remote dispatch, which is the part of Boss that only the remote hosts can test, with no new install surface. Model B only adds UI capture on the remote, which Model A already gets on the laptop against the same fixture.

## 7. Trial run (evidence)

One engine-only fixture was started from this worker pane on the operator's laptop while the production engine and app were running. No app was attached and every pool size was `0`, so no coordinator session and no worker was spawned. The production state root, sockets, tmux server and cube database were not read or written by the harness at any point; the evidence below is the fixture's own logs and directory.

**Attempt 1 (failed, two findings).** Root in this session's scratchpad (`/private/tmp/claude-501/.../scratchpad/boss-iso/`). The engine logged `test-fixture mode: resolved paths verified distinct from production state` with db, events socket, pid and token all under that directory, wrote its pid file, token, DB and stem-scoped trace/audit/text logs, ran tmux preflight and the local capability probe (`gh-authed=true`), then exited with `failed to bind unix socket ...: path must be shorter than SUN_LEN`. The audit `start` record also showed `launched_by="app"` with the production app's pid, inherited via `BOSS_APP_PID` from this pane. Both are folded into §2.1 and the recipe in §4.1. Before that, the first build attempt failed on the pinned-Xcode mismatch (host moved to Xcode 27, Bazel had 26.6 cached); clearing the cached `local_config_xcode` / `local_config_apple_cc` repos as `mac-toolchain-xcode-pinning.md` prescribes fixed it without an expunge.

**Attempt 2 (succeeded).** Root `/tmp/boss-e2e-8749335d/`, `BOSS_APP_PID` unset, the four directory overrides from §4.1 set, `BOSS_ATTACHMENT_PORT=0`. Observed:

**Two more findings from the successful run:**

- **The boss-event healing sweep writes to the shared worker-settings directory.** At startup the fixture logged `healing boss-event path in worker settings files dir=$TMPDIR/boss-worker-settings ... files_walked=40 files_healed=0`. Those 40 files are production workers' `claude --settings` files. `files_healed` was 0 only because the resolved `boss-event` path matched; a fixture built from a different binary, or resolving `boss-event` from a different location, would rewrite the hook command in live production workers' settings. This is a write to a shared surface that the isolation guard does not cover (`worker_setup.rs` `heal_worker_settings_json`, called from `app/server.rs`). Row 15 in §2 is corrected accordingly, and scoping the sweep to the engine's own instance is added to PR 1 in §6.
- **Driver probes found no drivers.** `host_capability_probe: local driver probe complete binary=claude found=false` (same for `codex`, `grok`), so `driver_count=0`: a fixture started from a worker pane would have no eligible local host for dispatch. The probe runs under the worker-sanitised PATH plus login-shell profile, and in this pane that did not resolve the driver binaries. The production engine, launched by the app, prepends well-known tool directories first. The harness (§6, PR 3) must do the same or export `BOSS_DRIVER_COMMAND`-style absolute paths; this was not resolved in the trial because no worker dispatch was attempted.

Not demonstrated: worker dispatch from the fixture, the app attached to the fixture, and anything on the remote hosts. The first two are the next experiments once the sandbox product exists (§6, PR 5); the remote model is argued from the existing SSH adapter code only.
