# Audit: how the macOS app calls the engine (fan-outs, re-send storms, polling)

- **Date:** 2026-10-19
- **Kind:** investigation (doc only, no code changes)
- **Scope:** every request the macOS app sends to the engine over the frontend socket, what triggers it, how many requests one trigger produces, what the engine does to serve it, and measured request rates against an isolated, seeded engine.
- **Out of scope:** the `resolve_project_design_doc` per-project fan-out (already being fixed; used only as the reference example) and the engine's SQLite locking / read-admission work (separate changes in flight).
- **Related:** `tools/boss/docs/investigations/cli-read-starvation.md`, `tools/boss/docs/forensic-surfaces.md`.

The app issues no per-card requests from the board, which is the good news. The bad news is that almost every _trigger_ in the app is a burst rather than a request: a connect, a product switch, a Work-tab visit and every `work_invalidated` push each fan out into a fixed set of 5 to 8 list reads plus one read per project, and the `get_work_tree` reply then fans out again. On the engine side a hot loop in the GitHub-auth forwarder can flood a session with pushes; the session queue then injects `resync_required`, the app answers a resync with its entire connect burst, and the replies refill the queue. Measured against a seeded engine, the app sat at roughly 3,000 requests per minute while "idle" in that state.

## TL;DR

1. **Engine-side hot loop (new, severe).** When the stored GitHub token is `Authorized` and either no product has a GitHub external tracker or the org probe fails (for example offline), `spawn_github_auth_forwarder` re-broadcasts `git_hub_auth_state` and re-runs `list_products` in a tight loop. Measured: 1,300 to 1,500 pushes per second to the app, continuously. Each iteration is a DB read. It runs with or without an app connected.
2. **Resync amplification (new, severe whenever any push burst happens).** A push burst that overflows the 256-entry per-session queue makes the engine inject `resync_required`, and the app answers a resync with the _full_ connect burst (10 reads plus one `list_planner_runs` per project). The replies refill the queue, so the system settles at about two resyncs per second. The 61-project design-doc incident had the same shape with a different seed.
3. **Every `get_work_tree` reply fans out** (`applyWorkTree`): `list_attention_items_for_work_item`, `list_attention_groups` and `resolve_project_design_doc` per project with a doc pointer. Several triggers already request the two attention lists _before_ the tree, so they are fetched twice per trigger.
4. **Connect, reconnect, product switch, Work-tab entry and every `products_list` reply double-fetch the tree.** Reconnect is indistinguishable from first connect and replays the whole startup burst.
5. **`work_invalidated` side-fetches are not debounced.** Only the tree fetch has a 150 ms debounce; the three attention lists, `list_planner_runs` for every project, `list_executions` for every card ever opened, and a `list_engine_attempts` poll fire once per invalidation. Measured: one board mutation on a 12-project product costs the app about 20 requests, 12 of them `list_planner_runs`, identically for an edit, a create or a move.
6. **A 5-second `list_engine_attempts {limit: 0}` poll** runs on every tab for the life of the connection, and the engine does not short-circuit on `limit: 0`: it reads every conflict resolution, CI remediation and rebase attempt, then discards them.
7. **Engine handlers that are expensive for what they return:** `get_work_tree` (full recompute even for `delta: true`, N+1 runtime and doc-pointer queries), `resolve_project_design_doc` (scans `work_executions` first), `list_attention_groups` (1 + 2N queries), `comments_list` (3 queries per comment), `get_review_guide_summary` (chain BFS plus a recursive CTE per verdict, polled every 5 s while open), `list_product_design_docs` (spawns `gh` under a read permit, no timeout), `trunk_status` (keychain read plus a blocking HTTP call per request), `execution_transcript` (whole-file read and parse, polled every 5 s while live).

## Method

**Code reading.** Every `send*` function in `tools/boss/app-macos/Sources/EngineClient+Requests.swift` (plus the raw-socket sends in `BossEnginePaths.swift` and the pane responses in `EngineClient+PaneResponses.swift`) was traced to its call sites and each call site classified by trigger. Each verb was then traced to its handler under `tools/boss/engine/core/src/app/` and the DB work read from the `work/` modules. SQLite `EXPLAIN QUERY PLAN` was not run; "scan" below means no index covers the predicate per `work/schema_init.rs`.

**Measurement.** An isolated engine was started per the recipe in `.claude/CLAUDE.md` (`--socket-path /tmp/boss-audit-a1.sock`, `BOSS_EVENTS_SOCKET` unset), with a restricted `PATH` so tmux is unresolvable and the engine holds dispatch instead of spawning a coordinator or workers. It was seeded through the `boss` CLI with 5 products, 60 projects (each with its auto-created design task), 300 tasks and 15 chores, with product 1's tasks spread across backlog, doing, review, blocked and done. Nothing in the engine logs app-to-engine request verbs (see "Observability gap"), so a transparent Unix-socket proxy was placed between the app and the engine and logged the `type` of every frame in both directions. The app was launched headless with `--capture-to … --capture-after 180`, so each scenario ran for three minutes and exited on its own. CLI mutations for the board-change scenario went straight to the engine socket, not through the proxy, so only the app's own traffic was counted. The proxy and seed scripts were temporary and are not committed.

Two caveats on the rig:

- The first idle run hit the GitHub-auth hot loop (finding 1) because the dev-build engine reads the OAuth token from the file fallback under the user's Boss state directory. Re-running the fixture with a private `HOME` left it disconnected and produced the clean baseline. Both runs are reported because the first is the more alarming one.
- The population-timing log (`engine-population-timing-*.jsonl`) is not scoped by fixture isolation: an isolated engine writes it into production's `diagnostics/` directory unless `BOSS_ENGINE_DIAGNOSTICS_DIR` is set. The second run set it; the first did not. Filed as a follow-up.

## Transport facts that frame everything

- Every request goes through `sendLine` (`EngineClient.swift:292`). There is **no in-flight dedupe or coalescing while connected**: two identical requests are two writes. The only coalescing anywhere is `scheduleWorkTreeRefetch`'s 150 ms per-product debounce (`ChatViewModel+EventHandling.swift:834-843`) and `requestBackgroundWorkRefresh` skipping when a `limit: 0` poll is already pending (`ChatViewModel+BackgroundWork.swift:65-71`).
- `queueIfDisconnected: true` (38 read verbs) parks a payload while the socket is down; a byte-identical newer payload supersedes it; cap 64; all are flushed on `.ready` (`EngineClient.swift:347-363, 493-503`). `get_work_tree` carries a fresh `fetch_seq` per call, so queued tree fetches are never byte-identical and never deduped: N product switches while disconnected become N full fetches on reconnect, each with its reply cascade.
- User mutations are tracked in an `ActionLedger` and retained for an explicit Retry; they are never auto-replayed. Reads are never retained. Reconnect backoff is 0.5 s to 30 s.
- `.connected` fires on every `.ready` and there is a single `.connected` arm in the view model, so **reconnect equals cold start**.
- `work_tree_update` is **not an unsolicited push**. The engine only produces it as the reply to `get_work_tree {delta: true}` (`engine/core/src/app/work_items.rs:1285-1336`); the app turns the reply into a `.workTree` event via `WorkTreeDeltaCache.apply`. On a base-sequence mismatch the app sends `get_work_tree {delta: false}` (`EngineClient.swift:723`); the engine clears its per-session cache on a full fetch, so the next delta reply is a full snapshot and there is no thrash loop.
- Pushes the engine sends unsolicited: `topic_event` (`work_invalidated`, `resync_required`), `work_item_created/updated/deleted`, `work_items_created`, `project_tasks_reordered`, `worker_live_states_list`, `git_hub_auth_state`, `engine_health_result`, `attention_*`, `automation_*`, `conflict_resolution_*`, `ci_remediation_*`, `comment_result`, `review_guide_summary`, `host_*`, `engine_request`.
- Subscribed topics: `work.products`, `worker.live_states`, `github.auth`, `engine.health`, `work.product.<selected>`, plus `comments.artifact.<kind>:<id>` per open comment layer (`ChatViewModel+WorkLookups.swift:220-249`, `ChatViewModel+Comments.swift:102-119`). Subscriptions are diffed and **do not change on tab switch**, only on connect and product switch.
- Engine side, every bulk read opens a **fresh SQLite connection** per request (`work/schema_init.rs:277-294`: `open_with_flags` plus PRAGMAs); only `GetWorkTree` and `ListProposals` use the read-only `reader()`. Several read handlers still take the shared writer mutex (`resolve_work_item_id`, `get_settings`, `evaluate_dispatch_admission`, `trunk_status`). Read admission is a near-unbounded semaphore (4,096 concurrent), and `read_freshness` substitutes a newer reply for an older in-flight one but never skips the query.

### 1.4 Things checked and found clean

- No `WorkBoardCard*`, badge strip, badge, revision badge, banner, staleness indicator or external-tracker banner issues a request on appear; badge data comes from pushes and list replies. Per-card requests only happen on selection (`list_executions` for the one popover task).
- `work_item_updated` for tasks, chores and projects is applied in place with no refetch.
- Subscriptions are diffed and not churned on tab switch; comment topics are ref-counted per artifact.
- `loadTranscript`, `loadAttentionMergesIfNeeded` and `PlannerRunAffordance` cache or guard their requests.
- The `DriverQuotaSection` 60 s tick, the `DispatchEventsData` / `LogViewer` 2 s timers, and the 5 s one-shot sleeps in `OptimisticKanban` and `EventHandling` generate no engine traffic.
- The engine-process supervision tick does not open probe sockets while the client is connected.
- The delta-base-mismatch fallback does not loop.

## 2. Engine-side pushes and the session queue

The engine never pushes a work tree. Mutations publish `TopicEvent { WorkInvalidated { reason, product_id, item_ids } }` on `work.product.<id>` (and `work.products`), and the app refetches. Publish fan-out is one small envelope clone per subscribed session; the recompute happens on the refetch. Per session, `SessionSink::enqueue` coalesces a pending unsent `TopicEvent` for the same topic in place, but **non-topic pushes (`git_hub_auth_state`, `worker_live_states_list`, `engine_health_result`, attention and automation pushes) are never coalesced**. The bulk lane holds 256 entries (`MAX_SESSION_QUEUE`, `app/session_queue.rs`); when it is full and the client is still draining, the oldest uncorrelated push is evicted and a single `resync_required` marker is queued (`admit_under_pressure`); a client with no write progress for 5 s is disconnected.

The app's reaction to `resync_required` (`ChatViewModel+Connection.swift:90-103`) is a near-copy of the connect burst: `list_products`, `list_worker_live_states`, `list_live_status_disabled_slots`, every open comment layer reloaded (3 requests each), an un-debounced `get_work_tree`, `list_attention_items_for_work_item`, `list_attention_groups`, `list_deferred_scope_attentions`, `list_planner_runs` for **every project of the product**, and `list_engine_attempts {limit:0}`; the `products_list` reply then adds another `get_work_tree`, and each tree reply adds the WT cascade. That is 10 + J + 2 + 2 + P requests, and about as many reply frames back into the same 256-slot queue that just overflowed.

### 2.1 The GitHub-auth forwarder hot loop

`spawn_github_auth_forwarder` (`app/server.rs:326-358`) is:

```text
loop {
    state = rx.borrow_and_update()
    broadcast_github_auth_state(state)           // push to every session on github.auth
    if state is Authorized { org_state: Unknown } {
        resolved = probe_and_record_org_state(..) // list_products on the DB, then GET /orgs/{org} per org
        controller.update_org_state(resolved)     // send_if_modified(|s| { *os = org_state; true })
    }
    rx.changed().await
}
```

`update_org_state` always returns `true` from `send_if_modified` for an `Authorized` state (`github_tracker/src/github_oauth.rs:748-757`), so `changed()` fires even when `resolved` is `Unknown` again, and `probe_and_record_org_state` returns `Unknown` whenever no product has a GitHub external tracker configured (`!probed_any`, `:879`), when `list_products` fails, or when every org probe errors (network down, token revoked). Each iteration is a `list_products` read, a broadcast to the app, and in the probe-failure case a real GitHub request. Measured at 1,300 to 1,500 broadcasts per second with the engine at about 13 % CPU on an idle laptop. Whether a given production install is in this state depends only on whether at least one product has `external_tracker_kind = github`; it is worth checking by sampling `engine-trace.jsonl` for `frontend frame write started` lines with a `git_hub_auth_state` prefix, or simply by the engine's idle CPU.

## 4. Pathological patterns, ranked, with proposed fixes

Ranking weighs requests per minute under realistic triggers against the DB cost of the handler. Each item is sized to be its own change. Items 1 and 2 are engine-side; the brief asked for app patterns, but they are the two biggest multipliers on everything the app does and the measurement would be misleading without them.

### 4.1 GitHub-auth forwarder hot loop (engine) — thousands of DB reads and pushes per second

**Shape:** polling disguised as a watch loop; `send_if_modified` reports a change when nothing changed. **Measured:** 1,300 to 1,500 `git_hub_auth_state` pushes per second; the first idle run logged 142,000 of them in three minutes. Each iteration also runs `list_products`.

**Fix:** make `update_org_state` return `true` from `send_if_modified` only when the org state actually differs, and make the forwarder stop probing after an `Unknown` result: either back off (for example 30 s, then 5 min) or wait for an explicit trigger (`git_hub_auth_status`, a product's tracker config changing, a `restore_from_store`). The broadcast should also be skipped when the DTO is identical to the last one sent. One file (`app/server.rs`) plus one method in `github_tracker/src/github_oauth.rs`, plus a test that drives the watch channel with an `Authorized { Unknown }` state and asserts a bounded number of probes.

### 4.2 `resync_required` answered with the full connect burst (app, with an engine assist)

**Shape:** refetching full state where a delta exists; retries without backoff. **Measured:** with the queue overflowing, ~2 resyncs per second, each costing 10 + J + 2 + 2 + P requests; steady 3,000 requests per minute on a 12-project product, dominated by `list_planner_runs` (1,500/min), the two attention lists (375/min each) and `get_work_tree` (250/min).

**Fix (app):** route `resync_required` through the same 150 ms per-product debounce as `work_invalidated`, and make the resync fetch set the _minimum_ needed (one `get_work_tree`, one `list_attention_groups`, one `list_attention_items_for_work_item`), not the planner-run and live-state sweep. Add a per-session cap: if a second `resync_required` arrives within, say, 5 s, back off exponentially instead of refetching. **Fix (engine):** `admit_under_pressure` should coalesce non-topic pushes by kind the way it coalesces topic events (at most one pending `git_hub_auth_state`, `worker_live_states_list` or `engine_health_result` per session), so a push storm cannot overflow the queue in the first place. Both halves are small; the engine half has existing tests in `session_queue.rs` to extend.

### 4.3 The `applyWorkTree` cascade (app) — 2 + P requests per tree reply, on top of the same requests sent before the tree

**Shape:** per-item fan-out (`resolve_project_design_doc` × P, the reference example) and duplicate requests for the same data (attention lists requested both before and after the tree). **Measured:** 3 `list_attention_groups` and 2 `list_attention_items_for_work_item` per connect; 2 each per invalidation and per product switch.

**Fix:** the engine should include the attention summary the board actually renders in the `work_tree` payload (counts per work item and the open group list for the product) so the app never requests them after a tree. Until then, drop the two list calls from `applyWorkTree` and keep only the ones fired by the trigger. The design-doc resolve is already moving to on-click; the remaining principle is that `applyWorkTree` should make no requests at all.

### 4.4 Double tree fetch on connect, Work-tab entry, product switch and every `products_list` reply (app)

**Shape:** duplicate requests for the same data; refetching full state on a trigger that already scheduled one. The `products_list` handler unconditionally fetches the tree for the selected product, so any product-level mutation anywhere (create product, set repo URL, archive) costs a full tree plus its cascade, and `refreshWork` (Work-tab entry, Refresh button) costs two trees. **Measured:** 2 `get_work_tree` in the clean connect burst; the first run showed the tree being fetched 106 times in 10 s.

**Fix:** only fetch the tree from the `products_list` reply when no product was selected before (the auto-select case); when a product is already selected, let the invalidation path own the refetch. Make `refreshWork` request `list_products` only and let the reply pick the product, or request the tree only. Treat reconnect differently from first connect: on reconnect, re-subscribe and send one `get_work_tree {delta: true}` and let the engine's delta cache answer with only what changed, rather than replaying the settings, health, auth and live-state reads that the engine also pushes on their topics.

### 4.5 Invalidation side-fetches are not debounced (app)

**Shape:** re-sending on every push; per-item fan-out (`list_planner_runs` × J, `list_executions` × every card ever opened). A burst of N invalidations coalesces the tree fetch to one but sends N × (3 + J + loaded cards) list requests. **Measured:** see the board-change table; `list_planner_runs` is the top verb by count under churn, and the only consumer is a per-project affordance that already fetches once on appear.

**Fix:** move the attention lists, `list_planner_runs` and `list_executions` into the same debounced refetch as the tree (one coalesced burst per 150 ms), and have the engine include planner-run state (just the latest outcome per project) in the work tree so the per-project list goes away entirely. Evict `executionsByTaskID` entries when a popover closes so closed cards stop being refetched. This is one change in `ChatViewModel+EventHandling.swift` plus a small protocol addition.

### 4.6 The 5-second `list_engine_attempts {limit: 0}` poll (app + engine)

**Shape:** polling where the engine could push; a handler that does full work for a request that asks for nothing. **Measured:** exactly 12 per minute idle on every tab; the engine reads every conflict resolution, CI remediation and rebase attempt and throws them away each time, plus a `planner_runs` scan for the background-work snapshot.

**Fix (engine, trivial):** skip the attempts fetch when `limit == Some(0)`. **Fix (app + engine):** publish the background-work snapshot on a topic (`engine.background_work`) whenever a conflict resolution, CI remediation or planner run changes state, and drop the timer. The engine already pushes `conflict_resolution_*` and `ci_remediation_*` events, so the only new thing is the planner-run transition.

### 4.7 `conflict_resolution_*` / `ci_remediation_*` pushes → two `limit: 200` list fetches each (app)

**Shape:** refetching full state on a push that already carries the changed row; requests issued while the consuming view (Activity) is not visible. Each push costs a `list_conflict_resolutions` or `list_ci_remediations` with 200 rows of JSON diagnosis / log excerpt plus a `list_engine_attempts {limit: 200}` that re-reads the same tables.

**Fix:** apply the pushed row in place (the push carries the attempt) and fetch the lists only when the Activity window is open. The card chips need only the open set per PR, which the push can carry.

### 4.8 Automation pushes → per-automation `list_automation_runs` (app)

**Shape:** per-item fan-out; requests while the tab is unmounted. `automations_list` triggers N `list_automation_runs`; every `automation_created/updated/result` push triggers a runs fetch and an open-task count that `automations_list` already contains.

**Fix:** fetch runs lazily when an automation row is expanded, and have the engine include `open_task_count` and the last run summary in the automation push payload.

### 4.9 Comment layers reload 3 requests per layer per trigger (app)

**Shape:** refetching full state where a delta exists; `comments_resolve` ships the whole plain-text projection every time. On connect, resync and every `comment_result` echo, every open layer sends `comments_list` + `comments_banner_state` + `comments_resolve`, and `comments_list` is 3 queries per comment on the engine.

**Fix:** apply the `comment_result` echo in place instead of reloading; call `comments_resolve` only when the document text changed; batch `comments_with_thread` into one `IN(...)` query on the engine.

### 4.10 View-scoped 5-second polls (app)

`get_review_guide_summary` (the heaviest small-result handler in the engine) and `execution_transcript` (whole-file read) poll every 5 s while their viewers are open; `metrics_list_live` polls every 5 s but is in-memory. **Fix:** subscribe to `executions.<id>` (the topic already exists) for the live transcript and have the engine send an offset-based tail; push `review_guide_summary` when a finding or verdict changes (the engine already has a `review_guide_summary` push type) and drop the timer.

### 4.11 Reconnect replays the startup burst with no dedupe of queued reads (app)

Covered by 4.4; the extra point is that `queuedReads` dedupes by byte-equality and `get_work_tree`'s `fetch_seq` defeats it. **Fix:** key the queue by `read_admission::key`-style view identity (verb + product) rather than bytes.

## 6. Observability gap

Nothing in the engine records app-to-engine request verbs. `engine-ipc-*.jsonl` logs only engine-to-app `EngineToAppRequest`s and their responses; the Swift `IpcLog` logs only `recreate_coordinator`; `metrics_list_live` has no per-verb counter; the population-timing log covers `get_work_tree` only; the read-admission diagnostics dump verb names only on rejection, rate-limited to one per second. The only per-request hook is `variant_name(&request)` at `app.rs:~2512`, already computed for diagnostics. A per-verb counter family in `metrics_init.rs` (`frontend_requests_total{verb}`, `frontend_pushes_total{kind}`) fed from that point would have surfaced every finding in this document from the production Metrics window, and the socket proxy used here would not have been needed.
