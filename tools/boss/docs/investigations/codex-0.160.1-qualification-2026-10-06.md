# Qualifying codex-cli 0.160.1 for the codex driver

- **Date:** 2026-10-06
- **Kind:** version qualification — changelog review against the driver's measured contracts, plus a live re-measurement of the TUI surfaces the driver screen-scrapes
- **Pins:** from `codex-cli 0.153.4` to `codex-cli 0.160.1` (`tools/boss/engine/core/codex_cli_version.bzl`); pane mode `--no-alt-screen`, the spawn line `CodexDriver::build_codex_command` ships
- **Isolation:** every live run used a scratch `CODEX_HOME` under the session scratchpad seeded with a writable byte copy of `auth.json` (per [`codex-auth-isolation-2026-07-26.md`](codex-auth-isolation-2026-07-26.md)), its own tmux server (`tmux -L …`, never Boss's), and the release tarball extracted next to its `codex-code-mode-host`. The host machine's `~/.codex` and installed `codex` were read, never written. Control runs used the installed 0.153.4 with the same harness.
- **Related:** [`codex-tui-liveness-marker-stability-2026-07-31.md`](codex-tui-liveness-marker-stability-2026-07-31.md) (the marker method), [`codex-tui-pivot-pricing-2026-07-30.md`](codex-tui-pivot-pricing-2026-07-30.md) (spawn-line contract), [`codex-pretooluse-decision-vocabulary-2026-07-30.md`](codex-pretooluse-decision-vocabulary-2026-07-30.md) (hook dialect)

## Why

On 2026-10-06 the host machine auto-updated codex from 0.153.4 to 0.160.1. 0.159 and 0.160 ship a TUI overhaul (new welcome screen, borderless header, turn footers, interruption notice), and 0.156/0.157 introduced a shared background app-server daemon that interactive sessions attach to by default. Boss pins a version only for tests; production workers run whatever `codex` is on `PATH`. The machine was rolled back and this pass qualifies 0.160.1 so the move can be deliberate.

Verdict: no impact.

- `driver/src/codex/progress.rs` guard-notification handling (L161-190) — see the first bullet; unchanged inputs, unchanged output.

## Live guard-conformance probe status

**Passed on 0.160.1, 2026-10-07:** `bazel test //tools/boss/engine/core:codex_guard_live_test --test_env=BOSS_CODEX_AUTH_SOURCE=<path to an auth.json>` completed with exit 0 in 32.7 seconds (invocation `2a8a4d6a-d0d2-4816-801b-eded9c9c5c36`). The single dispatched model, `gpt-6-astra`, exercised every `EXPECTED_PROBES` entry without skips: shell approval, push refusal, workspace patch approval, interactive-shell refusal, MCP refusal, and data-directory patch refusal. The exact tool names, payload keys, aggregate decisions and matching guard sets all passed unchanged.

The manual `network_enabled_rust_test` grants network access on both Linux and macOS. It supplies the checksum-pinned CLI and code-mode host, stages both together, and copies the caller's credential into a writable private tempdir before auth snapshotting. The caller's credential is never modified.

Diagnosis of the earlier failures: the macOS hermetic wrapper denies Keychain access, so the CLI could not establish TLS until given an explicit CA bundle. After that, the model executed but hook launches failed and produced no trace: Codex selects the passwd login shell (`/bin/zsh` on this host) even with `SHELL=/bin/bash`, and that executable was not a declared runtime input. The live target now declares the host login shell and CA bundle separately from the common test runtime. The existing sandbox policy is unchanged; unrelated tests do not gain that shell. These were fixture/environment failures, not a change in the six guard verdicts.

This probe deliberately substitutes `codex exec` for the production interactive TUI command; the substitution asserts exactly one match so a spawn-line change fails loudly. It does not qualify TUI keyboard input or saved-session reload. The interactive-shell step is a model `exec_command` attempting `sh -s`, not stdin delivery to the Codex TUI. The earlier separate TUI measurements remain the evidence for Escape and mid-turn keyboard delivery.

## Harness notes

Pane submission via `tmux send-keys -l -- <text>` followed immediately by `send-keys C-m` — the shape `boss_tmux::send_keys` uses — intermittently leaves a long prompt in the composer with a newline inserted instead of submitting, on **both** 0.153.4 and 0.160.1 (first attempt after a turn ends in 2/2 harness runs per version; a 1 s gap before `C-m` submitted reliably). The engine's pane delivery already waits for echo rather than submission, so this is a pre-existing property of the TUI's paste-burst handling, not a 0.160 change; the measurements above use the documented 1 s submission gap.

### Recovery boundaries

Fresh spawns use `driver/src/codex.rs:1056` and never reload a saved CLI session. Persistent panes retain the running Codex process; remote engine recovery re-establishes event forwarding (`core/src/remote_reattach.rs:118`) rather than issuing a CLI resume. Progress recovery deserializes the normalizer snapshot (`driver/src/codex/progress.rs:493`), including open tool calls and notification offsets. Rollout session IDs are discovery and attribution inputs, not resume arguments.

## Concurrent trust-observation measurement

The review's concurrent shape was re-run with `bazel test //tools/boss/engine/driver:driver_test //tools/boss/engine/core:engine_lib_test --nocache_test_results`. With warm outputs and 12 overlapping actions, the driver took **50.4 s** and the slowest engine shard took **50.5 s** (invocation `fce4defe-7101-43e6-bea8-0cb6d5fea728`). This attempt passed, but reproduced the large slowdown close to the driver's 60 s budget; the earlier reviewed failure is not claimed to have repeated.

The driver target now has `tags = ["exclusive"]`, so Bazel runs its 30 real trust observations after the engine shards finish. In the same invocation shape after the change, driver_test passed in **4.8 s** (invocation `ee60ecc9-d0fa-40e8-aaa8-9dd45dcfb7d0`). The production 10 s trust deadline, target size, and all assertions remain unchanged. This prevents contention within one Bazel invocation; it does not reserve the host against other workloads.

That post-change invocation's engine shards hit their existing 300 s timeout while still completing tests. This is recorded separately from the driver scheduling result in the PR validation, including the complete isolated-shard rerun; it is not counted as a passing combined suite.

The earlier isolated run reported 3.4–210.7 s per shard (invocation `86154daa-7e9f-4570-bb88-d6aa1a7adcb0`). Its shard-level logs are not available in this revision, so the 210.7 s observation cannot be assigned reliably to a test or shard. It is not evidence for a cause of the timeout. The previous attribution to environmental concurrency sensitivity is withdrawn; the reproducible base/head measurements below replace it.
