# Qualifying codex-cli 0.160.1 for the codex driver

- **Date:** 2026-10-06
- **Kind:** version qualification — changelog review against the driver's measured contracts, plus a live re-measurement of the TUI surfaces the driver screen-scrapes
- **Pins:** from `codex-cli 0.153.4` to `codex-cli 0.160.1` (`tools/boss/engine/core/codex_cli_version.bzl`); pane mode `--no-alt-screen`, the spawn line `CodexDriver::build_codex_command` ships
- **Isolation:** every live run used a scratch `CODEX_HOME` under the session scratchpad seeded with a writable byte copy of `auth.json` (per [`codex-auth-isolation-2026-07-26.md`](codex-auth-isolation-2026-07-26.md)), its own tmux server (`tmux -L …`, never Boss's), and the release tarball extracted next to its `codex-code-mode-host`. The host machine's `~/.codex` and installed `codex` were read, never written. Control runs used the installed 0.153.4 with the same harness.
- **Related:** [`codex-tui-liveness-marker-stability-2026-07-31.md`](codex-tui-liveness-marker-stability-2026-07-31.md) (the marker method), [`codex-tui-pivot-pricing-2026-07-30.md`](codex-tui-pivot-pricing-2026-07-30.md) (spawn-line contract), [`codex-pretooluse-decision-vocabulary-2026-07-30.md`](codex-pretooluse-decision-vocabulary-2026-07-30.md) (hook dialect)

## Why

On 2026-10-06 the host machine auto-updated codex from 0.153.4 to 0.160.1. 0.159 and 0.160 ship a TUI overhaul (new welcome screen, borderless header, turn footers, interruption notice), and 0.156/0.157 introduced a shared background app-server daemon that interactive sessions attach to by default. Boss pins a version only for tests; production workers run whatever `codex` is on `PATH`. The machine was rolled back and this pass qualifies 0.160.1 so the move can be deliberate.

### Engine-contract review (modules the brief named)

- `core/src/codex_guard_trace.rs` (module doc L1-27) consumes the `GUARD_TRACE_MARKER` / `GUARDS_SILENT_MARKER` notifications that `driver/src/codex/progress.rs` emits from `drain_guard_trace_notifications` (L161). Those read the shim's own trace file (`guard_trace.rs` `guard_trace_path` L101, `read_records_from` L527) and the on-disk armed chain (`guard_chain::armed_chain_status`), not any Codex stream field. The measured PreToolUse payload keys, hook dialect, and "untrusted hook is silently skipped" behaviour are unchanged on 0.160.1, so no 0.154–0.160 change alters what the trace observes. Verdict: no impact.
- `core/src/codex_unobserved_command.rs` (module doc L1-21) depends on a start record with no matching completion at the turn boundary. The rollout record types (`custom_tool_call` / `custom_tool_call_output`) and the code-mode cell dialect were measured identical, and 0.158's launch-failure events surface as ordinary completions, so the start/complete pairing is unchanged. Verdict: no impact.
- `core/src/codex_home_retention_sweep.rs` (module doc L1-12) works only from `driver_runtime_state` rows and execution status, and deletes whole homes. The `CODEX_HOME` layout and rollout filename/`session_meta` shape were measured identical, and Codex's own log-database reclamation operates inside a live home. Verdict: no impact.
- `driver/src/codex/progress.rs` guard-notification handling (L161-190) — see the first bullet; unchanged inputs, unchanged output.

## Live guard-conformance probe status

`codex_guard_conformance_against_live_dispatched_models` (`core/src/conformance/guard_conformance.rs`) now resolves the pinned release through `codex_cli_binary()` (`BOSS_TEST_CODEX` first), snapshots a private copy of the credential inside the test tempdir (the auth snapshot takes a `<source>.boss-lock` sibling and may adopt a refreshed token back, neither of which the hermetic wrapper permits beside a credential outside the test tmpdir), exposes the binary as `codex` on `PATH` for the hook-trust gate, and drives the model headlessly through `codex exec` (the driver's production command is the interactive TUI, which exits with `Error: stdin is not a terminal` when piped — the harness predates the TUI pivot).

Qualification command (opt-in; spends real API calls): `bazel test //tools/boss/engine/core:engine_lib_test --test_filter=codex_guard_conformance_against_live_dispatched_models --test_env=BOSS_CODEX_GUARD_LIVE_PROBE=1 --test_env=MONO_TEST_ALLOW_NETWORK=1 --test_env=BOSS_CODEX_AUTH_SOURCE=<path to an auth.json>`.

Result on 0.160.1 (2026-10-07): the harness provisions, attests hook trust live, and boots `OpenAI Codex v0.160.1` with the probe prompt, but every model request then fails inside the hermetic sandbox (`failed to refresh available models: Connection failed: error sending request`, `Reconnecting… 5/5`), so no `EXPECTED_PROBES` step executed and none of the production-guard routes (push, apply_patch, interactive stdin, MCP tools, data-directory edits) was observed on 0.160.1. That is not a pass; the always-on hermetic half (tool-mode fixture, spawn contract) and the shell-hook block / `hooks/list` trust evidence above are what 0.160.1 is qualified on.

## Harness notes

Pane submission via `tmux send-keys -l -- <text>` followed immediately by `send-keys C-m` — the shape `boss_tmux::send_keys` uses — intermittently leaves a long prompt in the composer with a newline inserted instead of submitting, on **both** 0.153.4 and 0.160.1 (first attempt after a turn ends in 2/2 harness runs per version; a 1 s gap before `C-m` submitted reliably). The engine's pane delivery already waits for echo rather than submission, so this is a pre-existing property of the TUI's paste-burst handling, not a 0.160 change; it is recorded here and left out of this qualification.
