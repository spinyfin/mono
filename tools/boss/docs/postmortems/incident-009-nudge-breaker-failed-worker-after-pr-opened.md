# Incident 009 — The nudge circuit breaker failed a worker after it had already opened its PR

- **Date:** 2026-11-03 UTC (evening of 2026-11-02 in the host's local zone, CST, UTC−06:00). All timeline times below are **UTC**.
- **Impact:** A long-running eval task in `brianduff/isse` was failed by the nudge circuit breaker about 2.5 minutes after its worker opened and the engine verified [brianduff/isse#86](https://github.com/brianduff/isse/pull/86). The failure text falsely said "No PR was produced." The task went to `blocked`, the PR was unbound from the execution, and the workspace lease was released as `proven_completed` while a paid background eval was still running in it. A manual restart started a fresh worker in a different workspace with no knowledge of the open PR or the running eval.
- **Status:** Not fixed. The defects described here are present on `main` at the source baseline. This document changes no code; see §7 and §8.
- **Provenance:** A read-only snapshot of the engine database (`work_executions`, `work_runs`, `worker_proposals`, `task_status_audit`), the engine's text log and JSONL trace for the execution, the worker's Claude Code transcript, the GitHub PR, and source inspection.
- **Source baseline:** `spinyfin/mono` `main` at `0a701e98f677`. All `path:line` references refer to this revision. Engine paths are relative to `tools/boss/engine/` unless they start with `tools/`; `protocol/…` is `tools/boss/protocol/…`. The running engine binary may be slightly older than the baseline, but every log message quoted below matches source text at that commit word for word.

## 1. Summary

The initial premise of the incident report was that the worker had not used Boss's long-wait mechanism. That premise is wrong. The worker **did** use `boss propose wait`: it declared seven waits, all accepted, and it was told about the mechanism in its brief and in every nudge. It ran out of the **4 h cumulative per-execution wait budget** (`WAIT_MAX_TOTAL_SECS_PER_EXECUTION`). Once the budget was gone it **opened brianduff/isse#86 at 05:41:01**, and the engine bound and verified the staged PR URL. About 2.5 minutes later the merge poller replayed a **stale `no_pr` nudge intent**, recorded before the PR existed, through the breaker. That tripped the breaker and failed the execution with the false text "no new commit, PR, or state change. No PR was produced."

### Verdict

The breaker did not fire because of a long wait as such. It fired because:

1. a cached produce-a-PR nudge intent was never invalidated when the worker produced a PR, and
2. the breaker's progress check for the no-PR path is the constant string `"no_pr"`, so nothing the worker did could count as progress except a _finalized_ PR.

The PR stayed unfinalized because no `propose done --outcome delivered` had been declared yet. The worker was deliberately not declaring, because the eval was still running.

### 3.2 The `work_runs.finished_at` = 01:52:32 oddity

This is a recording artifact and did not cause the failure. The `work_runs` row represents the _dispatch/spawn_ run. It is finalized as `completed` 2 s after spawn while the execution "parks at its wait state — LIVE" (`dispatch/src/coordinator/run.rs:1106`). The breaker later flipped the run's `status` to `failed` with `error_text`, but did not refresh `finished_at`. So the row reads "failed, finished 01:52:32", which misleads anyone reconstructing runtime from `work_runs`. **Inference:** which `UPDATE work_runs` wrote the failure status was not traced. Worth a small fix (either the run row should span the pane's life, or the failure write should not imply that row's end time), but it is not part of the causal chain.

## 5. Investigation and root cause

### 5.1 How the breaker decides "no progress"

**The breaker itself.** `completion/src/nudge_breaker.rs:155-180` keeps an in-memory map `execution_id -> (fingerprint, count)`.

- A different fingerprint resets `count` (line 163).
- The same fingerprint increments it. It trips when `count >= max` (default 3, line 50) or when `total_count >= ABSOLUTE_MAX_NUDGES` (12, line 62) (lines 179-180).
- A 60 s `MIN_RENUDGE_INTERVAL` debounce applies (line 72).

**What counts as progress is entirely what the caller puts in the fingerprint.**

- For a worker with no PR, the Stop path calls `nudge_or_park(&execution, PROBE_NO_PR, "no_pr", None, …)` (`completion/src/stop.rs:1579`; same in `completion/src/no_op.rs:133`). The fingerprint is the **constant string `"no_pr"`**: no commit SHA, no diff hash, no bookmark head. Local commits, file changes, passing tests and background job progress can never reset the count. Only a code path that leaves the "no PR" branch, or calls `nudge_breaker.forget`, can.
- The doc comment at `completion/src/nudge.rs:17-20` says the fingerprint "must encode the work state so an unchanged state counts as unproductive". `"no_pr"` encodes one bit.
- The only reset when a PR is contributed is `completion/src/pr_transition.rs:648-652` (`nudge_breaker.forget`, `build_wait_tracker.forget`, `background_children_tracker.forget`). That runs only when the PR is **finalized**.

**Gate order in `nudge_or_park`** (`completion/src/nudge.rs:38-366`):

1. Manual hold.
2. Unresolved `[blocked]` / escalation.
3. **Active worker wait** (`wait_registry.active`, lines 91-128). Suppresses the nudge and does not consult the breaker. It records a `NudgeHold::WorkerWait` intent for the merge-poller recheck.
4. Build-wait / background children.
5. Breaker `record` (lines 279-318). `Trip` → `fail_for_unproductive_nudges` (lines 625-680), which formats "No PR was produced." whenever the _passed_ `bound_pr_url` is `None` (line 634).

**The path that actually tripped: `recheck_background_nudge`** (`completion/src/nudge.rs:392-622`), driven on every merge-poller pass by `core/src/merge_poller/sweep.rs:494-500`.

- It **replays the intent captured at an earlier Stop**: `intent.probe_text`, `intent.fingerprint`, `intent.bound_pr_url` (lines 544-554). It does not recompute them from current state.
- After a sweep-delivered nudge on a `Debounced` / `WorkerWait` hold, the intent is deliberately **retained** (lines 587-596) "all the way to the breaker's own terminal".
- Activity (a moved watermark) only _defers_ the replay (lines 425-442). When the worker goes quiet again, the stale intent fires (lines 529-554).

**The bug.** When the worker opened PR #86, the Stop at 05:42:07 went down the staged-PR branch (`completion/src/stop.rs:822-836` → `completion/src/metadata_gate.rs:529` `await_run_done_declaration` → `HoldingWithinHorizon`, lines 570-582). That branch:

- returns `AwaitingRunDoneDeclaration` **without calling `nudge_or_park`**, so the `forget_intent` at `completion/src/nudge.rs:353` never runs, and
- does not call `nudge_breaker.forget` / `background_children_tracker.forget`, which happen only on finalization (`completion/src/pr_transition.rs:648-652`).

So the retained `no_pr` intent, with `bound_pr_url=None` and the breaker already at count 3, survived the PR's creation. The next quiet sweep (05:43:31) replayed it and tripped. The same gap exists in the PR-recheck staged-URL deferral (`completion/src/recheck.rs:117-120`).

Two code paths disagreed:

- The staged-PR path judged the run to be within a 1200 s declaration horizon.
- The stale-intent replay judged it to have produced no PR.

The replay won because it runs independently, later in the same sweep (`core/src/merge_poller/sweep.rs:490-500`, after `sweep_pending_pr`).

### 5.3 Root cause (verified)

**A stale, cached produce-a-PR nudge intent was replayed after the worker produced a PR.** `recheck_background_nudge` replays the fingerprint and `bound_pr_url` captured at nudge time (`completion/src/nudge.rs:544-554`) instead of re-deriving current state. The staged-PR / awaiting-run*done paths (`completion/src/stop.rs:829-836`, and `completion/src/recheck.rs:117-120` → `completion/src/metadata_gate.rs:529`) neither retire that intent nor reset the breaker; only PR \_finalization* does (`completion/src/pr_transition.rs:648-652`). With the breaker already at 3 on fingerprint `"no_pr"`, the next quiet sweep tripped it. The breaker also wrote a factually false diagnostic ("No PR was produced") because the message comes from the replayed `bound_pr_url=None` (`completion/src/nudge.rs:633-635`), not from a fresh check.

## 6. Contributing factors

1. **(Verified) The progress definition is one bit.** The no-PR fingerprint is the literal `"no_pr"` (`completion/src/stop.rs:1579`). Over 3 h 50 m the worker produced commits, a passing 1035-test suite, a drafted report, and a $70+ paid sweep. None of it registered as progress. The count reached 3 across 75 minutes and seven waits, because waits _suspend_ the breaker but never reset it.
2. **(Verified) The wait budget is far shorter than the work and charges unused time.** A 4 h cumulative cap with full-grant charging spent about 72 min of budget on early wakes and one reworded re-declaration. The task (a multi-hour paid eval at large/xhigh effort) structurally needed more than 4 h of idle wall-clock. The cap is per execution and has no escalation path; once it is exhausted the worker's only options are to open a PR early or be failed.
3. **(Verified) The worker was told a wait mechanism exists but not its real budget.** The brief and nudges state the 2 h per-wait cap. The 4 h total is described only as "also capped". The worker discovered the number from a rejection at 04:31.
4. **(Verified) No liveness signal for background processes.** `--waiting-on pid` is ignored (`protocol/src/types/proposal.rs:493-495`), and the descendant probe is disabled in production (`core/src/background_children.rs:13-45`). A live, progressing child process (with a `progress.json` the worker was reading) carries no weight, so a wait is purely a time grant.
5. **(Verified) Teardown orphaned live work and mislabelled it.** On failure the engine reaped the pane and released the cube lease with `cause=proven_completed` while `node evaluate.ts --spend-cap 200` was still running in `isse-agent-004`. Nothing checks for or stops child processes. The workspace can now be re-leased to another task with a paid job still writing into it. The replacement execution (05:46:27, manual start) landed in `isse-agent-002` and cannot see the eval's outputs.
6. **(Verified) "No automatic replacement will be started" leaves work stranded.** PR #86 is open with a verified head, but the task went to `blocked/worker_failed` and the PR is no longer bound to the execution (`work_executions.pr_url` is empty). A human had to restart the task, and the restart spun up a fresh worker that does not know about PR #86 or the running eval. **Inference:** this is likely to produce a duplicate PR or a duplicate paid run; the new execution's behaviour was not inspected.
7. **(Inference) Sweep-driven nudges arrive immediately at wait expiry.** Nudges 2 and 3 came 2 s and 48 s after expiry. A worker whose job is still running has no way to absorb a nudge other than declaring another wait, which consumes budget, so every expiry costs a rung of the ladder.
8. **(Minor, verified) Misleading `work_runs.finished_at`** (§3.2). Not causal.

## 7. Recommended fix direction

Root-cause fixes only. Do **not**:

- raise `DEFAULT_MAX_UNPRODUCTIVE_NUDGES` or the 4 h cap;
- exclude isse or eval tasks;
- suppress the breaker message;
- special-case this execution.

Instead:

1. **Make intent replay current-state-driven.** `recheck_background_nudge` must re-derive the nudge decision (PR state, staged PR URL, run*done horizon) from current engine state before calling `nudge_or_park`, rather than replaying the captured fingerprint and `bound_pr_url`. Equivalently, the staged-PR / `await_run_done_declaration` paths (`completion/src/stop.rs:829-836`, `completion/src/recheck.rs:117-120`) must retire any retained produce-a-PR intent and reset the `no_pr` breaker entry the moment a PR is staged and verified for the execution. A staged, verified PR on the execution's branch \_is* the progress that fingerprint exists to detect. Add a regression test with this sequence: wait expiry → three sweep nudges → staged PR → quiet sweep must yield `AwaitingRunDoneDeclaration`, never `NudgeBreakerParked`.
2. **Make the breaker's failure text truthful.** Compute the PR clause from current state (staged or bound PR URL) at trip time, not from the replayed argument. A breaker should never assert "No PR was produced" while `pr_url_capture` holds a verified URL.
3. **Encode real work state in the no-PR fingerprint.** Include the execution bookmark's head commit or change id and the working-copy diff hash, so committed or changed work resets the ladder, as the `nudge_breaker` module doc already promises.
4. **Give waits a liveness basis instead of a pure time budget.** Make `--waiting-on pid:<n>` (or a harness background-task id) something the engine actually watches. While the named process is alive and owned by the worker's process tree, or its declared progress file advances, the wait stays valid, with a bounded staleness check rather than a fixed 4 h lifetime grant. This is the "driver/harness-owned delegated-work signal" the `completion/src/background_children.rs` module doc already calls for. Also charge waits by elapsed time, not granted time, so early wakes do not burn budget.
5. **Never release a lease as `proven_completed` while worker-spawned processes are alive in the workspace.** Either terminate the process tree on failure, or keep the workspace pinned and surface the orphan. The failure notice should name the PR and the live process so a restart resumes them instead of starting fresh.
6. **Tell the worker the real budget.** State the 4 h cumulative cap and the remaining budget in the brief, in the nudge, and in every accepted `propose wait` response. Document the sanctioned path when a job will outlive the budget (for example `propose done --outcome blocked` asking for a manual hold).

## 9. Lessons

- A cached decision replayed later is a claim about the past. Any path that acts on it (here, failing an execution) must re-check the facts it depends on against current state.
- A progress fingerprint that cannot change except through the one outcome being waited for is not a progress check; it is a countdown.
- A time budget is a poor proxy for "the worker is still doing useful work" when the engine has no way to see that work. If the only legal response to a budget running out is to ship early or be failed, the budget will force early ships.
