# Incident 010 — Focus-blind review admission let out-of-focus PRs take every pre-merge review reservation

- **Date:** 2026-11-03 UTC (evening of 2026-11-02 into early 2026-11-03 in the host's local zone, CST, UTC−06:00). All timeline times below are **UTC**.
- **Impact:** With dispatch focus mode active, the pre-merge automated review pipeline for in-focus work stalled. Four pre-merge review batches for **out-of-focus** PRs (spinyfin/mono#3290, #3441, #3442, brianduff/appoint#170) were admitted and held all 16 review-pool reservation units, while focus mode guaranteed none of their reviewers would ever dispatch. Two in-focus PRs (spinyfin/mono#3443, #3445) were deferred with "waiting for a review-pool slot" and could not be reviewed until the session driving the response changed the focus set by hand. User-visible deferrals were 18.6 min (#3443) and 24.1 min (#3445). The underlying condition is worse than those numbers: from 04:35 onward three never-runnable batches held 12 of the 16 units, so in-focus pre-merge review was serialised to **one batch at a time**, and that was still the case when the evidence snapshot was taken at 06:34:39. A post-merge safety-net review (spinyfin/mono#3405) was also held by focus from 04:51 with no signal at all. The repo owner considers this a catastrophe because focus mode cannot be turned off for the Boss work that needs it.
- **Status:** Not fixed. Mitigated by hand for the two PRs named above (see timeline). The defects described here are present on `main` at the source baseline. A fix for focus-aware admission was started at 06:17. This document changes no code; see §7 and §8.
- **Provenance:** Two read-only snapshots of the engine database (06:10:38 and 06:34:39) — `pr_review_batches`, `pr_review_batch_members`, `work_executions`, `work_attention_items`, `tasks`, `metadata`; the engine's text log and JSONL trace filtered to review / admission / reservation / focus lines; the tool audit of the session driving the response; GitHub (`gh pr view`); and source inspection.
- **Source baseline:** `spinyfin/mono` `main` at `0a701e98f677` (2026-11-03 04:45Z). All `path:line` references refer to this revision. Engine paths are relative to `tools/boss/engine/` unless they start with `tools/`.

## 1. Summary

Pre-merge review admission is a static reservation scheme: every non-terminal pre-merge batch holds a fixed block of 4 units from creation until its supervisor finishes, against a capacity of 16, so at most four pre-merge batches can exist at once. Dispatch focus mode (merged in spinyfin/mono#3436 at 22:45:57 on 2026-11-02 and switched on for the first time at 00:08:55) is a gate in the dispatcher only: out-of-scope `ready` executions are held with the `focus_mode` wait reason. The two mechanisms never consult each other. Admission happily creates a batch for an out-of-focus PR and charges it 4 units; the dispatcher then holds that batch's reviewers indefinitely; the batch never completes, so its block is never returned; and the inert-batch reaper correctly (by its own definition) refuses to reap a batch whose members are live and `ready`.

Three out-of-focus standalone Boss tasks accumulated blocks over the night (#3290 at 00:14, #3441 at 04:01, #3442 at 04:35). An in-focus PR (#3443) used the last free block at 05:28 and released it at 05:36; an out-of-focus appoint PR (#170) took it at 05:44. From then on every unit was held by work focus would never run, and every in-focus PR that finished a revision was deferred.

The session driving the response unblocked #3443 by adding the appoint product to the focus set (which let #170's reviewers run and free a block). Its second attempt — cancelling #3290's two never-started reviewer executions to make the reaper release that batch — did not work: the dead-member recovery sweep treats a deliberate manual cancel exactly like a host death and minted attempt-2 reviewers, still focus-held, so #3290 kept its block and two misleading "Automated review died without findings — auto-refired" attentions were filed. #3445 was finally admitted at 06:33:50 on the block freed by #3443's own batch completing, not by anything the cancel did.

### Verdict

The root cause is that **review admission and dispatch disagree about what may run**: admission reserves pool capacity for work the dispatch gate has already decided not to run. Contributing factors are the fixed-block reservation model (a batch holds its whole block from creation, before any reviewer has started), a recovery sweep that cannot tell a manual cancel from a crash, no verb to fail or release a whole review batch, an unfixed prior bug in the same family, and a deferral message that promises a release that cannot happen while focus is unchanged.

### 3.1 Why each holding batch was admitted despite focus

Nothing on the admission path reads the focus set. `create_pre_merge_review_batch_for_pool` checks only "already reviewed at this head" and the reservation arithmetic (`work-db/src/review_batches.rs:1425-1451`); `can_admit_review_batch_in_tx` (`:276-290`) compares reserved units to capacity; `reserved_batch_count_in_tx` (`:226-239`) counts open batches with a live root. The focus verdict is computed only inside `drain_ready_queue` (`dispatch/src/coordinator/scheduler.rs:1092-1118`) and applied per row at `:1244-1253`. So #3290, #3441, #3442 and appoint#170 were admitted because they were the next producer to ask while a block was free. Focus played no part.

## 4. Why cancelling #3290's reviewers produced a retry and not a release

1. `handle_cancel_execution` (`core/src/app/executions.rs:917-1010`) cancels the execution, writes an audit event and force-releases any run or lease. It does not touch the batch or the batch member, so the member stays `pending` and the batch stays `collecting`.
2. The PR-review recovery loop runs every 60 s (`core/src/app/server.rs:2295-2305`). Its batch-member candidate query `list_dead_review_batch_member_candidates` (`work-db/src/review_batches.rs:1772-1813`) selects pre-merge leaf members at `attempt < 2` with no attempt-2 row, whose execution status is in `('orphaned', 'abandoned', 'failed', 'cancelled')` (`:1798`). **A deliberate manual cancel is in the same bucket as a host death.**
3. `pr_review_recovery::run_one_pass` (`core/src/pr_review_recovery.rs:158`, `:333`) calls `retry_dead_review_batch_member` (`work-db/src/review_batches.rs:1870-1937`). That marks the attempt-1 member `failed` (`:1882-1886`), and because `attempt < 2` and no retry exists, inserts a fresh `ready` `pr_review` execution and an attempt-2 member (`:1910-1935`). It then files `pr_review_died_without_findings` ("auto-refired").
4. The reaper deliberately stands aside while that is possible. `reap_inert_review_batches` (`work-db/src/review_batches.rs:2045-2099`) skips any batch with a non-terminal member execution (`:2062-2069`) **or** with a retryable dead attempt-1 leaf (`:2070-2085`). Its stale branch also needs `updated_at` older than `REVIEW_BATCH_STALE_SECS` (10 min, `:103`), which the retry insert resets.

The attempt-2 reviewers are scoped to the same out-of-focus root, so they are held `focus_mode` and the batch is exactly as stuck as before, with two false "died" attentions added.

**Inference (not exercised):** cancelling the attempt-2 executions as well would have released the block. At `attempt >= 2`, `retry_dead_review_batch_member` stamps the member failed and runs `try_advance_review_batch_quorum_in_tx` (`:1888-1898`). With both leaf roles settled failed, that should report `InsufficientQuorum` and fail the batch, which drops it from `reserved_batch_count_in_tx`. That "escape hatch" means destroying a review, filing two more misleading attentions and a batch-failed attention, and knowing the retry internals. It is not a usable tool.

## 5. Root cause and contributing factors

### 5.1 Root cause: admission is blind to the dispatch focus gate

Admission (`work-db/src/review_batches.rs:226-286`, `:1439-1451`) and dispatch (`dispatch/src/coordinator/scheduler.rs:1092-1118`, `:1244-1253`; scope rule `work-db/src/dispatch_focus.rs:1-28`, `:300`) make independent decisions about the same work. Admission reserves capacity for a batch; dispatch then refuses, by design and indefinitely, to run that batch's reviewers. The focus design is explicit that out-of-scope reviews are "held, not skipped" (`tools/boss/docs/dispatch-focus-mode.md:19`, `:33`) and that holding is harmless because "rows are held, never dropped". That is true for a plain `ready` row. It is false for a review row whose batch owns a fixed share of a shared, capped resource. The focus change did not consider the reservation scheme, and the reservation scheme assumes every admitted batch will make progress.

The result is a **priority inversion**: the more out-of-focus work finishes an implementation run while focus is on, the less review capacity the in-focus work has, down to zero.

### 5.2 Fixed-block reservations held by never-started batches

A pre-merge batch takes all 4 units at creation (`PRE_MERGE_BATCH_RESERVATION_UNITS`, `work-db/src/review_batches.rs:212`; capacity `DEFAULT_REVIEW_POOL_SIZE` 16, `storage-values/src/pool_policy.rs:23`) and keeps them "even while some of its member executions are still queued" (doc comment `:262-268`). The design reason is sound — a batch's supervisor must never be starved by a later batch's leaves — but nothing ties the reservation to the batch actually being able to run. #3290 held 25% of review capacity for 6 h 20 m without a single reviewer process.

### 5.3 Reaper semantics

`reap_inert_review_batches` reaps only batches that can never settle: root deleted, pre-merge root done/archived, or stale with no live member and no retryable dead leaf (`work-db/src/review_batches.rs:2031-2085`). A focus-held batch has a live root and `ready` members, so it is not "inert" in that sense. That is the reaper doing its job: these batches are **starved**, not orphaned, and age-based reaping would be wrong (it would destroy review of work that is merely out of focus for now).

### 5.4 Recovery cannot tell a manual cancel from a crash

`cancelled` is in the dead-status list for retry (`:1798`, `:1847`) and for the reaper's "retryable dead leaf" exclusion (`:2083`). A deliberate queued-only cancel of a never-started reviewer is therefore re-queued within a minute and reported as a review that "died without findings". The cancel reason ("free review-pool place … re-queue review later") was recorded and ignored.

### 5.5 No manual escape hatch

- `bossctl review` has only `start` and `show` (`tools/boss/bossctl/src/review.rs`). There is no verb to fail, cancel or release a review batch, or to list which batches hold reservations and why their members are waiting.
- `bossctl agents launch` (`force_dispatch`), the documented focus bypass (`tools/boss/docs/dispatch-focus-mode.md:44`), takes a task and launches its next implementation run. It cannot launch one specific `ready` review execution. So there was no way to say "run #3290's reviewers now, once, without widening focus".
- The only working lever was widening focus to a holder's product, which is what the repo owner built focus mode to avoid. For the three standalone Boss tasks, that lever means putting the whole Boss product in focus.

### 5.6 Post-merge accounting is not involved, and is itself dead

`reserved_batch_count_in_tx` excludes batches whose root is `done`/`archived` for every phase (`work-db/src/review_batches.rs:230-236`). Post-merge roots are `done` by construction (the reaper's own comment, `:2033-2037`). So post-merge batches always count zero. They did not take any pre-merge units here, and post-merge admission (`:1511-1517`) is gated only by pre-merge units. The consequence today was different: the #3405 post-merge reviewer sat focus-held from 04:51 with no reservation pressure and no attention, so nothing anywhere said that a safety-net review was not running.

### 5.7 Global dispatch pause does not cause the same inversion

The pause gate runs before the focus gate (`dispatch/src/coordinator/scheduler.rs:961-1089`). Under the default `new_work` pause, review executions are exempt and keep draining (`:966-976`, `:1064-1076`), so admitted batches progress. Under an `all_spawns` pause, every row including reviews is held (`:1077-1088`), so admitted batches sit unstarted and hold their blocks. Because _nothing_ dispatches, though, no in-scope work is starved relative to out-of-scope work, and normal order resumes on unpause. Admission is pause-blind too, so an `all_spawns` pause over-admits up to four batches, but that is not an inversion. Focus is the first gate that holds a **subset** of review rows indefinitely while the rest keep flowing, and that is what turns blind admission into starvation.

### 5.8 Prior bug in the same family left unfixed

A bug filed 2026-10-11, "Review batch with never-started members holds a review-pool reservation for 6 days; stale-batch reaper skips it", described brianduff/flunge#1757's pre-merge batch. The DB shows that batch created 2026-10-05 16:30:48 and not completed until 2026-10-14 18:01:05. Its attempt-1 executions were marked failed at 16:32:20 without ever starting, while the members stayed `pending` until 2026-10-14 17:55. That is **9 days** holding 4 of 16 units. The mechanism differs (member/execution status divergence, not focus), but the class is identical: **a reservation is held by a batch whose reviewers are not running, and nothing releases it.** Fixing that class generally — tying a reservation to a batch that can make progress — would have covered today's case.

### 5.9 The deferral message promises something false

`file_admission_deferred_attention` (`observation-contracts/src/lib.rs:771-778`) says "The review starts once a batch completes and the deferred-admission sweep retries." Under focus, the holding batches could not complete, so the review would never start. The message does not name the holders or say they are held by focus, so the reader has no way to tell "the pool is busy" (self-resolving) from "the pool is wedged" (needs action). The deferred-admission sweep also orders candidates by `t.updated_at ASC` (`work-db/src/pr_flow.rs:1047`) with no regard to focus. When a block frees, an out-of-focus producer can take it as easily as an in-focus one, which is exactly how appoint#170 took the block #3443 released at 05:36.

## 6. How long has this existed? (history check)

- **Focus-blind starvation specifically could not occur before this incident.** Focus mode merged at 22:45:57 on 2026-11-02 and was first activated at 00:08:55 on 2026-11-03. The exposure began at 00:14:12, when the first out-of-focus batch (#3290) was admitted. Pool saturation by focus-held batches lasted 05:44:56–06:23:54 (39 min, all 16 units), and 12/16 units have been held since 04:35:05 (still true at 06:34:39).
- **Today's user-visible waits:** #3443 deferred 18 m 37 s, #3445 24 m 08 s, appoint#170 (second head) deferred from 06:31:29 and still waiting at the snapshot. Without the manual focus change, #3443 and #3445 would have waited until focus was cleared or widened. Their wait had no natural upper bound.
- **The broader reservation-starvation class is older.** There were 241 `pr_review_admission_deferred` attentions from 2026-09-10 to 2026-11-03. For each one, I measured the wait as the time until the next pre-merge batch for the same root. That is an upper bound, because the root may have left review in the meantime. I then checked which open pre-merge batches at the deferral time had no started reviewer:
  - **2026-10-05 → 2026-10-14:** flunge#1757's never-started batch held a block throughout (74 h–147 h old at the deferrals sampled). Deferrals in that window waited up to 165 min (Oct 8), 130 / 1211 / 1249 min (Oct 10) and 134 min (Oct 11). These are prior occurrences of the same class, with roughly a quarter of capacity lost for 9 days.
  - **September and late October:** most long deferrals coincide with four batches whose reviewers _were_ running, or with holders less than an hour old (normal queueing behind a busy pool). They are capacity saturation, not starvation, and I do not attribute them to this defect.
  - Several attentions are still `open` weeks later (for example 2026-09-13, 2026-10-09). This looks like attention-resolution leakage when a task leaves review by another path. It is not evidence of a stuck review, and I did not investigate it further.

## 7. Fix direction

Root-cause fixes only. **Out of scope by name:** raising the review-pool size or `BOSS_REVIEW_POOL_SIZE`; lowering the per-batch reservation weight; age-based reaping of non-inert batches; excluding specific PRs, products or tasks from review; exempting reviews from focus; and rewording the deferral attention as the only change.

1. **Make admission and dispatch agree on scope (primary).** Admission should ask the same scope question the dispatcher asks (`executions_outside_dispatch_focus` / the scope rule in `work-db/src/dispatch_focus.rs`). When focus is active and the batch's cycle root is out of scope, return `AdmissionDeferred` (with a distinct reason) and keep the producing task in the existing deferred-admission hold. It is then admitted by the normal sweep when focus is cleared or widened to cover it. Fail closed in the same direction the dispatcher does: if scope cannot be resolved, do not admit.
2. **Un-admit already-admitted out-of-scope batches when focus narrows or activates.** In `handle_update_dispatch_focus` (`core/src/app/dispatch_focus.rs:126`), or in the sweep that observes the new focus set, take every open pre-merge batch whose root is now out of scope and **none of whose members has ever started**. Retire its unstarted reviewer executions _without_ routing through dead-review recovery, mark the batch so it releases its reservation, and return the producer to the deferred-admission hold. Batches with a started member keep their block and finish. This is the step that would have released #3290, #3441 and #3442 at 06:23 and on every earlier focus change.
3. **Focus-aware ordering in the deferred-admission sweep.** When a block frees, admit in-scope candidates first (`work-db/src/pr_flow.rs:1047` currently orders by `updated_at` only). With (1) in place this mostly falls out, but the sweep should state the rule explicitly.
4. **Tie reservations to a batch that can make progress, generally.** (1) and (2) cover focus. The flunge#1757 class shows the same failure without focus, so the reservation invariant should be "held by a batch that is running or able to run", enforced where a batch's members become permanently non-dispatchable or diverge from their executions. That is not age-based reaping. Close the 2026-10-11 bug against this fix rather than separately.
5. **Distinguish a manual cancel from death in review recovery.** A queued-only, explicitly reasoned cancel of a batch member should not be in the `('orphaned', 'abandoned', 'failed', 'cancelled')` retry bucket (`work-db/src/review_batches.rs:1798`, `:1847`, `:2083`) and should not file `pr_review_died_without_findings`. Either reject member-level cancels with a pointer to a batch-level verb (below), or treat them as a deliberate batch abandonment that releases the reservation.
6. **Truthful deferral signal.** When admission defers, name the batches holding the reservation and why their reviewers are waiting (`focus_mode`, `dispatch_paused`, running). Drop "starts once a batch completes" when no holder can complete. This is a companion to (1)–(2), not a substitute.
7. **Decide post-merge accounting explicitly.** Either count post-merge reservations (and change the done-root exclusion for that phase), or delete the dead post-merge arithmetic and document that post-merge reviews are unreserved. Also surface a focus-held post-merge review somewhere, since today it waits silently.

### Tooling gaps

- `bossctl review batches` (read): list open batches with phase, PR, reserved units, age, each member's execution status and dispatch wait reason, and whether any member has started. That answers "who holds the pool and why" without opening the DB.
- `bossctl review release <batch|pr>` (write, confirmed): fail or abandon a whole batch, retire its unstarted reviewers without triggering recovery, release the reservation, and return the producer to deferred admission.
- A per-execution force-dispatch for review rows, or `bossctl review start --pr N --force`, that runs one held batch's reviewers once through focus, as `agents launch` does for implementation runs.

## 9. Lessons

- **A gate that holds work must be reconciled with every resource that work has already claimed.** Focus mode was designed as "admission gate and nothing else; held, never dropped". That is safe only for rows that hold nothing. A review row inherits a reservation from its batch, so holding it holds the reservation. Any new dispatch gate (focus, per-host, per-product caps) needs a check against review reservations, worker slots and workspace leases before it ships.
- **Static reservation needs a progress invariant.** "Reserve from creation until completion" is correct only if completion is reachable. The 2026-10-11 bug was a warning that it is not always reachable. It was filed as one PR's anomaly rather than as an invariant failure, and was left open.
- **Recovery that treats every terminal status as a crash fights the person driving it.** The cancel was the right instinct with the wrong tool. Recovery sweeps should honour explicit human intent, and the system should give people a batch-level verb so they do not have to reverse-engineer retry internals mid-incident.
- **Diagnose before you act on the escape hatch.** The response session's cancel and its "move the fix into a focused project" suggestion both rested on unverified assumptions: that the reaper would release the batch, and that being in focus creates admission capacity. Reading `retry_dead_review_batch_member` and `reap_inert_review_batches` first would have ruled out both. The one effective action, widening focus for appoint, came from correctly identifying which holder could be made runnable.
- **User-facing waiting messages must be conditional on the wait being able to end.** "Starts once a batch completes" was false for the whole incident, and nothing else said so.
