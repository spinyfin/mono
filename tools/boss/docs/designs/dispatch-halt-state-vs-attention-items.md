# Boss: dispatch/execution halt state does not belong in attention items

- **Status:** shipped for active-task churn and deliberate parks — see PRs mono#2742 and mono#2964.
- **Prompted by:** a churn-guard park being invisible on the kanban board — the card sits in Doing looking normal while nothing runs, and the only way to find it was the CLI. Rendering attention items on cards was considered and rejected: it would have made the wrong representation load-bearing rather than fixing it.
- **Code:** `tools/boss/engine/core/src/attention_lifecycle.rs` (the kind registry this doc classifies), `tools/boss/engine/core/src/orphan_sweep.rs`, `tools/boss/engine/core/src/work/dispatch.rs` (`bounce_dispatch_failed_to_backlog`), `tools/boss/app-macos/Sources/WorkBoardBanners.swift` (`WorkDispatchFailureBanner`).

## The rule

`work_attention_items` (design: `attentions.md` — a different, older store than the `Attention`/`AttentionGroup` question/followup feature that doc describes) is documented as being for "engine-raised operational alerts" in general. In practice a narrower rule is the one that matters for _this_ failure mode, and is the one this doc adopts going forward:

> **An attention item is for something a human must decide about — the work, the deliverable, or an engine action that needs sign-off. It is not for state the engine can describe and re-describe itself: "I stopped trying to dispatch this," "a worker pane died," "a queue is stalled." That second category is dispatch/execution _mechanics_, and the kanban board must be able to show it without ever reading the attentions table — it needs a dedicated, typed field the UI reads directly, the same way `Task.dispatch_failed_reason` / `dispatch_failed_error` / `dispatch_failed_at` already drive the card's red "Failed to start" banner.**

The test to apply to a candidate kind: _if every open instance of this kind vanished right now, would the board still correctly show what's going on?_ For `churn_guard_parked` the answer was no — the card looked identical to a healthy Doing card. That is the signature of the defect, not "attention items are read from the wrong screen."

Attention items remain the right mechanism whenever the honest answer to "what closes this?" is `ClearedBy::HumanDecision` or `ClearedBy::ProducerReconciles` _and_ the thing being decided is about the work or an engine action needing sign-off, not about whether the dispatcher is currently able to run something.

## Shipped halt surfaces

`churn_guard_parked` (filed by `orphan_sweep` when an `active` work item accumulates too many terminal executions in the trailing window) moves off `work_attention_items` entirely. It now goes through the same mechanism a pre-spawn dispatch failure already uses: `WorkDb::bounce_dispatch_failed_to_backlog(work_item_id, "churn_guard", body)`. See the code comment on that call site in `orphan_sweep.rs` for the exact tradeoffs (status change, retry cadence).

`pr_review_recovery` retains the _same_ `churn_guard_parked` attention kind. It guards a `pr_review` execution for a task under active review, where "Backlog" is not a meaningful destination (the task has an open PR under active review); it needs its own board-surfacing design, not a copy-paste of the active-task fix.

### Deliberate parks and attention coexistence

For `run_done_declared_blocked` and `nudge_breaker_tripped`, the sweep retains the open attention item as the decision record and separately moves the task to Backlog with `dispatch_failed_reason = deliberate_park`. Both liveness guards run before this write, even when dispatch is paused or all worker slots are busy. This write never mints an execution. The blue Waiting on you banner names deliberate park and, when present, churn guard; its visible summary tells the user to review the attention item and drag to Doing to resume. Detailed execution diagnostics remain available on hover.

Unlike a churn-only halt, a deliberate park is excluded from automatic dispatch-failure recovery. An explicit work start or drag to Doing starts a fresh run, clears the halt stamp, and resolves the attention through `ClearedBy::WorkResumed`. The two surfaces coexist because the attention records the decision needed while the typed field makes the stopped state visible on the board. A combined park and churn trip retains the deliberate-park reason and its explicit-resume requirement.

### Cancelled executions

A cancel is a stop-until-asked decision — `bossctl agents stop`, `bossctl executions cancel`, the app's cancel, a kanban drag back to Backlog, or an engine transition that deliberately ended the run. It goes through the same surface: when the row is `todo`, the cancelled execution is its latest and no other non-terminal execution exists, the cancel itself (`park_work_item_after_cancel`, called from every `WorkDb` cancel path) moves the row to Backlog with `dispatch_failed_reason = execution_cancelled`, `autostart = 0`, and a body naming the execution, who cancelled it (`CancelActor`: `human` for an operator action, `engine` for a lifecycle transition), the cancel reason the caller supplied, and the resume instruction. The card renders it as the grey "Stopped — execution cancelled" banner; `boss task show` / `bossctl agents status` print "Stopped: execution cancelled". Like a deliberate park it is excluded from `dispatch_failure_recovery_sweep`; only an explicit `bossctl work start` or drag-to-Doing resumes it, and the fresh run clears the stamp.

Before this, a never-started execution that was cancelled (mid-spawn, or a queued row cancelled explicitly) left its row `todo` with `autostart = 1` and nothing queued: `reconcile_work_item_execution` never mints behind a terminal same-kind execution, so the kanban showed the row in Doing as "Queued — reason unknown" indefinitely. Two companions close the remaining gaps:

- **Convergence of already-stranded rows.** The reconciler now handles a `todo` + `autostart` row whose latest execution is terminal and has no live sibling (`converge_stranded_autostart_row`). If that execution was cancelled before it ever started, the row is parked under `execution_cancelled` with a body that says the cancel reason was not recorded at the time, and a `warn` names the row and execution. Otherwise `autostart = 1` behind an execution that ran means the row was re-armed after it ended (`start_execution_run` consumes the flag), so a replacement is minted.
- **An engine-stated hold reason.** `TaskRuntime.dispatch_hold_reason` says why a dispatch-pending row has nothing queued, from the reconciler's own decline-to-mint gates (`human_driven`, `deferred`, `pr_awaits_review`, `deliberately_parked`, `repo_unresolved`) or `awaiting_reconcile`. The card maps each to a specific "Held — …" line; it never guesses, and "reason unknown" is gone.

An `active` row whose pending execution is cancelled is deliberately left `active` (a human put it in Doing; the orphan-active sweep re-dispatches it), and a live cancel is parked only after the existing `active → todo` demote. Callers that replace the execution in the same breath opt out with `CancelExecutionOpts::keep_work_item_schedulable` (the merge poller converting a merged revision, forced-dispatch residue cleanup) or `cancel_running_execution_for_requeue` (scheduler preemption).

**Cancel provenance** (`CancelActor` / `execution_cancelled_event` in `tools/boss/engine/core/src/work/executions_runs.rs`). Every cancel names its actor, and the same provenance lands on the execution's dispatch timeline: each app-level cancel site — the operator `CancelExecution` / `StopRun` RPCs, the drag-back and delete teardowns (`cancel_and_release`), `force_stop_execution`, the coordinator's requested-host cancels and forced-dispatch residue cleanup, scheduler preemption, and the merge poller's parent-PR-merged cancel — emits an `execution_cancelled` dispatch event with `actor`, `reason`, `prior_status` and `work_item_moved`. Before this only the merge poller did, so an operator reading `bossctl dispatch diagnose` for a stranded row saw a timeline that stopped at `pane_spawned` / `tmux_adopt` while the durable row said `cancelled`, with nothing saying who or why. A legacy stranded row the reconciler converges is parked with actor `unrecorded`, and its body says so rather than guessing.

### Bucket B — genuinely human-judgment-about-the-work (correctly attention items; no change needed)

`question`, `followup`, `deferred_scope`, `deletion_signoff` (`merge_parent_deletion`), `review_result_giveup`, `revision_no_op`, `mid_turn_reap`, `worker_escalation`, `worker_blocked`, `abandoned_branch_no_pr`, `revision_archived`, `ci_remediation_exhausted`, `answer_agent_stranded`, `unobserved_command` (+ `_overflow`), `external_tracker_removed_upstream`, `external_tracker_permission_denied`, `push_restriction`, `envelope_overrun`, `probe_undelivered`, `answer_agent_ready_age`, `external_tracker_auth_failed`, `external_tracker_token_revoked`, `external_tracker_transient_errors`.

Of particular note, since a sibling chore ("worker_blocked and worker_escalation attention items are unreachable from every read surface") depends on this classification: **`worker_escalation` and `worker_blocked` are correctly classified.** They are the `[effort-escalation]` / `[blocked]` Stop-boundary markers (`worker_escalation.rs`) — a worker explicitly asking a human/coordinator for a decision it cannot make alone. That is exactly the shape an attention item is for. The fix for that sibling chore should be "make the existing attention item reachable" (a genuine read-surface gap), not a representation change like this PR made for `churn_guard_parked`.

### Bucket C — attention item is the decision record; board reads a typed halt

These kinds stay on `work_attention_items` because the honest answer to "what closes this?" is a human decision about the work (`ClearedBy::WorkResumed`). They also need board-native state so the card does not sit in Doing looking healthy. Both halves shipped together in mono#2964: the sweep retains the open attention item and stamps `dispatch_failed_reason = deliberate_park`. One predicate (`DELIBERATE_PARK_ATTENTION_KINDS` / `work_item_is_deliberately_parked`) covers both kinds; they must not be split across buckets.

| kind                                                 | why both surfaces                                                                                       | confidence |
| ---------------------------------------------------- | ------------------------------------------------------------------------------------------------------- | ---------- |
| `run_done_declared_blocked`, `nudge_breaker_tripped` | typed halt coexists with the decision attention item; the board names the wait, the attention names why | high       |

## Migration for pre-existing open `churn_guard_parked` items

A one-shot data migration (`migrate_resolve_open_orphan_sweep_churn_guard_parked`, `tools/boss/engine/core/src/work/migrations_c.rs`) marks stale open `work_attention_items` rows with `kind = 'churn_guard_parked'` whose body text records `orphan_sweep` as the source (and whose target task is still `status = 'active'`) as `resolved`. It deliberately does **not** touch the task row — no `status`/`autostart` change, no write to `dispatch_failed_reason` / `dispatch_failed_error` / `dispatch_failed_at`. The pre-fix sweep filed its attention item before checking durable worker liveness, so an `active` task carrying one of these items can still have a live worker process after an engine restart; demoting that row to Backlog at startup would recreate the race the current guarded sweep avoids. The next guarded `orphan_sweep` pass re-parks genuinely orphaned work with fresh failure counts (and the new board-native `dispatch_failed_reason` representation). The source check matters because `pr_review_recovery` can also file this kind against an `active` task (`list_dead_pr_review_candidates` allows any status other than `done`/`archived`, not just `in_review`), so task status alone cannot tell the two sources apart; rows recording `pr_review_recovery` as their source are left untouched, since that path still uses the attention item.
