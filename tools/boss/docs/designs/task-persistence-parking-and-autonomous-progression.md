# Task persistence: explicit parking, and administrative progression agents for everything that is not parked

- **Date:** 2026-10-23
- **Provenance:** execution `exec_18e140c1186c8900_e8` (`project_design`), project "Task persistence: parking and autonomous progression"
- **Status:** design, awaiting review
- **Baseline:** origin `main` at `8c9ee8ee` ("Cache per-item board runtimes in work-tree assembly", mono#3265). Every `file:line` below is against that revision; paths are relative to the repo root.

- **Related operational contracts:** [attention-lifecycle](../attention-lifecycle.md), [worker-liveness-contract](../worker-liveness-contract.md), [post-crash-recovery](../post-crash-recovery.md), [execution-recovery-pointers](../execution-recovery-pointers.md)

**TL;DR.** Two mechanisms. **Parking** is a nullable set of columns on `tasks` and `projects` (`parked_at`, `parked_by`, `parked_reason`, `parked_via`) that is orthogonal to `status`: a parked row keeps its lifecycle position, disappears from the board's default view, and is skipped by every automatic dispatch and upkeep path through one shared predicate; un-parking runs a fixed reconciliation sequence built from the existing per-item probes. **Progression** is a new administrative execution kind, spawned by a sweep for any non-parked item that is in one of the enumerated stuck states and has no live work. A progression agent never writes to a repo. It diagnoses, then either creates work for coding agents (a revision on the item's own PR, or a precursor task the item depends on), performs a bounded set of taxonomy moves through an engine-enforced RPC tier, or asks the human one typed question that lands on the kanban's Needs Attention section **and** fires a macOS notification. The ladder ends in a human question after two attempts, never in silence. A new task status ledger and a "stuck" report measure the end-state claim and supply the traffic numbers that every cap in this design is set from.

**The contested property, up front:** _an item that is neither parked nor waiting on a human and has no live execution is a defect, and the engine will spend an agent on it._ A reviewer could reasonably object that this converts "quietly waiting" into agent spend and into questions the owner must answer. The design accepts that trade because the alternative, the owner personally noticing and investigating stuck items, is the cost the project exists to remove; the bandwidth section bounds the spend, and the parking mechanism is how the owner opts an item out.

## Goals

- The owner can park a task, chore, or whole project with one gesture; a parked item leaves the default board, is easy to find under a "Parked" filter, and is easy to un-park.
- Parked items atrophy by design: no CI-fix revisions, no conflict-resolution revisions, no AI review, no speculative rebases, no re-dispatch, no nudges. Facts about them (a PR merged by hand, a PR closed) are still recorded.
- Un-parking reconciles the item before normal work resumes: PR state refreshed, conflicts and red CI routed into the existing remediation paths, stale halt stamps cleared, dispatch eligibility re-derived.
- Every non-parked, non-terminal item that is not being actively worked, in any sense the engine already has a word for (coding, revision, AI review, CI fix, conflict resolution, waiting on a dependency that is itself live, waiting for a slot), gets an administrative agent whose only job is to progress it.
- Progression agents act through an explicitly scoped, engine-enforced surface. They can create revisions and precursor work, move an item along legal state transitions, change dependency edges in a bounded way, and ask the human. They cannot write to any repository, and they cannot do anything human-only.
- A question a progression agent forces reaches the owner on a channel the owner actually looks at and acts on, and is visibly distinct from routine status.
- When progression fails, the failure is recorded, surfaced, and escalated to a human question; nothing loops or gives up silently.
- The end state is measured: a report of items not progressing for longer than a threshold, bucketed by whether they are waiting on a human, on capacity, on a parked prerequisite, or on nothing at all. The last bucket is the number this project exists to drive to zero.

## Non-goals

- **Automatic parking by age, priority, or inactivity.** The owner parks things explicitly. Progression agents may _recommend_ parking in a question; they never park.
- **Progression agents that write code.** No repo checkout write path, no pushes, no PR edits, no GitHub comments. Everything that needs a diff becomes a revision or a task for a coding agent. (Amendment to the project brief, 2026-10-23.)
- **Replacing the deterministic sweep fleet or the existing remediation producers.** `ci_watch`, `conflict_watch`, `pr_review_recovery`, `orphan_sweep`, `dep_unblock_sweep` and the rest keep their jobs. Progression is the judgment layer above them for the residue they flag but cannot resolve.
- **Building Boothby.** [boothby.md](boothby.md) describes an install-wide groundskeeper with a journal, undo, and transcript mining. Only its first task shipped (`tools/boss/engine/core/src/work/boothby.rs`, the pre-image capture; no scheduler, session, or executor exists in `engine/core/src`). This design does not depend on Boothby, and it does not finish Boothby; the overlap is discussed under Alternatives.
- **Keeping the asking agent alive while the human decides.** Progression questions use the terminate-and-restart shape the operator chose in the Needs Attention design.
- **A general notification system** (digests, Slack, email). The channel added here is the minimum that reaches the owner for a forced decision; what exists and does not exist is catalogued below.
- **Changing what `deferred`, `human_driven`, `autostart`, or `archived` mean.** Each is a recorded decision with its own consumers; parking is a new, orthogonal dimension. Whether `deferred` should later fold into parking is an open question, not a v1 change.
- **Hub-and-spoke scheduling.** Progression runs on the local engine like every other execution; remote placement is the distributed-engine project's concern.

## Background: what exists today

Facts the design builds on, cited so reviewers do not have to re-derive them. The stuck-state enumeration is its own section below.

### Lifecycle vocabulary

- Task statuses are `todo | active | blocked | in_review | done | archived` (`tools/boss/protocol/src/types/task.rs:32-45`); `done`/`archived` are terminal (`:55-57`), `active`/`in_review` are "live" (`:68-70`). The board labels `todo` as Backlog and `active` as Doing (`:77-86`).
- Project statuses are `planned | active | blocked | done | archived` (`tools/boss/protocol/src/types/project.rs:49-55`). Projects already carry `last_status_actor` with the values `human | boss | engine | boothby` and a `status_basis` (`:93-130`), and a transition ledger, `project_property_audit` (`tools/boss/engine/core/src/work/schema_baseline.rs:654-662`, written by `record_project_status_audit`, `work/audit_misc.rs:19-31`). **Tasks have no equivalent ledger**: no `status_changed_at`, no `blocked_since`, no history table. `Task` carries `created_at`, `updated_at` (re-stamped by any mutation), `completed_at` (`task.rs:825-834`), `archived_at` (`:748-766`), `dispatch_failed_at` (`:1239-1241`) and the PR poll timestamps, nothing else about when a status was entered.
- Execution kinds are enumerated at `tools/boss/protocol/src/types/execution.rs:44-80`: `answer_agent, automation_triage, chore_implementation, ci_remediation, conflict_resolution, investigation_implementation, pr_review, pr_review_guide, product_design, project_design, revision_implementation, task_implementation`. `is_read_only_review` (`:84-86`) marks the two kinds that never write to a PR branch and are therefore exempt from per-PR writer serialization.
- Three per-row flags already gate dispatch without being a status: `autostart` (one-shot timing pause, `task.rs:562-569`), `deferred` (durable "future scope": visible on the board with a "Future" badge, still auto-unblocked by the dependency cascade, never auto-dispatched, cleared as approval by an explicit `RequestExecution` or drag-to-Doing, `task.rs:571-592`), and `human_driven` (no agent may dispatch or close it, `task.rs:594-617`).
- The dispatch-eligibility predicate is `task_accepts_execution` (`tools/boss/engine/core/src/work/exec_status_helpers.rs:241-281`): it refuses `blocked_reason IN ('worker_failed', 'awaiting_operator_answer')`, soft-deleted rows, `done | archived | in_review`, and honours `autostart` while in `todo`. `blocked` is deliberately accepted so that dependency-gated rows can receive `waiting_dependency` executions.
- Engine-side halts that the board reads as typed fields rather than attention items: `dispatch_failed_reason | dispatch_failed_error | dispatch_failed_at` on `Task` (`task.rs:1217-1241`), with the values `churn_guard` and `deliberate_park` documented in [dispatch-halt-state-vs-attention-items](dispatch-halt-state-vs-attention-items.md) (shipped in mono#2742 and mono#2964). Note that the engine already uses the word "park" for `deliberate_park`: a run that declared itself blocked or tripped the nudge breaker. This design uses **parked** only for the owner's explicit decision, and refers to the engine state by its column value.

### Who may write what

- Every work-item write resolves a caller tier from socket-peer process ancestry: `RpcTier { User, AppOrBoss, BossOnly, Worker }` (`tools/boss/engine/core/src/app/trust.rs:61-66`), classified once per connection (`:68-76`). The write actor recorded in `last_status_actor` comes from the same resolution (`resolve_write_actor`, `tools/boss/engine/core/src/app/work_items.rs:27-36`), and the `critical` priority is refused to every non-human tier (`refuse_worker_critical_raise`, `:34`; [critical-priority](../critical-priority.md)).
- The worker tier's verb policy is an exhaustive deny-by-default match over every `FrontendRequest` in its own crate (`tools/boss/engine/worker-policy/src/lib.rs:1-36`). **Finding:** enforcement of that tier is behind the `worker_rpc_tier` feature flag, `default_enabled: false`; until it is on, "the mediation policy is enforced only by prompt text" (`tools/boss/engine/feature-flags/src/lib.rs:405-420`). Any agent whose purpose is to mutate taxonomy cannot rely on a flag that ships off; its tier has to be enforced unconditionally.
- Capability-restricted spawn already exists as a template. `WorkerKind { Standard, Reviewer, Triage, AnswerAgent }` (`tools/boss/engine/core/src/worker_setup.rs:106-131`); the answer agent runs with `--permission-mode dontAsk`, a `permissions.allow` allowlist, and a `permissions.deny` belt, assembled in `worker_setup` (`deny_rules`, `:1041`; `bossctl` is denied to every worker kind, `:1090-1124`) and documented in `tools/boss/engine/core/src/answer_agent.rs:14-32`, with exactly one allowlisted mutating command (`THREAD_REPLY_COMMAND`, `:53`).
- The coordinator agent is one Claude Code session in tmux (`tools/boss/engine/core/src/coordinator_tmux.rs:31`), prompted by `bossSystemPrompt` (`tools/boss/app-macos/Sources/Ghostty/BossPaneModel.swift:398`). It coordinates and delegates, never edits code (`:430-434`), and acts when the operator or a probe prompts it. **No autonomous unstick loop exists anywhere**: the automated unsticking today is the deterministic sweep fleet wired in `tools/boss/engine/core/src/app/server.rs::serve`, and Boothby's scheduler was designed but never built.

### How dispatch decides what runs

- One ready queue, sorted by `critical` first, then `DispatchClass ASC`, then `work_executions.priority DESC`, then `created_at`, in `WorkDb::list_ready_executions` (`tools/boss/engine/core/src/work/executions_runs.rs:677`, `ORDER BY` at `:703-705`). `DispatchClass` ranks merge-conflict revisions, then CI-fix revisions, then review-finding revisions, then other revisions, then everything else (`tools/boss/engine/core/src/work/dispatch_class.rs:44-50`). The task's `low | medium | high` priority is **not** in the sort; only `critical` is.
- Three pools: interactive (16 slots, `MAX_WORKER_POOL_SIZE`, `tools/boss/engine/core/src/coordinator.rs:190`), automation (8, `:196`), review (16, `:210`). Routing is `pool_for_execution` (`tools/boss/engine/core/src/coordinator/config.rs:872-904`): `PrReview`/`PrReviewGuide` to review, `AutomationTriage` and automation-sourced tasks to automation, everything else, including answer agents and every revision, to interactive.
- The interactive concurrency cap, `MAX_CONCURRENT_INTERACTIVE_WORKERS = 8` (`coordinator.rs:250`, runtime `bossctl dispatch concurrency`), is admission-only and is enforced in `drain_ready_queue` (`tools/boss/engine/core/src/coordinator/scheduler.rs:1221-1282`) by comparing the interactive pool's `busy_count()` (`coordinator.rs:1501`) against it. Automation spills into idle Lower Decks slots only in a second drain pass and is preemptible (`tools/boss/engine/core/src/dispatch_spillover.rs:1-30`).
- Dispatch pause has two origins, `Operator` and `Breaker` (`coordinator.rs:1832`), and one authority, `dispatch_hold_for` (`config.rs:627-707`): an operator pause holds every non-review, non-critical row; a breaker pause (3 distinct items failing to spawn within 300 s, `tools/boss/engine/core/src/spawn_health.rs:110-127`) holds everything except an operator-forced launch. Held rows get `dispatch_wait_reason = "dispatch_paused"` (`scheduler.rs:1014-1040`).
- Per-PR single writer: `resolve_chain_hold` (`scheduler.rs:678`) over `live_executions_elsewhere_in_chain` (`tools/boss/engine/core/src/work/dispatch.rs:1449,1573`), checked before the claim (`scheduler.rs:1389`), at the start of `schedule_execution` (`tools/boss/engine/core/src/coordinator/execution.rs:688-720`), and again after the lease (`:1385-1460`). A row held this way for 900 s files `chain_serialized_stall` (`coordinator.rs:347`). Read-only review kinds bypass the hold. `request_execution` reuses an existing live row instead of minting a second (`tools/boss/engine/core/src/work/dispatch_helpers.rs:1600-1650`), and `has_writer` in `work/revision_sequencing.rs` treats `claimed | running | waiting_human` as live.
- Churn guards, with their constants: orphan re-dispatch trips at 3 terminal executions in 3600 s or 3 consecutive without a `completed` run (`tools/boss/engine/core/src/work.rs:54,58,81`), evaluated in `orphan_sweep.rs:552-555` and applied by `bounce_churn_guard_parked_to_backlog` (`orphan_sweep.rs:832`; `work/workitems.rs:391`), stamping `dispatch_failed_reason = "churn_guard"` (`work.rs:130`) and `autostart = 0`. `dispatch_failure_recovery_sweep` (`tools/boss/engine/core/src/dispatch_failure_recovery_sweep.rs:1-75`, every 60 s) re-dispatches such rows after `DISPATCH_FAILURE_RECOVERY_MIN_AGE_SECS = 600` (`work.rs:297`), bounded by 5 recoveries per 24 h (`work.rs:304,307`), **re-applying the same window**, so a slow loop stays in Backlog until a run completes or an operator starts it; `deliberate_park` rows are never auto-retried. Pre-start failures retry at 5/15/45 s and then bounce (`coordinator.rs:323`); transient API errors resume at 30/120/300 s and then file `worker_recovery_exhausted` (`tools/boss/engine/transient-error/src/lib.rs:385-415`; `tools/boss/engine/core/src/transient_recovery.rs:132,139`); the nudge breaker parks after 3 unproductive nudges (`tools/boss/engine/core/src/nudge_breaker.rs:50,62,72`).
- Remediation producers: a CI failure creates a CI-fix revision (`maybe_spawn_ci_revision`, `tools/boss/engine/core/src/ci_watch.rs:~700`) within a per-PR budget (`products.ci_attempt_budget`, default 3, `tools/boss/engine/core/src/work/blocking.rs:714`), after which the row is `blocked: ci_failure_exhausted`; a merge conflict runs the ladder (`tools/boss/engine/core/src/conflict_ladder.rs`: deterministic resolver, engine rebase, small agent) and then a merge-conflict revision (`tools/boss/engine/core/src/conflict_watch.rs:1413`), with the fourth attempt in an hour pre-abandoned as `churn_threshold_exceeded` (`work.rs:43-49`). The `conflict_resolution` execution kind is legacy with no production creator. AI review is enqueued on PR push (`tools/boss/engine/core/src/completion/pr_transition.rs:271-303`), at most `DEFAULT_MAX_REVIEW_CYCLES = 3` (`tools/boss/engine/core/src/config.rs:40`), and re-fired by `pr_review_recovery.rs`, whose own churn guard parks the task via the attention kind `churn_guard_parked` while the task stays `in_review` (`:441-505`).
- What is measured today: `dispatch.queue_depth.*`, `dispatch.queue_oldest_wait_seconds.*`, `dispatch.completed` and the drain duration (`tools/boss/engine/core/src/dispatch_metrics.rs:19-58`), persisted every 30 s to `metrics_counter` / `metrics_gauge` and read with `bossctl metrics`; the dispatch event stream (`<state_root>/dispatch-events/current.jsonl`) with `bossctl dispatch stats` giving wait aggregates per defer reason and the 15-minute dispatch rate; `boss cost` for tokens. **There is no attempts-per-item counter and no stuck-duration measure**; both have to be derived from `work_executions` rows today.

## Stuck states: an enumeration of how an item stops progressing today

There is no single "stuck" state. An item stops progressing through one of four mechanisms: a `blocked` status with a specific `blocked_reason`; a Backlog bounce (`todo`, `autostart = 0`, `dispatch_failed_*` set); a task that stays `active` or `in_review` while an open attention row or a sweep exclusion gates re-dispatch; or an execution-level or global hold. Each has a different clearing contract. The table lists every shape found, what produces it, what exits it today, and what is left over ("residue") for a progression agent or a human. **Findings from the sweep (silence is not neutral):**

- The UI's product status picker offers "paused" (`tools/boss/app-macos/Sources/WorkFormSheets.swift:489`) and no engine code gives `'paused'` any meaning (`products.status` is free-form TEXT, `E/work/schema_baseline.rs:637`). A pause affordance was added without a decision about what it does.
- Live tasks inside an **archived project disappear from the board** because the visible-items loop iterates only visible projects (`tools/boss/app-macos/Sources/ChatViewModel+WorkLookups.swift:124-128`), while the engine keeps dispatching them. - `run_done_backstop.rs:56-60` still documents a parked run as "`waiting_human` with an attention item"; the code fails it to `worker_failed`. Doc drift to fix in Task 1's PR, which touches that path's ledger write.

## Alternatives considered

### A. Park by reusing an existing flag or status

Three existing fields look like parking: `deferred`, `autostart = false`, and `status = archived`.

- `deferred` was introduced as a **scope** classification ("filed now but explicitly not yet in scope to run", `task.rs:571-592`). It is cleared by an explicit `RequestExecution` or a drag to Doing as the approval, it only has meaning in `todo` (an `in_review` PR cannot be "not yet in scope"), it stays visible on the board by design, and projects have no equivalent. Parking must survive a dependency cascade, must apply to an `in_review` item with an open PR, must hide the row, and must apply to projects. Reusing `deferred` would redefine a field that `WorkBoardCard.swift:585-615`, the dependency cascade, and the explicit-dispatch path all consume with the scope meaning.
- `autostart = false` only gates the auto-dispatcher while the row is in `todo` (`exec_status_helpers.rs:276-281`); it does nothing for an `in_review` item's upkeep and is already written by the churn guard (`bounce_dispatch_failed_to_backlog`) as a failure stamp.
- `archived` is terminal (`task.rs:55-57`), carries provenance (`archived_by/at/reason`), excludes the row from every listing, and is the signal several sweeps treat as "this work is over" (e.g. `list_dead_pr_review_candidates` allows any status other than `done`/`archived`). Un-archiving is a status move that loses the prior status.

**Rejected.** Each of these is a recorded decision on a different dimension (scope, timing, lifecycle). Parking is an attention decision: "I am not spending attention or bandwidth on this, and neither should the engine, but its lifecycle position is correct." The checkable test: an `in_review` PR the owner wants to leave alone for a month is the central parking case, and none of the three fields can express it without lying about something else.

### B. Park as a new `TaskStatus::Parked`

A sixth status variant gives compile-time exhaustiveness: every status-keyed branch must say what it does with a parked row (`task.rs:25-28` explains that this is the enum's purpose).

**Rejected, narrowly.** A status cannot be orthogonal to the position it replaces: un-parking an `in_review` item would need a second field to remember that it was `in_review`, at which point the second field is the real state and `Parked` is a cache of "hidden". It also forces every exhaustive match on `ProjectStatus` to grow a variant, and several of those matches have real semantics (`is_live`, `can_still_change_pr`, the board routing). The orthogonal-column approach achieves the same exhaustiveness where it matters through one predicate consulted by the candidate-listing helpers, with a parameterised test asserting that each producer's listing excludes parked rows.

### C. Progression as a Boothby pass

[boothby.md](boothby.md) already proposes "unwedging stuck work" as part of an install-wide, 30-minute groundskeeper with a journal and undo, running at coordinator-plus privilege, defaulting to propose mode.

**Rejected as the vehicle, with the overlap named.** Boothby is install-wide and periodic; progression is per-item and event-shaped (an item becomes stuck, an agent is dispatched for _it_, with a brief about _it_). Boothby's catalogue is taxonomy hygiene plus log mining; progression's is unblocking. Boothby's default `propose` mode routes every action through an approval question, which is precisely the channel this design must keep for genuine decisions. And only Boothby's first task has shipped; making progression depend on nine more Boothby tasks puts the owner's stated pain behind an unrelated build-out. What _is_ reused: the `last_status_actor` convention (a new `progression` actor value, audited the same way `boothby` was), the per-verb autonomy/cap idea, the "never fight live work" guard, and the fingerprint-refusal idempotence rule. Whether Boothby's journal and undo should later cover progression actions is an open question; progression's actions are either already-reversible engine verbs (status moves, dependency edges) or produce ordinary work items (revisions, precursors) that have their own lifecycle, so v1 relies on the task status ledger and `created_via` provenance for its audit trail.

### D. Progression as more deterministic sweeps

Encode each stuck shape as a reconciler: a hidden-revision-blocked-while-CI-green sweep, an exhausted-CI-budget retrier, a mutual-block breaker.

**Partially adopted, mostly rejected.** Where a stuck shape has a mechanical, checkable resolution the design does put it in engine code (the un-park reconciliation sequence is exactly this, and the enumeration below flags two shapes that should become sweep fixes regardless of progression). But the project's own examples are judgment calls: "probably transient" churn, "which of these two blocking each other should give way", "is this precursor still needed". A threshold answers those badly in both directions, and every wrong answer is either lost work or a loop. The enumeration's residue column is the argument: for most entries, what exists today is a sweep that detects and a human who decides.

### E. Progression inside the coordinator session

Give the coordinator a standing instruction to find and unstick stuck items.

**Rejected** for the reasons [boothby.md](boothby.md) §A3 gives and one more: the coordinator is a human-paced chat whose output reaches the owner only when the owner is reading it; it stops when the session is closed; and the engine has no path that pushes a stuck item into it (there is no engine-to-coordinator-chat injection beyond the handoff inbox and a prompt-change nudge). The coordinator today learns about stuck items when the owner asks, which is the behaviour the project exists to end.

### F. Approval-gated creation of revisions and precursors

Per the amendment, the design must decide whether a progression agent's revisions and precursor tasks are created directly or need approval. The gated option: every such creation becomes an operator question.

**Rejected** on precedent and on purpose. Precedent: the engine already creates revisions autonomously on a CI failure, a merge conflict, and a review verdict (`ci_watch`, `conflict_watch`, `pr_review`), and nobody approves those individually; a progression-created revision is the same artefact with a better brief. Purpose: the design must keep the forced-question channel for decisions only a human can make; routing routine unblocks through it would train the owner to ignore it, which is the failure mode of the Notifications window. The chosen approach bounds direct creation instead: a per-item budget, a fingerprint rule that forbids repeating an action that did not work, and a hard cap of one open progression-created precursor per item.

## Chosen approach

### Part 1: Parking

#### 1.1 Data model

Four nullable columns on `tasks` and the same four on `projects`:

```sql
ALTER TABLE tasks    ADD COLUMN parked_at     TEXT;  -- epoch seconds as text; NULL → not parked
ALTER TABLE tasks    ADD COLUMN parked_by     TEXT;  -- status actor that parked: 'human' | 'boss'
ALTER TABLE tasks    ADD COLUMN parked_reason TEXT;  -- optional free text from the owner
ALTER TABLE tasks    ADD COLUMN parked_via    TEXT;  -- 'direct' | 'project:<project_id>'
ALTER TABLE projects ADD COLUMN parked_at     TEXT;
ALTER TABLE projects ADD COLUMN parked_by     TEXT;
ALTER TABLE projects ADD COLUMN parked_reason TEXT;
ALTER TABLE projects ADD COLUMN parked_via    TEXT;  -- always 'direct' for projects in v1
```

`parked_at IS NOT NULL` is the single load-bearing fact. The other three are provenance: `parked_by` is the resolved status actor (`resolve_status_actor`), `parked_via` records whether the row was parked itself or by its project's cascade, and `parked_reason` is whatever the owner typed. On the protocol side, `Task` and `Project` gain the same four `Option<String>` fields with `#[builder(default)]` (both structs are on the builder pattern), and `WorkItemPatch` gains `parked: Option<bool>` plus `parked_reason: Option<String>`, following the `deferred` / `archived_reason` shape (`tools/boss/protocol/src/types/work_item.rs:127, 174`). The DB mappers stay struct-literal.

Migrations follow the guarded `ALTER TABLE … ADD COLUMN` pattern in `work/migrations_*.rs` (the design-doc pointer columns on `projects` are the precedent), ordered after the baseline per postmortem incident-003.

**Who may park.** `human` and `boss` tiers (the owner from the app or CLI, and the coordinator on the owner's instruction). `Worker`, the new `Progression` tier, engine sweeps, and Boothby are refused at the write boundary, the same way `critical` is refused (`app/work_items.rs:27-36`). Parking is the owner's decision by the project's own non-goal.

#### 1.2 Project cascade

- Parking a project stamps every non-terminal, non-deleted task in it (including hidden revision rows and `deferred` rows) with `parked_at = now, parked_via = 'project:<id>'`, in the same transaction. Tasks already parked directly keep their own stamp.
- Un-parking a project clears only rows whose `parked_via` names that project. A task the owner parked individually before or during the project park stays parked.
- A task created inside a parked project (by the planner's auto-populate, a follow-up mint, or `boss task create --project`) is born parked with `parked_via = 'project:<id>'`. A revision created for a parked parent is born parked with `parked_via = 'project:<id>'` when the parent was parked via its project, or `'direct'` otherwise; in both cases the engine should not be creating it in the first place (see 1.4), so this is a backstop.
- Parking an individual task inside an un-parked project is ordinary; it does not affect the project.

#### 1.3 What happens to running work and open PRs

- **A live execution is not killed.** Parking an item whose execution is `running | waiting_human | claimed` lets it finish: killing a mid-turn worker is how incident-004 lost work, and parking is an attention decision, not a cancellation. The board shows the parked card (under the Parked filter) with a "finishing current run" sub-label derived from the live execution, nothing new is computed app-side. The owner who wants the slot back now uses the existing stop verb.
- **Pending executions are cancelled.** Rows in `ready | queued | waiting_dependency` for the item are cancelled through the existing never-started cancellation path (`executions cancel`, per [post-crash-recovery](../post-crash-recovery.md)), with reason `parked`. Un-park re-mints them through ordinary reconciliation.
- **Completion of the in-flight run proceeds normally**: PR URL capture, the `in_review` transition, the ledger write. What is suppressed is everything that would otherwise follow automatically (AI review scheduling, CI watch, conflict watch), through the predicate in 1.4.
- **Open PRs are left alone on GitHub.** The engine stops upkeep but keeps observing terminal facts: the merge poller still moves a parked `in_review` task to `done` when its PR merges, and still runs the closed-unmerged handling when the PR is closed, because those are facts about the world, not upkeep. Converting the PR to draft on park (the `default_pr_draft_mode` setting shows the engine already knows how to create drafts, `engine/core/src/settings.rs:81`) is listed as a deferred entry: it is reversible and would stop reviewers and the merge queue acting on a parked PR, but its interaction with the trunk merge-queue poller is unverified and it is not needed for v1.
- **Dependencies.** A parked prerequisite does not satisfy its dependents; they stay `blocked: dependency` with `dispatch_wait_reason` naming the parked prerequisite. Progression treats "blocked on a parked prerequisite" as a human decision already made and does not ask about it; the stuck report has a bucket for it.

#### 1.4 Atrophy: one predicate, consulted at every producer

`WorkDb::upkeep_eligible(task)` (and `is_parked`) is false for a parked row, for a row whose project is parked, and for revisions whose chain root is parked. It is consulted in:

- `task_accepts_execution` (`exec_status_helpers.rs:241`), so no automatic path mints an execution. An explicit `RequestExecution` on a parked row is refused with a typed error telling the caller to un-park first; the un-park path is the only way back.
- the candidate listings of every upkeep producer: CI remediation (`ci_watch`), conflict resolution (`conflict_watch`, including the mechanical-rebase rung behind `conflict_ladder_mechanical_rebase`), AI review scheduling (`review_start`), dead-review recovery (`pr_review_recovery`), speculative conflict prediction and stacked-PR offers (both behind flags on the merge poller), orphan re-dispatch (`orphan_sweep`), and the project postmortem sweep (a parked project gets no postmortem task).
- the dependency cascade (`dep_unblock_sweep`): a parked row whose prerequisites complete is still flipped `blocked → todo` (lifecycle position stays truthful), but no execution is minted, exactly as `deferred` behaves today.
- the new progression sweep (Part 2).

The exclusion lives in each producer's SQL candidate listing, not at the point of action, so a parked row is never even nominated. A parameterised test over the list of producers asserts the exclusion, so adding a producer without the predicate fails a test rather than quietly upkeeping parked work.

#### 1.5 Un-park reconciliation sequence

`reconcile_unparked_item(work_item_id)` runs synchronously in the un-park RPC for the status changes, and schedules the probe steps as one background job (they call GitHub). Each step reuses an existing per-item entry point; the sequence is new, the steps are not. Every step appends a `[parking]` audit line through the shared `append_description_line` helper (`engine/core/src/reconcile_audit.rs:24-36`) and emits an `unpark_reconcile` dispatch event with the step name and outcome.

1. **Clear the park** (`parked_* = NULL`) and write a ledger row (Part 3) with `basis = 'unparked'`. For a project, do this for the project and every `parked_via = 'project:<id>'` child, then run steps 2–7 per child.
2. **Clear stale halt stamps** that predate the park: `dispatch_failed_reason/error/at` (a churn-guard or dispatch-failure stamp from before the park says nothing about now). `blocked_reason = 'worker_failed' | 'awaiting_operator_answer'` is **not** cleared: both record a human-attention state that parking did not change.
3. **Refresh PR state** with one bounded live check through the merge poller's single-item refresh (the machinery behind `boss pr status --refresh`). Merged → the ordinary merged path to `done`; closed → the ordinary closed-unmerged path.
4. **If `in_review` with an open PR:** run the single-item conflict probe; `CONFLICTING` enters the existing conflict path (mechanical rung first when its flag is on, else a conflict-resolution revision). Run the single-item CI probe; red required checks enter the existing CI remediation path **with the attempt budget reset** (`reset_ci_attempts_used`), because exhausted attempts from before the park are stale evidence. If no AI review has completed for the current head, `review_start` schedules one as it would for a fresh `in_review` transition.
5. **If `todo | active | blocked`:** re-run `reconcile_work_item_execution` so a `ready` or `waiting_dependency` row is minted exactly as for a fresh row; `active` with no live execution is handed to `orphan_sweep`'s ordinary re-dispatch, with the churn window reset.
6. **Revisions** that were parked via the parent are un-parked with it and re-enter per-PR chain serialization unchanged.
7. **Enqueue a progression candidate** for the item with the stuck-age threshold waived once, so an item that is still stuck after steps 2–6 is diagnosed immediately rather than after the normal grace period.

The sequence is idempotent: re-running it on an already un-parked item performs steps 3–7 only, and each probe is a no-op when its signal is clear. A failing step is recorded and the sequence continues; the item is left un-parked and the progression candidate from step 7 is what catches whatever the failed step would have fixed.

#### 1.6 UI and CLI affordances

- **Card and project context menus** gain "Park…" / "Unpark" (`WorkBoardCard.swift:258-284` context menu; `ContentView.swift:796-803` project sidebar menu, next to Archive). "Park…" opens a small sheet with an optional reason; this is a confirmation for an action the user just took, which `app-macos/AGENTS.md:9` allows.
- **Board filter.** The default board excludes parked rows (in the visible-item assembly, `ChatViewModel+WorkLookups.swift:120-198`, next to `showBlockedOnly`). A "Parked" toggle in the filter popover shows parked rows only, each with a grey "Parked · <relative time> · <reason>" chip; parked projects appear dimmed in the sidebar with a parked count, as archived projects do today. - **Engine RPC.** One `ParkWorkItem { id, parked: bool, reason }` request handled through the ordinary `UpdateWorkItem` tier rules, so the actor and the refusal for non-human tiers come for free.

### Part 2: Progression

#### 2.1 The stuck signal and the candidate predicate

An item is a **progression candidate** when all of the following hold:

1. Not parked, not in a parked project, not terminal, not soft-deleted, not `human_driven`, not `deferred` (a recorded scope decision), and not `blocked: awaiting_operator_answer` (a question is already in front of the human).
2. **No live or pending execution of any kind** on the item, on any revision whose `parent_task_id` is the item, or on any item sharing its PR (`pr_url` / `revision_parent_pr_url`), where live/pending means `queued | ready | waiting_dependency | claimed | running | waiting_human`. This is the "already being actively worked" test, and it covers coding, revisions, CI fix, conflict resolution, AI review, and review-guide generation in one query.
3. Not waiting on capacity: the item's current `dispatch_wait_reason` is not a slot, cap, or pause wait. Waiting for bandwidth is not stuck.
4. Not `blocked: dependency` on a prerequisite that is itself live, parked, or a progression candidate (progress the prerequisite, not the dependent; if the prerequisite is parked, the owner decided).
5. In one of the stuck states from the enumeration, continuously for at least `progression.stuck_after` (set from measurement; see 2.6), as read from the task status ledger (Part 3). The un-park path waives this once.
6. No progression execution for the item within `progression.cooldown`, and the item's progression budget is not exhausted (2.4).

The predicate is one SQL view, `progression_candidates`, so the sweep, the report, and `bossctl dispatch diagnose` all read the same definition.

#### 2.2 Spawn: a new execution kind, dispatched like everything else

`ExecutionKind::Progression` (`"progression"`). The `progression_sweep` (a `spawn_sweep_loop` reconciler like the rest in `app/server.rs`) selects candidates oldest-stuck first and mints a `work_executions` row per candidate with `work_item_id = <the stuck item>` and `created_via = 'progression_sweep'`. Binding the execution to the stuck item means the existing `get_live_execution_for_work_item` dedup gives one progression run per item for free, and the candidate predicate's clause 2 means a progression execution's own liveness excludes the item from a second one. `Progression` joins `is_read_only_review`'s exemption from per-PR writer serialization under a renamed predicate, `never_writes_pr_branch`, because it never touches the branch.

The agent is a `WorkerKind::Progression` worker spawned through the ordinary path (`runner.rs → spawn_flow.rs → worker_setup.rs`), with the answer agent's capability-restricted template: `--permission-mode dontAsk`, an allowlist of read-only tools plus the `boss progress …` verb family and the read-only `boss task show|list`, `boss pr status`, `gh pr view|checks` commands, and a deny belt covering `jj`, `git`, `cube pr`, `gh pr edit|merge|comment|review`, `gh api` with a mutating method, and every file-write tool. **It has no workspace lease.** The brief composer (2.3) packages what a checkout would otherwise be used for, so the agent never holds a repo it could write to; "no repo write path" is then structural rather than a deny rule.

#### 2.3 The brief

The engine composes a diagnosis packet per run, so the agent spends its turns deciding rather than discovering:

- the item, its project, its dependency edges in both directions with each neighbour's status and live execution (`dependencies.rs`);
- the stuck classification from the enumeration, with the ledger rows showing when the state was entered and what the last three status changes were;
- every execution for the item and its revision chain, with terminal status, `error_text`, and `run_done_outcome`, plus the churn-window count the guard would compute;
- for an item with a PR: the merge poller's last snapshot (`mergeable`, `merge_state_status`, required checks), the conflict diagnosis from the `conflict-diagnosis` crate when `CONFLICTING`, the failing-check log excerpt from `ci-log-reader` when red, the active/exhausted attempt rows from `conflict_resolutions` and `ci_remediations`, and the AI review verdict state;
- open `work_attention_items` and operator questions on the item and its chain;
- the item's progression history: prior runs, their dispositions, and the fingerprints already acted on (2.5);
- the verb catalogue with the remaining budget.

#### 2.4 The scoped access model

A new `RpcTier::Progression`, classified from peer-pid ancestry of the registered progression pane exactly as `Worker` is, and **enforced unconditionally**, not behind `worker_rpc_tier`. Its verb policy is an exhaustive deny-by-default match in a leaf crate, `progression-policy`, mirroring `worker-policy`. Every allowed mutating verb is additionally **scope-checked**: the engine resolves the calling execution, loads the neighbourhood it was spawned for (the item, its revisions, its direct prerequisites and dependents), and refuses any target outside it. The neighbourhood is computed at spawn and stored on the execution so the check is a set membership, not a graph walk per call.

Writes record `last_status_actor = 'progression'`; the actor is audited the way `boothby` was (exhaustive-match sweep of `StatusActor` consumers), and `StatusActor::is_engine_cascade` stays false for it, so a progression block or unblock sticks like a human one.

#### 2.5 Idempotence, budget, and the escalation ladder

- **Stuck fingerprint.** `hash(stuck_state_kind, blocked_reason, pr_head_sha or NULL, latest terminal execution id)`. It changes when the world changes (a new head, a new execution, a different state) and stays the same while nothing has moved.
- **Fingerprint refusal.** The engine records `(item, fingerprint, verb)` for every mutating progression verb. A second call of the same verb on the same fingerprint is refused with a typed error naming the prior run; the agent must choose a different action or ask. This is what makes "re-dispatch, bounce, re-dispatch, bounce" structurally impossible rather than behaviourally unlikely.
- **Budget.** `progression.max_creates_per_item_window` revisions-plus-precursors per item per rolling window (default placeholders in 2.6, set from measurement). Exhaustion is a refusal; the agent must ask.
- **The ladder.** Run 1 acts. After `progression.cooldown`, the sweep re-evaluates; if the fingerprint is unchanged, run 2 is spawned and must take a different action (refusal enforces it). If after run 2 the fingerprint is still unchanged at the next pass, or if any run ends `no_action` or `needs_human`, **the engine itself files the question**: a multiple-choice operator question on the item, "Progression could not unstick this after N attempts. Park it, archive it, or keep trying?", with the dispositions and summaries in its explanation. The item parks `awaiting_operator_answer`; "keep trying" resets the ladder for the fingerprint.
- **Infrastructure failure.** A progression execution that ends `failed | orphaned | abandoned` twice in a row for one item stops the sweep nominating that item and files the same engine question with the failure in the explanation. The stuck report's "progression failing" bucket counts these.
- **Unanswered questions are not silence.** They are the "waiting on human" bucket, visible in Needs Attention with their age, and re-notified (2.7).

#### 2.6 Bandwidth: pool, cadence, and what happens when a limit fires

Progression competes with mainline work on one laptop, so it runs in its own small pool and never takes an interactive slot:

- **Pool.** A `progression` worker pool of `progression.pool_size` slots (the `WorkerPool::new_automation(size)` primitive, instantiated again as Automations did). It does not spill into Lower Decks and nothing spills into it. Dispatch ordering within the pool is oldest-stuck first.
- **Admission.** Progression executions honour the operator dispatch pause and the breaker pause like every non-critical execution: a pause is the owner saying "stop spending", and the stuck report records "paused" as the reason nothing progressed.
- **Cadence.** `progression_sweep` interval `progression.sweep_interval`; per-item `progression.cooldown` between runs; `progression.stuck_after` grace before first nomination; `progression.run_timeout` after which the stale-worker reaper's ordinary rules apply.
- **Cost.** Progression uses the product's default driver/model at the lowest reasoning setting the driver offers; the brief does the discovery, so a run should be a few turns.

**Measurement before numbers.** Per `BOSS_COORDINATOR.md` ("Limits, throttles and timeouts"), none of these values is fixed in this doc. Task 1 ships the ledger and the report; the report run against seven days of real traffic yields the steady-state stuck population, the arrival rate of new stuck items, and the churn-guard and remediation-exhaustion rates. Task 9 then sets:

| Setting                                  | Set from                                                                                 | Placeholder until measured | When it fires                                                                                                     |
| ---------------------------------------- | ---------------------------------------------------------------------------------------- | -------------------------- | ----------------------------------------------------------------------------------------------------------------- |
| `progression.pool_size`                  | `ceil(peak candidates/day × mean run minutes / 1440) × 3`, minimum 1                      | 1                          | candidates wait in the sweep's queue, oldest first; report shows queue depth and oldest wait                        |
| `progression.sweep_interval`             | ≥ 10× the ledger write rate's p99 interval; a cheap SQL pass                              | 5 min                      | nothing; a candidate waits at most one interval                                                                    |
| `progression.stuck_after`                | ≥ 3× the longest observed legitimate pause between automatic transitions (e.g. CI run time, review scheduling lag) | 2 h                        | item is not nominated until elapsed                                                                               |
| `progression.cooldown`                   | ≥ 3× the longest observed time for a progression-created revision to reach `in_review`   | 6 h                        | item is not re-nominated until elapsed                                                                            |
| `progression.max_creates_per_item_window`| ≥ 3× the p99 of remediation attempts per item seen in `ci_remediations`/`conflict_resolutions` | 3 per 7 days               | `revise`/`precursor` refused; agent must ask                                                                      |
| `progression.run_timeout`                | ≥ 3× observed p99 progression run duration                                               | 30 min                     | stale-worker reap; counts as an infrastructure failure for the ladder                                             |

The placeholders exist so the feature can be exercised in a test instance; Task 9's PR replaces them with measured values and records the measurements in its body. The whole feature ships behind a `progression_agents` feature flag, default off, so the parking tasks and the report can land and be used before any agent is spawned.

#### 2.7 How a forced question reaches the human

The channel is the one the Needs Attention design already established as read by the owner, plus the interruptive half it lacks:

1. **The kanban's Needs Attention section** (Doing). Every progression question is an `operator_questions` row, so it renders on the existing inline card with Yes/No or the new multiple-choice buttons, oldest first. This section holds decisions only; routine status never appears in it, which is what distinguishes a forced question from status.
2. **A macOS notification** through `ReviewNotificationCenter`, generalised from its one call site: category "Decision needed", title the question's first line, body the item's short label, tap selects the card. Unlike "Ready for Review" it is presented in the foreground too (the `willPresent` suppression is lifted for this category only) and it carries sound. One notification per question at creation, and one reminder per `progression.remind_after` (set from measurement; placeholder 3 days) while the question stays open. The category and the reminder are what make it distinct from the review notification.
3. **A count in the Needs Attention header** of open questions, so the board shows "3 decisions waiting" without opening anything.

No digest, Slack, or email channel is added. The `ReviewNotificationCenter` extension is deliberately small because it is the one interruptive surface the owner has already accepted.

Multiple-choice answers require implementing the `multiple_choice` tag the Needs Attention design reserved (`OperatorAnswerType`, `tools/boss/protocol/src/types/proposal.rs:690-702`); Task 8 does that.

#### 2.8 Interaction with existing mechanisms, stated as invariants

- **Never two writers on one PR.** Progression never writes a PR branch. What it creates goes through `create_revision`, which the engine already holds `blocked` while another writer is live on the same PR (coordinator prompt, `BossPaneModel.swift:797`). The candidate predicate excludes any item whose PR chain has a live execution, so progression is not even dispatched while a writer exists.
- **Churn guard.** A progression `redispatch` is an explicit start: it clears the `churn_guard` stamp as drag-to-Doing does, and the resulting execution carries `created_via = 'progression:<exec>'` so `orphan_sweep`'s window counts it. If the guard trips again, the fingerprint rule forbids a second `redispatch`; the agent must find the cause or ask.
- **CI-fix and conflict revisions.** An active attempt in `ci_remediations` / `conflict_resolutions` (its revision non-terminal) makes the item ineligible. `ci_failure_exhausted` and a conflict ladder that fell through to a human are eligible; the agent may create one revision with a diagnosis-bearing brief, once per fingerprint, and then must ask.
- **AI review.** A live `pr_review` or `pr_review_guide` execution makes the item ineligible; a dead review (`pr_review_recovery`'s candidates) is eligible, and the usual action is `redispatch` of the review through the existing `review_start` path, which the engine exposes to the tier as a read-only-review restart.
- **Dispatch admission and the cap.** Progression executions live in their own pool and are invisible to the interactive concurrency cap and to Lower Decks spillover. They obey operator and breaker pauses.
- **Deliberate parks and operator questions.** `deliberate_park`, `worker_failed`, and `awaiting_operator_answer` are human-attention states by existing design; progression never restarts them and never asks a second question on top. They are the "waiting on human" bucket.
- **Boothby.** Boothby's "never fight live work" guard already excludes rows with non-terminal executions, so a live progression run keeps Boothby off the item. If Boothby's executor ships, its "redispatch / unpark stuck work" verb (#14 in its catalogue) should be removed in favour of progression, which is noted there as a follow-up, not done here.

### Part 3: Measurement

#### 3.1 Task status ledger

`task_status_audit (id, work_item_id, property, old_value, new_value, actor, changed_at, basis)`, modelled on `project_property_audit` (`work/schema_baseline.rs:654-662`), written in the same transaction as every change to `status`, `blocked_reason`, `parked_at`, `dispatch_failed_reason`, and `autostart`. The `basis` column carries the producer (`merge_poller`, `ci_watch`, `churn_guard`, `unparked`, `progression:<exec>`, …). This is the missing fact the human-channel sweep found: today nothing records when a task entered its current state, so "blocked longer than X" cannot be computed except for operator questions (`operator_questions.created_at`). Note also the `task_blocked_signals` caveat: its `ON CONFLICT` clause never updates `created_at` (`work/insert_helpers.rs:92-108`), so a flapping signal reports its first observation; the ledger makes that column's meaning irrelevant for measurement.

#### 3.2 The stuck report

`boss report stuck [--since 7d] [--json]` (and the same data as a `bossctl dispatch stuck` view) lists every non-terminal, non-deleted item with no live execution whose current state is older than a threshold, in buckets:

| Bucket                 | Definition                                                                                                                      | Interpretation                              |
| ---------------------- | ------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------- |
| `parked`               | `parked_at IS NOT NULL` (self or project)                                                                                       | owner's decision; shown for completeness    |
| `waiting_on_human`     | open operator question, `worker_failed`, `deliberate_park`, `human_driven` in Doing, `deferred`, human-set `autostart = false` with no failure stamp | the legitimate steady state                 |
| `waiting_on_capacity`  | `dispatch_wait_reason` is slot/cap/pause                                                                                        | bandwidth; the distributed-engine project   |
| `waiting_on_dependency`| `blocked: dependency` with a prerequisite that is live or itself a candidate                                                    | progressing upstream                        |
| `parked_upstream`      | `blocked: dependency` on a parked prerequisite                                                                                  | owner's decision                            |
| `progression_in_flight`| a progression execution is live, or the item is inside its cooldown after a `progressed` run                                    | being handled                               |
| `progression_failing`  | ladder exhausted or infrastructure failures, question filed                                                                     | the engine admitted defeat; counts as human |
| `engine_stuck`         | everything else                                                                                                                 | **the defect count; the end-state claim is that this is empty** |

Each row shows age in state, the stuck classification from the enumeration, and the last ledger basis. A daily snapshot of bucket counts and the `engine_stuck` max age is written through the metrics framework (`engine/metrics-registry`), so the claim can be read as a trend, not a point.

## Risks / open questions

- **Noise to the owner.** The ladder can file one question per stuck item every `cooldown × 2`. The measurement task bounds this with real numbers before the flag is turned on, and the reminder cadence is separate from question creation, but the first week with the flag on should be watched; a per-day cap on engine-filed questions is a one-line addition if the measured arrival rate warrants it.
- **Fingerprint granularity.** Too coarse and distinct problems share a fingerprint and the second is refused; too fine and the same problem re-fingerprints after trivial changes (a new head from an unrelated rebase). The proposed inputs are a judgment; the measurement task should check the distribution of fingerprint changes per item.
- **The un-park CI budget reset** could re-spend remediation attempts on a PR whose failures are not transient. It is bounded by the ordinary budget and by progression's own ladder; the alternative, leaving `ci_failure_exhausted` in place, makes un-park a no-op for exactly the PRs the owner un-parked to revive.
- **`deferred` versus parked.** Two owner-set "not now" flags with different hiding and different exit semantics is a real cost. The doc keeps them orthogonal to avoid redefining `deferred`'s approval-on-start semantics; a later task could migrate `deferred` to "parked with reason `future scope`" once parking exists, if the owner prefers one concept.
- **Multiple-choice operator answers** are new UI and new validation; the Needs Attention design reserved the tag but did not build it. Task 8 carries that cost; falling back to Yes/No for the ladder question ("Keep trying?" with "No" meaning park) is possible if that task slips.
- **Enforcing the progression tier unconditionally** while the worker tier is flag-gated is an inconsistency. It is the right inconsistency (an agent built to mutate must have its scope enforced), and it may be the push that turns `worker_rpc_tier` on; but the two policies should share the `PeerClass` plumbing, not fork it.
- **Projects with hundreds of tasks.** Project park/un-park is one transaction over all children; the un-park probe steps are per child and go to GitHub. The background job must rate-limit against the `gh` budget (`github_api_usage`) and emit progress; the measurement task should record the largest project's child count.
