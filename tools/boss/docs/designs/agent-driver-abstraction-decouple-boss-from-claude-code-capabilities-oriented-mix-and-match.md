# Agent-driver abstraction: decouple Boss from Claude Code (capabilities-oriented, mix-and-match)

- **Status:** built. The seam, the capability model, the dispatch gate, the `driver` data model, and the reference Claude driver all shipped; the outstanding residue is named in [Implementation status](#implementation-status).
- **Scope:** engine-side only. No Swift/app changes; the execution model stays "embed the agent CLI in a ghostty pane".
- **Downstream:** [Copilot CLI as alternative worker backend](copilot-cli-as-alternative-worker-backend.md), [Codex as a first-class agent driver](codex-as-a-first-class-agent-driver.md), [Grok as a first-class interactive agent driver](grok-as-a-first-class-interactive-agent-driver.md) — all three are concrete drivers on the seam this project defines.
- **Where the code lives:** `tools/boss/engine/driver` (`boss-engine-driver`: trait, capabilities, registry, `ClaudeDriver`), plus three crates this project spun out — `engine/structured-output`, `engine/stdout-progress`, `engine/utility-model`.

The deliverable is the abstraction itself: a capabilities-oriented driver seam plus a behaviour-preserving Claude driver behind it. Concrete non-Claude drivers are separate projects that plug into it.

This document is written after the implementation. Part 1 is the original coupling survey, kept as the historical record of what had to move; everything from [Chosen approach](#chosen-approach) onward describes what exists in the tree today, with divergences from the original plan called out where they happened.

## Goals

- Introduce an engine-side abstraction layer between Boss and the coding-agent CLI it drives, so Boss is no longer hardwired to Claude Code. Every place the engine today shells out to `claude`, parses Claude's transcript, wires Claude's hooks, or renders Claude's `settings.json` becomes a call through a **driver** interface.
- Express the interface as **capabilities** Boss needs from a backend, not as a Claude-shaped contract every backend must satisfy. A driver **declares which capabilities it supports**; Boss adapts (degrade / synthesize / refuse) per capability when one is absent. This is the operator's first hard requirement: _capabilities-oriented, not lowest-common-denominator_.
- Make backend choice **mix-and-match**: per-work-item (and per-product-default) driver selection, recorded on the work item, with Claude Code as one driver among several. This is the operator's second hard requirement: _not a global switch_.
- Re-home the engine's **direct Anthropic API calls** (live-status summarizer, pane-summary, magic-wand, attentions backstop) behind a separate _utility-model_ provider seam, so "the worker's driver" and "the model the engine uses for its own background inference" are independent axes.
- Produce a complete, file:symbol-level survey of the coupling (Part 1 below) so the implementation tasks have an exhaustive work-list, not a guess.

## Non-goals

- **Removing or de-privileging the Claude path.** Claude Code is the reference driver and the default. The abstraction must justify itself on the _second_-driver side; the Claude driver is a behaviour-preserving extraction of today's code, byte-for-byte where it spawns a worker.
- **Implementing the Copilot or Codex drivers.** Those are P284 and a later project. This doc defines the seam they plug into and proves the seam fits all three, but writes only the Claude driver.
- **App-side / Swift / macOS changes.** Out of scope. The execution model stays: embed the agent CLI in a ghostty terminal pane. A native UI chat interface is a separate, later project. The kanban already reads abstract `WorkerActivity` / `LiveWorkerState`; nothing app-side needs to know which driver ran.
- **A global cutover or a single `backend` toggle.** Mix-and-match is the end state. There is no env var that redirects all dispatches.
- **Re-deriving the effort/model design.** [`effort-and-model-estimation`](effort-and-model-estimation.md) already centralised the effort→model tables in `effort.rs`. This project makes those tables _per-driver_ rather than re-opening the vocabulary.
- **MCP injection, token/quota accounting, cost accounting.** Boss injects no MCP servers today and adds none here. Quota is the backend subscription's concern. Called out as known absences, not v1 work.

## Background — relationship to P284

P284 ("Copilot CLI as alternative worker backend") already exists as a design and answers the _two-backend_ version of this question: it forks the engine exactly once, at spawn, into `worker_setup::claude` vs `worker_setup::copilot`, carries a `backend: Claude | Copilot` enum, and writes a parallel hook-normaliser for Copilot's JSON stream. Its Alternative C ("one branch at the bottom, everything else shared") is the right instinct for _two_ backends.

This project generalises that instinct for _N_ backends and satisfies the capabilities requirement P284 explicitly defers (its Phase 4 names "an optional unifying `WorkerBackend` trait in the engine (the v2 abstraction this design defers)"). The relationship is:

- **P1422 (this doc)** defines the driver trait, the capability set, the absence-policy model, and re-implements Claude on it (behaviour-preserving).
- **P284** becomes the Copilot driver: a `CopilotDriver` implementing the trait, declaring the capabilities it has (and lacking PreToolUse hooks, real-time event socket, five-value effort), riding the absence policies this doc defines. P284's Q1–Q6 decisions (where the choice lives, spawn shape, hook gap, session files, feature-gap matrix, rollout) all survive — they become _the Copilot driver's answers to this interface's capabilities_.
- **Codex** becomes a third driver later, with its own capability declaration.

Where the Copilot design and this doc disagreed on a name (it calls the column `backend`; this doc proposed `driver`), this doc's choice was canonical because it is upstream. `driver` is what shipped.

**File-based structured output (folded in):** the structured-output cases above (ReviewResult, triage, FOLLOWUPS, PR URL) moved from _parse-it-out-of-the-transcript_ to _the worker writes it to a known file_. That is strictly more driver-friendly: a file-based structured-output contract needs no transcript-format knowledge at all. File-based structured output is the **primary** StructuredOutput mechanism; transcript-sentinel parsing survives only as the Claude driver's _fallback producer_.

As built (mono#2292), the contract lives in its own crate, `boss-engine-structured-output`, so both `engine/core` and `engine/driver` can speak it (`core → driver → structured-output`):

- `StructuredOutputKind` is `PrUrl | ReviewResult | TriageDecision | Followups | PostmortemFollowups`, each with **its own** engine-owned file `<execution-id>.<kind>.json` and a documented wire schema. Per-kind paths — rather than the single shared per-execution artifact the earlier work had — are what let one execution emit several payloads (an implementer writes a PR URL _and_, optionally, followups). The pre-contract shared `<execution-id>.json` is still read for the three kinds that used it, so a worker spawned by an older engine stays readable across an in-flight engine upgrade.
- Every Claude sentinel moved out of the engine and into `boss_engine_driver::claude::structured_output` behind `AgentDriver::structured_output_fallback(kind, text) -> Vec<FallbackCandidate>`. A driver with no prose conventions returns an empty `Vec` and rides the file channel alone — which is the point: satisfying `StructuredOutput` requires no transcript-format knowledge.
- PR-URL capture became a ladder rather than a single source: artifact → staged `PostToolUse` capture → driver final-message producer → cold-path `detect_pr`. The artifact is consulted on the turn boundary _and_ in `recheck_for_pr`, which closes a real hole — the staging cache is in-memory, so an engine restart between push and turn end used to lose a hook-captured URL. Self-reported URLs are refused outright for `revision_implementation`, where push evidence must keep coming from the SHA-delta gate.

## Alternatives considered

### Alternative A — Generalise P284's spawn-fork to an N-way `enum Backend` (no capability declaration)

Carry a `Backend` enum, `match` on it at the handful of fork points (spawn, hook normaliser, settings render), and add an arm per backend. This is P284's Alternative C scaled from 2 to N.

**Rejected.** It is lowest-common-denominator by construction and fails the operator's first hard requirement. The enum has no way to _declare_ that Copilot lacks a PreToolUse interception point or that Codex has a different transcript shape — every divergence becomes a new `match` arm scattered across `completion.rs`, `editorial_hook.rs`, `live_status_loop.rs`, `live_worker_state.rs`. When a backend can't do something, the `match` either silently no-ops (a hidden capability gap) or panics. There is no single place that answers "can this driver do X, and if not, do we degrade or refuse?" The match-arm sprawl is exactly the tax this project exists to avoid, and it grows with every backend × every divergent surface.

### Alternative B — External shim that emulates Claude's surface (`copilot-as-claude`)

Keep the engine 100% Claude-shaped; ship a wrapper per backend that accepts `claude`'s CLI shape, emits `.claude/hooks`-shaped events, and writes a Claude-shaped transcript jsonl. The engine never learns there is more than one backend.

**Rejected** (same reasoning P284 gave for its Alternative B, and it applies more strongly at N backends): backends with no real-time hook surface force the shim to _infer_ PreToolUse/PostToolUse/Stop from a log tail and synthesise Claude's JSON — brittle, and failures look like worker bugs rather than backend mismatches. Permission-rule translation (`Bash(:*)` → `--deny-tool 'shell(rm:*)'`) becomes a parser. The principle it violates: incompatibilities should be _visible to the engine_, where the degrade-vs-refuse decision is made — not hidden in a shim that fails low-fidelity.

### Alternative D — Pure data-descriptor drivers (a TOML per backend)

Express each driver as a static descriptor: binary name, flag template, file names, effort table, model menu. No code, just data the engine interpolates.

**Rejected** as the _whole_ answer (kept as a _component_). The genuinely divergent surfaces are behavioural, not textual: synthesising a `WorkerEvent` stream from Copilot's JSON, parsing structured output, classifying a backend's error strings, translating a permission policy into a backend's grammar. A data descriptor cannot synthesise an event stream or run a normaliser. The chosen approach _uses_ a descriptor for the easy 70% (binary, flags, file names, model menu, effort table) and a trait for the behavioural 30%.

### Alternative C (chosen) — Capabilities-oriented driver trait with a declared capability set and per-capability absence policy

A driver is a trait object that **declares a `CapabilitySet`** and implements the capabilities it claims. Boss queries the declaration, resolves the capabilities a given work-item kind requires, and applies a **per-capability absence policy** (synthesize / degrade / refuse) when the driver lacks one. This satisfies both hard requirements: capabilities are first-class and declared (not lowest-common-denominator), and selection is per-work-item (not global). It absorbs Alternative D's descriptor as the driver's static half.

---

## Chosen approach

### The shape

```
                         ┌───────────────────────────────────────┐
   work item ──────────► │  CapabilityResolver (dispatch gate)    │
   (kind + driver)       │  required(kind) ∩ declared(driver)     │
                         │  → synthesize | degrade | refuse       │
                         └───────────────┬───────────────────────┘
                                         │ resolved plan
                                         ▼
   ┌──────────────────────────────────────────────────────────────────┐
   │  trait AgentDriver  (one trait object per dispatch)               │
   │  • descriptor():   binary, file layout, model menu, effort table  │  ← Alt-D data half
   │  • capabilities(): CapabilitySet (what this driver declares)      │
   │  • spawn / provision / permission / observe / intercept /         │  ← behavioural half
   │    structured-output / control-verbs / transcript                 │
   └──────────────────────────────────────────────────────────────────┘
        ▲ ClaudeDriver (reference)   ▲ CopilotDriver (P284)   ▲ CodexDriver (future)

   Orthogonal axis:  trait UtilityModel  (engine's own background inference)
                     live-status • pane-summary • attentions • Planner • comment-intent
```

As built, the boxes map to `boss-engine-driver` (trait, `Capability`, `CapabilitySet`, `CapabilityResolver`, `DriverRegistry`, `ClaudeDriver`), with three crates spun out beneath or beside it — `boss-engine-structured-output` (the file contract, shared by engine and driver), `boss-engine-stdout-progress` (the second progress transport), and `boss-engine-utility-model` (the orthogonal axis). The dependency edges are one-way throughout: `core → driver → structured-output`, and `core → utility-model → claude_client`.

Everything downstream of the produced `WorkerEvent` stream and the resolved spawn plan — the dispatch state machine, slot accounting, cube lease, kanban, PR detection, conflict flow — is untouched and stays driver-agnostic (it already is).

### Capabilities

Each capability is a named unit Boss needs. A driver declares, per capability, that it **provides** it (and at what fidelity tier where relevant) or does not. The capability set:

| Capability                    | What Boss needs                                                                                                                                                      | Claude provides                                | Absence policy (default)                                                                                                                                                 |
| ----------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **Spawn**                     | Build the command/plan that starts a worker against a workspace with a prompt                                                                                        | `spawn_invocation` → `SpawnPlan`               | **Refuse** — a driver that can't spawn is not a driver                                                                                                                   |
| **WorkspaceProvisioning**     | Materialise per-session files (prompt, agent-rules, gitignore); suppress trust prompt; **tear down** any out-of-workspace per-run state                              | `.claude/*` + `~/.claude.json` pre-trust       | **Refuse** (prompt file is mandatory); trust-suppression alone may **degrade** (worker may prompt once)                                                                  |
| **PermissionPolicy**          | Apply Boss's abstract policy (autonomous-honour-denies; reviewer read-only; deny bossctl/state-dir/rm/sudo)                                                          | settings.json deny rules + permission-mode     | **Refuse** if the driver can't deny the structural set (bossctl/state-dir); **degrade** for finer rules                                                                  |
| **ModelAndEffortMenu**        | Resolve effort+override against the driver's model menu; classify family for autonomy default                                                                        | `ModelMenu` on `ClaudeDriver`'s descriptor     | **Degrade** — collapse Boss effort onto the driver's coarser knob (e.g. 5→3)                                                                                             |
| **ProgressObservation**       | Produce a `WorkerEvent` stream driving the activity machine; fidelity tiers: _rich_ (per-tool events) / _coarse_ (turn + lifecycle) / _minimal_ (process alive only) | rich (hooks)                                   | **Synthesize** from the best channel the driver has; never refuse — minimal tier (alive/exited) always works                                                             |
| **ToolUseInterception**       | Intercept-and-rewrite-or-deny a tool call before it runs (editorial T946/P576, path guard, revision PR guard)                                                        | PreToolUse hooks                               | **Degrade** to post-hoc (review the artefact after creation, request edit/redaction) **or Refuse** for editorial-required products — operator policy, see open questions |
| **TurnBoundary**              | A "turn ended" signal triggering completion detection + probe injection                                                                                              | Stop hook                                      | **Synthesize** (infer from stream idle) or **degrade** to process-exit-only completion                                                                                   |
| **StructuredOutput**          | Receive worker's structured results (PR URL, ReviewResult, triage, FOLLOWUPS); **file-based primary** (T1414), transcript-sentinel fallback                          | file primary + transcript fallback             | **Degrade** to file-only (drop sentinel parsing); PR URL via file or `gh` poll always works                                                                              |
| **TranscriptAccess**          | A redactable, role-structured view of the run for summarisation + post-hoc extraction                                                                                | jsonl transcript                               | **Degrade** — driver normalises to the canonical field shape, or supplies its own redactor; minimal tier = post-hoc transcript only                                      |
| **ControlVerbs**              | probe / interrupt / stop / reap / classify-error                                                                                                                     | PTY send-keys, Esc, signal, error-string table | **Degrade** per verb — reap (process kill) always works; probe/interrupt may be absent ⇒ the worker is fire-and-forget                                                   |
| **ToolProvisioning** (MCP)    | Inject MCP servers / tool defs                                                                                                                                       | none today                                     | **Unavailable** — not used in v1 for any driver; not a regression                                                                                                        |
| **PromptComposition**         | Driver supplies the agent-rules filename, the hook-enforcement wording, and the final-output convention; the body is shared                                          | CLAUDE.md template                             | **Refuse** if the driver supplies no instructions channel (every real CLI has one)                                                                                       |
| **AwaitingInputSignal**       | A positive "worker is blocked awaiting human input" signal, distinct from busy/idle — narrower than `ProgressObservation` itself                                     | `Notification`→`Stop` proximity                | **Degrade** — never Synthesize; Boss must not guess this state (see [Decision: AwaitingInput derivation](#decision-awaitinginput-derivation))                            |
| **CommandOutcomeObservation** | A positive per-command exit status, distinct from mere activity — the second capability carved out of `ProgressObservation` for the same reason as the row above     | `PostToolUse` tool response                    | **Degrade** — never Synthesize; Boss must not read a driver's silence as success (see the risk entry on `ProgressFidelity::Rich` below)                                  |

The enum in `engine/driver/src/lib.rs` matches this table; two rows carry names that differ from the prose above because the code name reads better in Rust: `ModelAndEffortMenu` (one capability, not the `ModelMenu + EffortMapping` pair the plan wrote) and `Capability::ToolProvisioning` for MCP. `Capability::all()` is the canonical iteration order the dispatch gate walks.

`UtilityModel` is the orthogonal capability (§1.8): "run a short background completion for the engine's own inference." It is **not** part of the worker `AgentDriver` — a Copilot work item still gets its live status summarised by whatever utility model the engine is configured with. Default stays Anthropic Haiku/Sonnet; the seam lets an operator point it elsewhere (or at the same provider as the work item's driver) without touching the worker path.

### The absence-policy model

Three dispositions, chosen _per capability per driver_, and resolved at dispatch:

- **Synthesize** — Boss manufactures the signal from a lower-fidelity channel the driver does have. Example: ProgressObservation under Copilot — parse `--output-format json --stream on` into `WorkerEvent`s (this is exactly P284's Q3). The activity machine never knows the difference.
- **Degrade** — Boss runs with reduced fidelity and records that it did. Example: 5-value effort collapsing onto a 3-value knob; coarse live status; post-hoc editorial. Degrade must `log()`/surface what was reduced, so a Copilot row that looks "coarser" is _known_-coarser, not silently broken.
- **Refuse** — Boss will not dispatch this work-item on this driver; it fails **at the dispatch gate, before the pane spawns**, with an actionable message (kanban shows `Errored`, not `Spawning` forever). Example: an editorial-required product dispatched on a driver with no ToolUseInterception, if the operator chose refuse-over-degrade for that surface.

The disposition is a property of `(capability, driver)`, with a per-kind escalation: a work-item _kind_ can mark a capability as **required-strict** (force Refuse on absence even if the default is Degrade). This is how "project_design stays Claude-only until validated" (P284 Q6) is expressed generically — `project_design` marks StructuredOutput + ToolUseInterception required-strict, so a driver lacking them is refused for that kind without a bespoke per-kind block.

### The trait surface as built

The plan described capabilities; the implementation had to pick concrete signatures, and several of them changed shape once a second driver's needs were held against them. The changes below are all _widenings_ — every one of them was made before a non-Claude driver existed, specifically so the seam would not need a second refactor when one arrived.

- **`spawn_invocation(SpawnRequest) -> SpawnPlan`.** The plan implied "produce the command line". The first signature was Claude-shaped positional parameters returning a bare `String`, with the engine wrapping it in a hardcoded `unset ANTHROPIC_API_KEY`. Both halves were replaced (mono#2355): `SpawnRequest` carries model, effort, settings path, the corp `non_opus_auto_mode` flag, an optional permission-mode override, and the run id; `SpawnPlan { env: Vec<EnvDirective>, command: String }` lets a driver own its environment as well as its command line. `EnvDirective` is `Set | Unset` rather than a `Vec<(String, String)>` precisely because Claude's requirement is to _unset_ a variable, which a set-only shape cannot express. The `unset ANTHROPIC_API_KEY` moved out of `pane_spawn.rs` into `ClaudeDriver`, and the engine renders whatever directives it is handed without knowing which driver produced them. Claude's rendered line is byte-for-byte unchanged.
- **`write_permission_config(...) -> PermissionArtifacts`.** The plan said "a place to express permission config" and the first signature returned a single `PathBuf` — which is Claude's `--settings` and nothing else. It now returns `PermissionArtifacts { config_files, extra_args, env }` (mono#1453), because a policy can equally be expressed as flags or environment rather than a file. `PermissionArtifacts.env` is also the single env-passing channel for permission config; `SpawnPlan.env` is the spawn-time one, and they were deliberately not allowed to become two competing mechanisms.
- **`progress_observation_wiring(...) -> ProgressIngress`.** The plan treated ProgressObservation as one seam with fidelity tiers. Implementation split the _transport_ out from the _fidelity_: `ProgressIngress::HookCallback(ProgressObservationWiring)` (Claude, fed by the unix events socket) versus `ProgressIngress::StdoutJsonl` (mono#2359). The transport distinction is not cosmetic — it is what the settings renderer branches on to produce an empty hooks map instead of panicking for a hookless driver, and what decides which ingress reader runs.
- **`turn_boundary(&WorkerEvent) -> Option<TurnEnd>`.** The plan named TurnBoundary a capability but the enum variant had no method behind it; completion, PR-URL capture, probe injection, effort-escalation parsing, and the Doing→Review transition all ran off `WorkerEvent::Stop` directly, a variant that exists only because Claude fires a `Stop` hook. `TurnEnd` carries `session_id`, `reason`, and `continuation` — the driver-agnostic name for Claude's `stop_hook_active` (mono#2361). The boundary is resolved **once, at ingress**: `IncomingHookEvent` holds it in a _private_ field populated only by `IncomingHookEvent::resolve(driver, …)`, so the compiler enforces that every event reaching a consumer went through a driver. `live_worker_state::apply_event` deliberately still matches `WorkerEvent::Stop` — that is the `ProgressObservation` surface, which consumes whatever stream a driver's normaliser produces and is driver-agnostic by construction.
- **`pr_url_capture_feed(...) -> PrUrlCaptureFeed`.** Not in the plan at all. Primary-path PR-URL capture read Claude's `PostToolUse` `tool_response.{stdout,stderr}` object shape directly in the engine, which finds nothing in a normalised stdout-JSONL stream where the equivalent is a bare `aggregated_output` string (mono#2378). What moved behind the seam is _what feeds the extractor_, not the extraction algorithm — the `gh`-command gates and URL regex stayed shared. Polling GitHub for a branch→PR mapping was considered and rejected as a substitute for a broken stream path.
- **`structured_output_wiring(StructuredOutputRequest) -> StructuredOutputArtifacts`.** Also a late addition (mono#2383): the fallback method alone described only how to _recover_ output, not how the designated result path reaches the agent. The trait default is the driver-agnostic env-file contract (`BOSS_STRUCTURED_OUTPUT` / `BOSS_PR_URL_OUTPUT`); a driver with native schema enforcement overrides it to add flags without another trait change. The request carries an **opaque** `schema: Option<serde_json::Value>` — this seam deliberately does not define a schema format. The env-file contract is _not_ conditional on the capability being declared; absence only drops the prose-scrape fallback.
- **`teardown_workspace(...)` + `DriverRuntimeState`.** A genuine gap in the original design: §1.2 enumerated provisioning surfaces and specified no counterpart, so a driver creating per-run state outside the cube workspace had nowhere to clean it up. `teardown_workspace` is now paired with `provision_workspace` and wired into **every** execution-termination path — normal completion, stop, all four reap sweeps, orphan/husk recovery, and app-crash reconciliation (mono#2346) — unconditionally, so a call site's own failure never skips it. It takes `workspace: Option<&Path>` because the workspace path is informational: `run_id` is the real key. `provision_workspace` then grew a return value, `Option<DriverRuntimeState>`, persisted to the new `work_executions.driver_runtime_state` column and reloaded at teardown (mono#2389). That column deliberately survives `clear_execution_workspace`, so orphan recovery and engine restart can still find a driver's recorded root after `workspace_path` is nulled. `ClaudeDriver` returns `None` and its teardown is a no-op: its only out-of-workspace state (the `~/.claude.json` trust entry, the tmp settings file) is keyed by a workspace directory name cube reuses across leases, so removing it per run would only force a rewrite.
- **Session identity widened in the protocol crate.** `normalize_hook_event` accepts `thread_id` as an equivalent alias for `session_id` (preferring `session_id` when both are present), and `SessionStartSource` gained `Clear` (mono#2342). The alias is not cosmetic: a driver can report the _same_ identity under `session_id` on a hooks channel and `thread_id` on a streaming channel, and a mapping written against one channel must not silently diverge from the other. `session_id` stays a plain `String` on every `WorkerEvent` variant — no tagged union, no driver-identity prefix.

Two ingress transports now converge on one fan-out. `boss-engine-stdout-progress` frames newline-delimited JSON off any `AsyncRead` (a child's stdout, an SSH channel, a test pipe) and normalises each envelope through the **injected** driver, with a pull-style cursor so the consumer paces the reader and no intermediate queue can drop or reorder (mono#2363). Every stream anomaly — unknown envelope, interleaved non-JSON, split reads, invalid UTF-8, a line over 1 MiB, an I/O error — is counted in `ReaderStats` and skipped, never fatal: a reader that panics on an unannounced field from a process Boss does not control is strictly worse than one that reports nothing. `dispatch_worker_event_fanout` is the socket accept loop's per-event body, extracted verbatim, and both ingresses call it, so by the time an event reaches the activity machine the transport that carried it is no longer observable.

### Genuinely divergent areas — how the model copes

- **Hooks (no analog).** The hardest surface. Resolved by making ProgressObservation a _capability with fidelity tiers_ and a **Synthesize** default: Claude provides the rich tier from its hook stream; a hookless driver provides whatever it has (JSON stdout, log tail, or process lifecycle) and Boss synthesises the same `WorkerEvent` stream. ToolUseInterception is the part of "hooks" that _cannot_ be synthesised after the fact (you can't un-run a `gh pr create`); that one degrades to post-hoc or refuses.
- **Permissions (different grammar).** PermissionPolicy is an _abstract_ policy (a deny-set + an autonomy mode), rendered by the driver. Claude renders settings.json; Copilot renders `--deny-tool` filters; the structural minimum (bossctl, state-dir) is refuse-on-absence so a driver that can't enforce it is never dispatched.
- **Transcript format (different shape).** TranscriptAccess requires the driver to _normalise to_ the canonical field names the redactor already knows (`tool_name`/`tool_input`/`tool_response`/`content[].type`) — the field-name compatibility shim lives in the driver, in the one place it matters, so `live_status_redact.rs` is unchanged.
- **Structured output (different mechanism).** Resolved by _moving the primary mechanism off the transcript entirely_ (T1414): the worker writes structured output to a known file. Every driver can write a file; only the Claude driver also keeps the transcript-sentinel fallback. This is the single most decoupling-friendly change and should land early.

## Mix-and-match & rollout

### How a driver is chosen and recorded

It mirrors the existing `model_override` machinery exactly, and shipped that way:

- **`tasks.driver TEXT NULL`** — per-row explicit choice (constrained in code to the registered driver names, no SQL `CHECK`, same as `model_override`).
- **`products.default_driver TEXT NULL`** — per-product default.
- Precedence: `task.driver` → `product.default_driver` → engine default (`claude`, `effort::ENGINE_DEFAULT_DRIVER`). The same three-step resolution is used by the spawn path, by post-hoc interception dispatch, and by teardown, so a run cannot resolve one driver at spawn and a different one at cleanup.
- CLI: `--driver` / `--unset-driver` on the task and chore create/edit verbs; `--default-driver` / its clearing flag on `boss product edit`. `--driver <non-claude> --model <claude-slug>` is rejected at CLI-parse time.

The runtime lookup is `DriverRegistry`, a slug → `Arc<dyn AgentDriver>` map with a single `require(slug)` helper returning `UnknownDriverSlug` rather than panicking. `require` is what every call site uses — there is no per-site `match` on slug anywhere in the engine. This mattered more than it sounds: for a period the trait, capability model, registry, and resolver all existed while the engine still constructed a concrete `ClaudeDriver` at provision, spawn, settings-render, and workspace-write time, so a second registered driver could pass the dispatch gate and then be spawned as Claude. mono#2385 closed that by routing every one of those sites (plus the remote host adapter's settings render and `SpawnConfig`'s invocation helpers) through `require`, with a stub non-Claude driver in tests proving the registered driver's methods are the ones invoked.

An unregistered slug is an **error, not a silent fallback to Claude** (mono#2347). `menu_for_driver_in` returns `Result<ModelMenu, UnknownDriverError>` and `resolve_spawn_config` propagates it, so `compose_worker_spawn` bails before a pane ever spawns. The bug that forced this is worth remembering: `menu_for_driver` took a driver slug and ignored it entirely, so a non-Claude work item resolved its effort level against Claude's model table and produced Claude model slugs — a silent, plausible-looking wrong answer. The same change renamed `SpawnConfig.claude_effort` to `effort_value` (the struct is driver-generic), including the `"claude_effort"` → `"effort_value"` dispatch-stream JSON key, which was verified to have no external consumers first.

This is the same column the [Copilot backend design](copilot-cli-as-alternative-worker-backend.md) calls `backend`. **`driver` is canonical** (the abstraction is "driver"; "backend" reads as a global mode), and that is what shipped in the schema, the CLI, and the trait names. That design, being downstream, adopts it.

### How effort→model resolves per driver

`effort.rs`'s single global table became **per-driver**. Each driver's `descriptor()` carries its own `ModelMenu` — model menu, effort→knob table, effort→default-model table, and family classifier, all as function pointers so the menu can live in a `static DriverDescriptor`. `resolve_spawn_config` keeps its precedence (row → pool → effort-default → product-default → engine-default) but resolves _against the selected driver's menu_:

- **Claude:** today's tables verbatim (5-value effort, sonnet/opus, opus⇒auto-mode).
- **Copilot:** gpt/opus/sonnet menu, 3-value effort (the 5→3 degrade), `--no-ask-user` autonomy.
- **Codex:** its own menu, later.

`model_override` is validated against the _resolved_ driver's menu at CLI-parse time: `--driver copilot --model claude-opus-4-7` is rejected with a clear "that's a Claude slug" message (P284's Q1 rule, generalised).

One limit the implementation surfaced and did not fix: `ModelMenu::effort_value_for_level` is typed against Boss's 5-variant `EffortLevel`, so a driver whose CLI exposes a **longer** ladder is reachable only through its top five — the type cannot express more. The plan only ever anticipated collapsing a longer Boss vocabulary onto a shorter driver knob (5→3), not the reverse. This is documented on the field itself in `driver/src/lib.rs`; it is a vocabulary ceiling, not a bug, and no shipped driver hits it yet.

### Migration shape

1. **Claude became the reference driver, behaviour-preserving.** The extraction was the bulk of the work and had to be byte-for-byte: the spawn line, the `.claude/` files, the deny rules, and the hook wiring all moved behind the trait without changing output.
2. **A conformance harness proves the equivalence claim** rather than asserting it (mono#2391, `engine/core/src/conformance/`). It ended up broader than the plan's "golden tests over the Claude renderers", because byte-for-byte Claude goldens only prove the reference driver did not regress — they say nothing about whether the seam is actually driver-neutral. It covers four surfaces: (a) Claude goldens for the spawn line, `settings.json`, `CLAUDE.md`, and deny rules, produced _through_ `&dyn AgentDriver`, with host temp paths normalised so the snapshot is portable; (b) **ingress equivalence** — paired session fixtures (Claude hooks vs. stdout JSONL) decode to the _same_ `WorkerEvent` sequence through `normalize_progress_event`, asserted at field-level `PartialEq`, not just event-kind order; (c) **boundary equivalence** — a hook-fired `Stop` and a native turn-completion event produce identical `TurnEnd` values and both drive the registry to `Idle`; (d) **version pinning** against the external CLI the fixtures came from, tolerating additive fields and unknown variants but failing loudly on a semantic change. A driver-shaped test double supplies the non-Claude side until a real driver lands.
3. **Concrete non-Claude drivers are separate projects** on the now-existing interface — the Copilot design's `CopilotDriver`, and the Codex and Grok driver projects, each declaring its own capability set and riding the absence policies.

No existing row has a `driver` value; NULL resolves to `claude`; existing dispatches are a no-op. There was no global switch at any point.

## Risks / open questions

- **Column name `driver` vs the Copilot design's `backend` — RESOLVED.** `driver` shipped, in the schema (`tasks.driver`, `products.default_driver`), the CLI flags, and the trait vocabulary. The downstream doc inherits it.
- **ToolUseInterception absence policy is a security-adjacent choice — still an operator call, but the degrade path is no longer dead.** [Editorial controls](editorial-controls-for-agent-authored-prs-and-github-comments.md) exist so Boss is safe in environments where leaking internal taxonomy is unacceptable. A driver with no PreToolUse interception can only do _post-hoc_ editorial (create the PR, then detect-and-request-edit), which has a window where un-redacted text is live on GitHub. Whether that degrade is acceptable, or whether editorial-required products must **refuse** non-intercepting drivers, remains an operator policy decision, not an engineering default. What changed is that `Degrade` now degrades to something rather than to nothing: `PostHocInterceptionFn` / `PostHocInterceptionAction` had been designed and landed with **zero engine callers**, so any driver resolving to `Degrade` silently lost editorial enforcement, the path guard, the revision-PR guard, and the checkleft push guard — not gracefully, entirely, with no signal (mono#2358). `dispatch_post_hoc_interception_on_post_tool_use` now runs in the `PostToolUse` loop, resolves the execution's driver by the same precedence used at spawn, and for a driver that actually lands on `Degrade` logs exactly which guards were skipped and that post-hoc review can only detect, never prevent. That warning fires **once per execution**, not per tool call. Crucially it also fires for a slug that is not in the registry at all, which is today's only way to reach the path — the loss of guards is never silent for any driver that can get there, registered or not. Claude early-returns before any of it, having real hooks. No shipped driver registers a post-hoc adapter yet.
- **UtilityModel decoupling: v1 or deferred?** The four direct-Anthropic call sites (§1.8) are independent of the worker driver. Decoupling them behind a `UtilityModel` provider seam is valuable for air-gapped / no-Anthropic-key environments but is _not required_ to ship mix-and-match worker drivers. Including it widens v1; deferring it leaves a hardcoded Anthropic dependency in the engine's own inference. **Resolved: shipped**, as a standalone seam per [the decision below](#decision-utilitymodel-shape-and-ownership) — `boss-engine-utility-model`, with the default provider preserving today's endpoint and models (§1.8). No call site moved off Claude.
- **ProgressObservation minimum-fidelity tier — decided.** Was: "if a driver gives only process-alive/exited (no per-turn signal), the stale-worker sweep may misfire (it keys on hook cadence); needs a decision before a minimal-tier driver ships." Resolved by `docs/investigations/codex-progress-channel-decision-2026-07-24.md` (Codex's progress channel is stdout JSONL, not hooks — making this Codex-critical-path, not hypothetical) plus the liveness-contract implementation it unblocked: `ProgressFidelity::stale_threshold_secs` (`engine/driver/src/lib.rs`) derives the sweep's cadence threshold from the driver's declared tier — `Rich` (Claude, and any stdout-JSONL driver whose stream carries the same per-tool boundary, e.g. Codex's `item.started`/`item.completed`) reuses today's 30-min threshold unchanged; `Coarse`/`Minimal` are exempted from cadence judgement entirely (no per-tool boundary to guard a long turn, so no threshold can be picked without guessing) and fall back to `dead_pid_sweep`'s process-liveness backstop — exactly the "hold `Working` while alive, exempt from the staleness sweep" behaviour this risk called for. A blanket exemption for "stdout-JSONL drivers" as a class was considered and rejected: it would exempt a `Rich`-tier Codex driver too, reintroducing the "genuinely hung Codex worker is never swept" failure mode. `stale_worker_sweep.rs`'s module doc ("Non-`Rich`-tier drivers" section) and `ProgressFidelity::stale_threshold_secs`'s doc comment carry the full reasoning and the rejected alternative.
- **Stop-reason richness loss — RESOLVED, see below.** ~~`AwaitingInput` is derived from `Notification`→`Stop` proximity (Claude-specific). Drivers run autonomous (Copilot `--no-ask-user`) and never emit it; a wedged autonomous worker shows `Working`, not `WaitingForInput`. Acceptable, but the "Working > N min, no events ⇒ flag" heuristic should be the generic replacement.~~ Superseded — see [Decision: AwaitingInput derivation](#decision-awaitinginput-derivation). The "Working > N min ⇒ flag" replacement floated here was rejected: it would be a guess, and the chosen resolution's hard constraint is that Boss must never fabricate this state.
- **Conformance harness scope — RESOLVED, and widened.** The harness shipped and gates the extraction, but "golden tests over the Claude renderers" turned out to be the smaller half of what was needed; see [Migration shape](#migration-shape) for the four surfaces it actually covers. The load-bearing addition is cross-transport equivalence: Claude goldens prove the reference driver did not regress, and only the ingress/boundary equivalence tests prove the seam is driver-neutral.
- **Error classification is Anthropic-specific** (`transient_error.rs`). `classify_error(&self, raw_output) -> WorkerErrorClass` is now a trait method, so the seam exists and Claude's Anthropic-string table sits behind it; each driver still needs its own table, or recovery degrades to "no auto-resume". Low-risk degrade, still named.
- **Remote/SSH driver-awareness — still open, and now the one place a hardcoded `ClaudeDriver` survives on a production path.** mono#2385 routed every _local_ spawn-time construction site through the registry, but the remote virtual-slot registration (`app/worker_events.rs::register_remote_worker_slot`) still falls back to the literal model label `"claude"` and reads `ClaudeDriver.capabilities()` for the `AwaitingInputSignal` flag rather than the run's resolved driver. Separately, structured-output artifacts are written to the _local_ system temp dir (`<temp>/boss-worker-output`), so a remote worker's artifacts are never fetched across the SSH boundary and remote runs still resolve structured output through the driver's prose fallback alone. [Remote execution](distributed-agent-execution-register-and-dispatch-to-remote-ssh-hosts.md) must carry the driver across that boundary; this is a dependency for remote + non-Claude.
- **The per-slot `ProgressFidelity` side-map does not survive an engine restart.** It is deliberately in-memory only (`live_worker_state.rs`) and is not on the `LiveWorkerState` wire struct, because it has no UI consumer — only the sweep's. The consequence is that an engine restart while a worker is alive loses the declared tier and the slot re-defaults to `Rich`, which would subject a `Coarse`/`Minimal` driver's live worker to cadence-based staleness judgement it is meant to be exempt from. Harmless while Claude is the only tier-`Rich` driver actually dispatching; a real gap the moment a lower-tier driver ships.
- **`ProgressFidelity::Rich` conflated cadence with per-command outcome — RESOLVED.** Surfaced by the Codex driver's gap analysis (`codex-as-a-first-class-agent-driver.md`, [G-5's reconsideration](codex-as-a-first-class-agent-driver.md#g-5-progressobservation--the-top-gap)): `Rich` correctly measures event cadence (a start/end boundary around every tool call), but Codex's declaration of it read as if that also implied a reliable per-command exit status. It does not — Codex's rollout `exit_code`/`status` fields are only sometimes present, can be dropped by the model's own result-projection layer, and become unparseable after truncation, and Boss's normaliser never read them anyway. `Capability::CommandOutcomeObservation` now carries that narrower claim on its own (`engine/driver/src/lib.rs`), declared by Claude and left undeclared — `Degrade`, never `Synthesize` — by Codex and Grok. This is the same shape as the `AwaitingInputSignal` capability below it: a driver can have a genuinely good event stream while lacking one specific signal that stream doesn't carry. It is also the seam a future cross-driver load balancer will need: a normalised per-command outcome must be tri-state (succeeded / failed / unobserved), because Codex's unobserved state has no Claude counterpart and collapsing it into a boolean would read Codex's silence as success.

### Decision: UtilityModel shape and ownership

A previously filed chore to route utility LLM calls through the driver was worded as calling for "a `UtilityModel` trait method on `AgentDriver`". That contradicts this doc's position above (§"Capabilities" table, and the diagram in "The shape") that `UtilityModel` is explicitly **not** part of `AgentDriver`. This section is the resolution, recorded here so the next reader hits the decision before the contradiction.

- **Shape chosen: a standalone `UtilityModel` provider seam, independent of `AgentDriver`.** Not a trait method on the driver, not a driver capability with an absence policy, not plain unstructured configuration either — the four call sites (§1.8) share enough surface (endpoint, auth, model slug, prompt/response shape) that a small independent trait plus config-driven selection is warranted, but that trait has its own lifecycle and does not live on the `AgentDriver` object or get resolved through the `CapabilityResolver` dispatch gate. The diagram in "The shape" above already draws this correctly (`Orthogonal axis: trait UtilityModel`); the deferred chore's wording did not match it.
- **The operator's utility-model choice can differ from the worker's driver — yes, by design.** This is the question that decides the shape, and the answer is unambiguous: a work item dispatched on `CodexDriver` (or `CopilotDriver`) must still be able to get its live-status summary, pane title, magic-wand edit, and attentions extraction from Claude Haiku/Sonnet, because those four call sites are short, frequent, interactive-path helper calls with a cost/latency profile that has nothing to do with which CLI is doing the agentic work. Coupling the two would mean an operator who moves a worker to Codex involuntarily also loses (or must separately re-route) the engine's own inference — that's the wrong default. Independent axes, independently configured.
- **Ownership: this design, not the Codex driver design, and not "neither."** `UtilityModel` is already listed under this doc's own "Future / not a v1 blocker" task breakdown (`UtilityModel` provider seam, "Dependencies: none structural") — it was scoped here from the start, just not flagged as the authoritative answer to the contradiction until now. The Codex driver design's capability gap table covering only the 13 `AgentDriver` capabilities and omitting `UtilityModel` is **correct, not a gap**: `UtilityModel` is not an `AgentDriver` capability, so a driver's capability declaration has nothing to say about it. The Codex driver design does not need a `UtilityModel` row and should not grow one; if a reader lands there looking for it, this section is the pointer back to this design.
- **What was built (this decision, delivered).** `boss-engine-utility-model` — a `trait UtilityModel` yielding endpoint + model + credential per `UtilityTask`, plus config-driven provider selection off `BOSS_UTILITY_MODEL_PROVIDER`. It does not hang off `AgentDriver` and is not consulted via the capability resolver. `live_status.rs`, `pane_summary.rs`, `attentions_detector.rs`, `planner.rs` and `comment-classifier` all resolve through it (`magic_wand.rs` had been retired by then — see §1.8). Model selection is **per task**, so an operator can put the kanban subtitle on a tiny model without dragging the Planner's Opus call along. The default provider returns exactly the prior endpoint and pinned models, so behaviour is unchanged; an unset or unrecognised `BOSS_UTILITY_MODEL_PROVIDER` falls back to that default and says so in the log rather than defaulting silently.
- **What the deferred chore's Deliver section should say instead:** route the four call sites (`live_status.rs`, `pane_summary.rs`, `magic_wand.rs`, `attentions_detector.rs`) through a standalone `UtilityModel` provider seam — a small trait plus config-driven provider selection, scoped and owned by this design — instead of a method on `AgentDriver`. The seam must let the operator's utility-model choice vary independently of any work item's `driver`/`backend` value. The chore remains deferred per its existing annotation and, per its own constraints, keeps every call site on Claude when it does eventually implement the seam — only the shape (independent seam vs. driver method) changes, not the model choice.

### Decision: AwaitingInput derivation

The "Stop-reason richness loss" risk above asked how `AwaitingInput` — the state that renders a worker as "waiting for input" rather than "working" — should be derived for a driver that isn't Claude, since the existing mechanism (a `Notification` hook immediately preceding `Stop`) is Claude-specific. The [`codex-progress-channel-decision-2026-07-24`](../investigations/codex-progress-channel-decision-2026-07-24.md) investigation settled the premise this was blocked on and added a Codex-specific reinforcement: `codex exec` is one turn per process, so a follow-up or probe is a _new process_ (`codex exec resume`), not an injected message into a live session — there is no live "the worker is now blocked awaiting a human" state for a signal to attach to at all, regardless of which channel carries progress. `Notification` also was not observed in that investigation's hook reproduction (stated as "not observed here," not "does not exist" — the config surface can't confirm or rule out the event).

- **Chosen: a new capability, `Capability::AwaitingInputSignal`, absence-Degrade (never Synthesize).** This mirrors how every other Part-1 finding is mapped onto the interface rather than left as an incidental property of the event stream. A driver declares the capability if — and only if — its `ProgressObservation` stream can positively signal "blocked awaiting human input" as distinct from busy/idle; `ClaudeDriver` declares it (`Notification`→`Stop` proximity, unchanged). The default absence disposition is **Degrade**, deliberately not Synthesize: the risk register's own suggested fallback ("Working > N min, no events ⇒ flag") was rejected because it is a guess, and guessing this specific state is the one thing explicitly ruled out — an operator acts on `WaitingForInput` as "I am the bottleneck," and a false positive from a staleness heuristic is worse than an honest `Working`.
- **Rejected: deriving it from Codex's native turn semantics.** `turn.completed` is a strictly better _turn-boundary_ signal than Claude's `Stop` hook (see the investigation and the `TurnBoundary` row), but it carries no "the process is now blocked on a human" bit — under `codex exec`, an ended turn just means the process is about to exit. There is nothing in Codex's stream this capability could honestly bind to yet; a real Codex driver simply omits `AwaitingInputSignal` from its declared set and Boss degrades.
- **Implementation shape.** `engine/core/src/live_worker_state.rs` consults a per-slot `awaiting_input_capable` flag at **both** places the engine can produce `WaitingForInput`: `apply_event` (the `Notification`→`Stop` proximity interpretation) and `mark_stalled_spawns` (the 30-second no-hook-events-since-spawn stall detector, run in production by the sweep in `app/server.rs`). The flag is seeded `true` by `register_spawn` so the ~30 existing test call sites keep working unchanged; the two production spawn sites — local pane spawn in `spawn_flow.rs` and the remote virtual-slot path in `app/worker_events.rs::register_remote_worker_slot` — instead call `register_spawn_with_capabilities`, passing the resolved driver's `CapabilitySet` value for `Capability::AwaitingInputSignal` directly into registration (no follow-up setter call, so there is no window where a concurrently delivered hook event could be evaluated against the seeded default). When the flag is `false`: a `Notification` event (however it arrived) is _not_ interpreted as an awaiting-input signal in `apply_event` — activity is left untouched, so `Stop` falls through to `Idle` as it would for any ordinary turn boundary; and `mark_stalled_spawns` leaves the slot in `Spawning` rather than promoting it, since the honest fallback for a slot this stalled sits with `dead_pid_sweep`'s process-liveness backstop, not a fabricated `WaitingForInput` (see the "ProgressObservation minimum-fidelity tier — decided" risk above). When this landed both production spawn sites still hardcoded `ClaudeDriver`, so the flag resolved to `true` everywhere in practice. The local site (`spawn_flow.rs`) has since been cut over and reads the resolved driver's `CapabilitySet` — the same commit also declares that driver's `progress_fidelity()` to the registry, so both per-slot flags now follow the driver rather than a constant. The remote virtual-slot site still reads `ClaudeDriver.capabilities()`; see the "Remote/SSH driver-awareness" risk above.
