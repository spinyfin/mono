# Completion contract: declarations end executions independently of deliverable acceptance

- Date: 2026-09-11
- Status: proposed design; implementation has not started in this change
- Provenance: Completion contract: one state machine, fewer terminalization paths
- Source baseline: `bcd7c69c2946d2b3744b05bf020916779e2b4ec8`
- Related design: [Worker proposal API](worker-proposal-api-replace-fragile-worker-to-engine-seams.md), particularly the declaration rationale introduced by mono#2622
- Reconciled with: [Host suspension awareness](https://github.com/spinyfin/mono/pull/2930) (mono#2930), written in parallel without either author seeing the other; the decisions that reconciliation left on this side are recorded in [Reconciliation with the host-suspension design](#reconciliation-with-the-host-suspension-design)
- Settled prerequisite: the in-flight change making `run_done` terminal at submission and accepting both live execution statuses

**An accepted terminal declaration ends the execution even when its deliverable cannot yet be verified.** Completion promises that the worker is finished and its resources will be relinquished; it does not certify that its PR, review, or answer is correct. This distinction permits one terminal transition implementation and removes evidence-dependent termination branches.

## Verdict

Replace the ten inventoried terminalization families with **one guarded database transition and one resource cleanup sequence**. Keep explicit declarations required for successful worker completion, delete PR-health and Stop-only completion, and move remaining deliverable decisions to their existing owners after termination. Target **100–150 KB net production code removed**, including changes outside `completion/`; moving code between files does not count as removal.

## Goals

- Reduce paths and code, rather than introduce a state-machine framework over existing finalizers.
- Specify every execution state and legal transition, terminal authority, signal response, and resource obligation.
- Make a valid declaration sufficient to end a run without another Stop, a GitHub request, or an active `work_runs` row.
- Preserve the protection against terminating a worker midway through investigating an already-green PR.
- Make lost completion ingress, duplicate signals, crash recovery, and release failures observable through contract tests at the real engine boundary.

## Non-goals

- Implementing this design in this PR, rewriting Boss, or redesigning scheduling, review, automation, or proposals beyond their completion seams.
- Adding a general transition framework, a new reconciler, a second durable queue, a compatibility finalizer, or a feature flag.
- Removing useful liveness detectors merely to make a caller count smaller. Detectors establish facts; they must cease implementing independent terminal writes and cleanup.
- Implementing host sleep/wake detection, clock sources, or the suspension ledger, or repairing the SHA-delta probe's retry policy. mono#2930 owns all of those, including the bounded retry on the acceptance-side `gh` fetches; this design consumes its awake-time primitives and removes that probe's authority to hold an execution open.
- Redesigning Cube lease expiry, remote execution transport, or the application pane model. Completion must use their existing ownership and acknowledgement mechanisms honestly.
- Treating every worker proposal as terminal. Follow-ups, blockers, and scope records can be submitted during ongoing work.

## Chosen approach

### Execution identity, declarations, and acceptance

An execution is one authorized worker lifetime, including acquisition and startup. A `work_runs` row records a runner invocation: pane spawn may already have finished that row while the execution is still live. These are equivalent only for a synchronous runner whose invocation owns the entire worker lifetime. The terminal operation closes any open invocation rows but never requires one to exist, and preserves the timestamps of invocations already closed.

A **terminal declaration** is an execution-scoped, validated statement by its worker that it has finished. `run_done` is the canonical durable representation. A sanctioned final-result submission may write that declaration in the same local transaction; PR health, a changed SHA, elapsed time, a comment discovered by a sweep, and plain Stop may not manufacture one.

`completed` means the worker declared `delivered` or `no_changes_needed`, not that the linked task is accepted or merged. A task's `done`, review admission, CI remediation success, conflict clearance, and review verdict application retain their existing domain owners. A terminal execution cannot be revived because its deliverable subsequently fails review; a new authorized execution handles additional work.

Local declaration validation checks caller identity, execution ownership, outcome vocabulary, and payload shape. It must not require a PR URL to have been discovered or verified, a changed SHA, a nonempty diff, clean CI, an extant task row, or a network-accessible artifact. Missing evidence becomes a visible unresolved deliverable, never a reason to retain the worker. No-op declarations preserve the fact that a revision finding was declined; they cannot mark an unresolved parent conflict or CI remediation successful.

### Complete execution state machine

The resulting runtime has **11 states**, down from 13. No `finishing`, `verifying`, or `cleanup_pending` execution state is added. Resource acknowledgements and work acceptance are properties with their own existing storage, not extra execution states.

| State                | Live?        | Required invariant                                                                                                                                                                           |
| -------------------- | ------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `queued`             | No           | Awaiting admission evaluation; no authorized worker or acquired resource ownership.                                                                                                          |
| `ready`              | No           | Admitted for dispatch; no worker or resource ownership yet.                                                                                                                                  |
| `waiting_dependency` | No           | Prerequisite prevents dispatch; no worker or resource ownership.                                                                                                                             |
| `claimed`            | No           | Exactly one scheduler claim owns acquisition/startup; slot or lease acquisition may be in flight. No second dispatcher may reconcile it back into the queue.                                 |
| `running`            | Yes          | Worker lifetime is authorized, including the committed startup window; may be thinking, doing tools, or between turns. Absence of a Stop is immaterial.                                      |
| `waiting_human`      | Yes          | Same resource ownership as `running`, with an explicit request for human/coordinator input. This is not an engine handoff, review wait, or completion park.                                  |
| `completed`          | No; terminal | Durable successful terminal declaration; outcome/summary and `finished_at` exist. No permission for further work. Acceptance may remain unresolved.                                          |
| `failed`             | No; terminal | A definite fatal runtime/startup failure, with durable reason and `finished_at`. Not a negative review verdict or a failed evidence fetch.                                                   |
| `abandoned`          | No; terminal | Deliberate end without a success claim: declared blocker, exhausted idle question, redundant/pending work withdrawal. Durable reason; operator-required cases suppress automatic redispatch. |
| `cancelled`          | No; terminal | Authorized cancellation of this lifetime, with durable actor/reason and `finished_at`.                                                                                                       |
| `orphaned`           | No; terminal | Execution's actual worker or workspace ownership was positively lost, with identity-scoped evidence and reason. No valid declaration or definite fatal result was accepted first.            |

Cleanup may be retried without rewriting terminal state.                                                                                                                     |

The scheduler's retry counter, host selection, and dependency policy remain its own; it cannot bypass the queue ownership invariants. A worker that encounters a new dependency after starting either pauses for input or ends this execution with a blocker. Scheduling the remaining work creates a new execution instead of returning a resource-owning live execution to a queue state.

`waiting_review` and `waiting_merge` are removed as execution states: a worker can be live while doing review-related work, or terminal while its task waits for review/merge. These waits belong to the task/PR. Delete their `RunWaitState` variants and caller arms rather than serialize new executions into them.

`readopt_inferred_terminal_execution` currently reverses `orphaned` (`work/executions_runs.rs:232–310`). That is a real existing exception to absorbing terminal states, not something this design overlooks. Remove the reversal: uncertain workers remain nonterminal and may have their registry/transport reattached using existing recovery code; confirmed terminal workers are fenced and cleaned up. This changes the _precondition_ for orphaning, not merely a test asserting that revival is forbidden. It preserves the duplicate-dispatch protection for an alive worker whose acknowledgement was lost.

### One terminal writer, one resource owner

Replace the terminal body of `finish_execution_run` in place. Its final form accepts an execution identity and a closed, typed terminal cause, derives status from the table, and performs the transaction. It has no caller-supplied arbitrary execution status, `clear_workspace_lease` switch, active-run requirement, or injectable callback. Keep a private transaction-level form so proposal application and dependency cancellation can include their small local writes atomically; this is the implementation of the same operation, not another policy entry point.

The successful transaction must:

1. Read and guard the execution state and signal ownership. For a terminal row, return its existing receipt without overwriting its outcome or timestamp. A replay still requests cleanup.
2. Persist the declaration or forced-terminal reason and `finished_at`, close open `work_runs`, and stage the existing `ExecutionTerminal` event through `PendingEvents` / `commit_and_publish`.
3. Commit any mandatory local disposition: declared-blocked or undeclared-idle attention and redispatch hold, accepted batch-member/result reference, and no-op reason. Missing/deleted work items do not prevent the execution transition. Retain the execution-scoped reason when a work-item projection is impossible.
4. Preserve identifiers needed to clean up resources until their release is acknowledged. On a terminal row, lease/workspace columns describe a **release obligation**, never authority to renew or do work. Do not null them merely to claim ownership of an in-memory cleanup attempt.

Reuse `WorkerCompletionHandler`, its teardown registry, `finish_worker_teardown`, existing durable run identity, and the existing terminal-work sweep. Merge `force_release` and caller-specific teardown tails into that sequence. Run-row bookkeeping for a successful pane spawn remains in the coordinator but loses the ability to write a terminal execution status. Delete each replaced terminal writer and its bespoke tail in the PR that migrates its callers; do not retain forwarding APIs for compatibility.

The transaction and its success response contain **no network-capable operation**. In particular, do not call a merge probe, `gh`, SSH, artifact collection, a host adapter, `CubeClient::release_workspace`, or pane RPC there. A local CLI is not proof of locality: `HostAdapterCubeClient::release_workspace` delegates to an adapter (`host_adapter.rs:1377`), which can be remote. Frontend delivery and cleanup run independently after commit; neither is awaited to decide or acknowledge terminality.

The existing terminal-work sweep also supplies the immediate cleanup wake and restart recovery, using its same cleanup function. The durable candidate is a terminal execution with remaining lease/workspace or runtime ownership, including rows without a current in-memory slot. This replaces its execution/work-item-specific terminalization and teardown branches. Do not create a new completion reconciler or terminal decision queue. The ordinary call requests immediate execution of the same cleanup; the existing periodic pass recovers a dropped wake or engine crash.

An execution's cleanup attempt must have one in-process owner across direct wake, replay, and sweep. Narrow the existing teardown registry into an atomic try-acquire for that purpose: its current `begin` refreshes a timestamp and assumes terminal-write losers never run cleanup (`teardown_registry.rs:107–130`), which is insufficient once replay is allowed to request it. Expiry must cancel/settle the bounded attempt before another owner proceeds. Release/clear writes compare the recorded lease or runtime token, following `work/run_rows.rs:1257`'s existing tmux identity-clear precedent; they never erase a successor's identity. Historical PID/summary fields remain history, not permanent cleanup candidates: clear active runtime ownership after verified release and use existing identity-validity checks before signaling any process.

### Resource release contract

Execution terminality, stopping the process, and making a physical slot/workspace reusable are different facts. Clearing a database field or dropping a registry entry is not equivalent to proving a process dead or an app pane free. This matters today: `app.rs:1843–2105` deliberately retains a pool claim without pane acknowledgement, and documents that a timer-only handback can cause repeated `SlotBusy` failures.

| Boundary                                     | Pane/process                                                                                                      | Slot/capacity                                                                                                                   | Cube lease/workspace                                                                                                                                                         |
| -------------------------------------------- | ----------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Terminal transaction commits                 | No further work, probe, or late-spawn registration is authorized. Cleanup is durably recoverable.                 | Execution ceases to be admitted as live; an occupied physical slot is marked unavailable until release is proven.               | No new heartbeat is authorized. Lease identity remains available for cleanup; it is not erased on attempt.                                                                   |
| Normal cleanup succeeds                      | Reap the identity-checked worker tree / tmux session and obtain pane removal or verified absence.                 | Compare-and-release the matching claim, then kick scheduling. Never release a successor's claim.                                | After process cessation and driver-state handoff, release the matching lease on its owning host; clear resource columns only after acknowledgement or authoritative absence. |
| Cleanup attempt fails or host is unreachable | Execution stays terminal. Record the failed phase; retry existing cleanup, never ask the worker for another Stop. | An unconfirmed physical slot stays unavailable, with an execution-scoped attention; do not advertise occupied capacity as free. | Retain durable release identity, stop renewal, and retry. Cube TTL is a disaster backstop, not the normal release guarantee.                                                 |
| Engine crashes/restarts                      | Existing terminal-work recovery finds the durable identity and repeats the same sequence.                         | Reconstruct or inspect actual ownership before reuse; registry loss alone is not release evidence.                              | A crash between remote acknowledgement and local clear is safe: retry release of that lease ID, then clear.                                                                  |

Preserve the useful existing order: worker cessation → driver credential/state teardown → workspace release. Do not release a workspace that a still-starting worker can subsequently occupy. Cancellation during `claimed` fences the startup owner; that owner settles any in-flight acquisition, reaps any late process, and submits its acquired identities to the same cleanup. The `NoLiveWorker` case must distinguish verified absence from an unresolved spawn; it is not unconditional permission to release.

An accepted declaration guarantees durable terminality on the submission transaction, independent of cleanup latency. The normal cleanup attempt starts immediately without waiting for PR observation or Stop. If that wake is lost, the existing 60-second terminal-work sweep must pick it up on its next runnable pass; the old two-pass heuristic is unnecessary for an explicit terminal decision. Each external cleanup operation has a foreground deadline; retain the existing 120-second Cube release bound and the pane/process bounds, and apply bounds to the remaining unbounded release calls. A timeout records pending cleanup and leaves identity intact for the next pass.

The worker may be stopped as soon as its terminal declaration is accepted, including before it prints a final sentence. It must complete pushes, writes, and reports first and must never need the next turn to trigger release. A successful CLI reply certifies the durable terminal outcome, **not** remote pane removal or deliverable acceptance. If the connection closes before the reply, the outcome is unknown to the caller; retrying the same declaration retrieves the receipt and re-requests cleanup.

No distributed design can guarantee that an unreachable or suspended host kills a process within a wall-clock deadline. During host/engine suspension, obligations persist and progress resumes on the first runnable cleanup pass. An in-flight pre-terminal heartbeat may finish once; no later renewal may be scheduled. Existing `LEASE_TTL_SECS` is 86,400 (`cube_lease_heartbeat.rs:389`); expiry does not prove the old process stopped. Keep that workspace/host unavailable to replacement work until the existing owner checks can establish safe reuse. The healthy-host release guarantee and failure attention must be tested separately; silently retaining an admitted worker slot and renewed lease for hours is prohibited.

**Existing final-result submissions are explicit declarations, not health exceptions.** A valid review report/verdict accepted for its batch member already definitively ends that member (`app/proposals.rs:377–404`). Preserve that behavior by writing its `run_done=delivered` declaration in the same transaction as report acceptance, then using the common terminal write. Verdict application may remain asynchronous. Likewise, final answer submission and `automation-outcome` can atomically record their result and the declaration for their bound execution; partial comments, ordinary task creation, and generic proposals cannot. This eliminates their Stop-only finalizers and gives every successful worker execution a durable declaration without demanding a second command from a worker whose final-result command can already reap it.

The old worker prompt says to declare **before** a push because observing a PR can reap it. That is incompatible with terminal-at-submit, not a convention to preserve. The settled prerequisite must synchronize that instruction with its behavior; the PR-path replacement removes all remaining reap-on-PR-observation arms and teaches **deliver first, declare last**. No grace period, second acknowledgement verb, or pre-declaration reservation is introduced. This design does not change the instructions governing the current design worker before the new behavior lands.

For duplicate/reordered signals, the first valid terminal transaction wins. An identical retry returns that receipt; a contradictory late declaration returns the existing terminal outcome with a typed conflict, rather than silently replacing it. A late fatal/Stop/PR observation cannot overwrite successful completion. Mandatory attention/result writes are atomic with their associated decision; frontend notifications are retryable projections. A failed local database commit returns an error, never a success receipt.

### One idle policy, no undeclared success

Reuse the existing declaration silence tracker and periodic nudge wake. Apply it to every live execution kind without a declaration; delete PR-specific idle/nudge ladders from completion. Hold while the worker is doing a tool, has known live delegated work, has an active build wait, or is explicitly waiting for input. Unknown process evidence is not affirmative evidence of idleness.

Keep the existing kind-specific 20-minute default / 40-minute revision horizons for **observed continuous idle time**; changing liveness thresholds is outside this project. After that horizon, send one declaration question. After a further horizon of observed idle time with that question delivered and unanswered, end as `abandoned`, reason `run_undeclared`, attention and redispatch hold committed with terminality. Activity resets the idle/question cycle. If the question cannot be delivered, route the transport/liveness finding to its existing owner; do not pretend an unanswered delivered question occurred. The periodic pass supplies progress without another Stop.

The backstop does not classify `waiting_human` as undeclared abandonment: the engine is already waiting for a named input. A blocker paired with done/blocked ends immediately. Actual death/fatal/cancellation still ends any live state through the table. Suspended host time is not evidence of observed idleness: both horizons and the question timer measure awake time, using the `HostClock` / `SuspensionLedger` primitives mono#2930 provides. This project does not implement host power signals or claim a wake event has already arrived; that is a scheduled dependency, stated in the reconciliation section below and on the idle-policy task row.

Delete `run_undeclared_at` and its special write/read paths when the backstop uses the ordinary terminal cause and attention. The measured zero population is useful deletion evidence, but the migration must still preserve any values that have appeared since measurement. Do not leave a dead column as a second source of truth for the same reason.

### Deliverable owners after termination

PR discovery, SHA comparison, CI/merge health, conflict verification, review admission, design-document extraction, and follow-up reconciliation must not run on the terminal call stack or delay cleanup. Reuse their existing merge-poller, proposal-application, and task-processing owners. Remove duplicate observations where those owners already perform the same check; relocating the entire current finalizer under an asynchronous wrapper does not satisfy this design.

The terminal transaction leaves a durable declaration and any already-known result reference. Existing PR observation must also consider terminal declared executions whose work is unresolved, so release does not make them disappear from consideration. Missing PR/artifact/report evidence is visible through the existing attention mechanism, with the execution's summary identifying the claim; no success promotion is inferred from absence. Work cannot be automatically redispatched just because `completed` is no longer live: the existing admission/orphan logic must recognize a declared execution awaiting result disposition and its resource release obligation. Failed verification may request a new revision through existing policy after safe cleanup; it cannot reopen this execution.

For no-op primary work, the existing no-op task disposition may close the task with the explicit reason. For no-op revisions, preserve the declined-finding surface and parent PR ownership. For reviews, accept the member report locally without implying GitHub verdict application succeeded. For answers and automation, missing local result records after a `delivered` claim are attention-worthy protocol defects, not successes manufactured by a Stop parser.

### Reconciliation with the host-suspension design

The [host-suspension design](https://github.com/spinyfin/mono/pull/2930) (mono#2930) was written in parallel with this one. Reconciling them leaves three decisions on this side. None changes the verdict, a ledger disposition, or the removal target, and none adds a task row.

**`Inapplicable` split: absorbed, and carried into the acceptance-side replacement.** mono#2930 proposed splitting `ShaDeltaGateOutcome::Inapplicable` into a transient fetch failure and a no-baseline case, because the two are indistinguishable in the trace today: the `debug!` arms that would separate them are not emitted by this engine build, and the recent incident needed a forensic export to tell "could not reach GitHub" from "no usable baseline". The enum's producing arms and its parking consumer are inside the code that "Remove PR evidence from execution termination" deletes, so the split is not implemented in `metadata_gate.rs`. The SHA comparison itself survives, as an acceptance-side observation under the existing PR-flow and merge-poller owners: the required scenario "Delivered with unavailable GitHub or unchanged PR head" relies on it to leave acceptance unresolved rather than promote success, and mono#2930 already assumes the fetches remain acceptance-side checks under this design. The distinction therefore keeps a consumer, and the replacement observation must carry it: an unreachable GitHub is a transient transport result that the existing owner re-observes later, while a missing dispatch baseline is a permanent "cannot corroborate by delta" fact that routes to the missing-evidence attention with that reason. Both outcomes must be logged at a level and target this engine build actually emits. This is one variant on a type the replacement needs anyway, not a new path, and it lands inside that row. The bounded retry on the `gh` fetches stays with mono#2930, as the non-goals state.

**Sleep awareness: a scheduled dependency, not a prose requirement.** The idle-question policy, the 20/40-minute horizons, and the universal idle backstop are all wrong under a suspended host unless elapsed time is measured as awake time. Two mono#2930 entries satisfy that: the `boss-host-suspension` crate, whose `HostClock` and `SuspensionLedger` expose `awake_elapsed_secs(since, now)`, and its in-memory-trackers entry, which moves `BuildWaitTracker`'s three production callers (`run_done_backstop::decide` and the build-wait and background-children paths in `completion/nudge.rs`) onto `HostClock::awake_secs()`. "Collapse marker and idle completion policy" is the row that cannot be implemented or tested until both have landed: its one observed-idle policy reuses that tracker, and its activity-reset and no-extra-Stop timer tests must assert that hours of suspension advance neither the question nor the abandonment, which is only expressible once the clock can be faked asleep. That external dependency is recorded on the row. No other row measures elapsed time as idleness evidence: cleanup deadlines are bounded foreground calls that resume on the next runnable pass after suspension, as the resource contract already states, and "Consolidate liveness terminal callers without resurrection" migrates the stale-worker and orphan detectors' terminal writes, not their thresholds, so it consumes mono#2930's persisted-stamp conversions without depending on them.

**Single-writer inventory: `stale_worker_sweep.rs` was a hole.** mono#2930 documents `execute_auto_reap` as writing `orphaned` and releasing slot and lease. Checked: `execute_auto_reap` (`stale_worker_sweep.rs:1467`) and the cadence fallback `run_cadence_fallback` (`stale_worker_sweep.rs:1669`) each call `mark_execution_orphaned` directly and then run their own release tail (driver teardown, token-verified tmux reap, `release_reaped_execution`, `force_release_lease_best_effort`). Neither reaches `execution_liveness.rs:254`, so they were not covered transitively. They are added to the caller inventory below and migrate with the other detectors: the token-verified recheck and the recovery backup are detection facts and stay, and the terminal write and release ordering move to the common implementation. That row and mono#2930's stale-worker entry both edit this file; whichever lands second forward-ports the other preservingly.

### Enforcing the contract

The current tests largely exercise helpers with prearranged state or assert a parser/finalizer result independently. Such a suite can prove both ends work while a flag or early return disconnects the only sanctioned ingress from terminal state. The marker regression demonstrates that coverage of the helper is not coverage of the worker promise; 630 KB does not establish the latter.

Use two complementary forms of enforcement, attached to the production change that needs them:

1. **Exhaustive state/cause tests at the database operation.** Iterate the state × terminal-cause table, both live statuses, all terminal outcomes, and missing/already-closed invocation rows. Assert legal edges, forbidden edges, declaration requirement, immutable terminal receipt/timestamp, mandatory attention, and retained release identity. A private typed cause and private terminal SQL prevent arbitrary status writers. Remove old writer APIs so compilation exposes missed callers; check the final SQL/call-site inventory as part of review.
2. **End-to-end tests through actual ingress and the production engine.** Extend the existing isolated socket-engine harness (`engine/core/tests/common` and `cli/tests/harness`) and compiled CLI test style used by `cli/tests/blocked_reason_length_limit.rs`. Add a completion contract target through Bazel. Drive the compiled `boss propose` command with real execution credentials; feed real driver-format final-message/Stop events through production event ingestion for marker cases. Use the actual dispatcher, proposal application, DB, worker registry, cleanup wiring, and isolated Cube ownership. A manually called finalizer, hand-built state machine, or fake success-returning pane releaser cannot satisfy this gate.

External provider responses may be deterministic fixtures at their transport boundary; do not replace the completion decisions under test. Process/lease release tests need a real sandboxed child and lease plus production ownership checks. Use the existing in-process app/pane test support or an isolated capture-capable app integration where actual pane acknowledgement is required. All tests run through `bazel test` under the repository test sandbox, never by launching a test binary directly or accessing production state. Extend existing harness support only where needed to exercise this path, not with a new test-only completion implementation.

**Standing merge rule: no completion arm or feature-flagged path lands without an end-to-end test that exercises it with the flag ON and asserts the terminal state.** Until an old flag is deleted, exercise both settings. A flag-off-only test is not evidence for a flag-on worker prompt. This project adds no feature flags.

## Risks / open questions

The choices below are made for this proposal; none requires operator input to finish the design. Review can reject the choices before implementation, but follow-up tasks must not silently choose different contracts.

- **Completion means a worker claim, not accepted work.** Existing UI or automation that equates `ExecutionStatus::Completed` with task success must use task/result disposition instead. Review specifically the orphan redispatch admission predicate so a declaration does not cause a second worker while audit/cleanup is pending.
- **Physical release cannot be unconditional under disconnection.** The chosen guarantee is prompt durable relinquishment, bounded attempts, visible retained obligations, and safe reuse only on proof. The existing app pool-claim grace shortcut conflicts with the safe-reuse property and must be corrected at its completion seam; it is not acceptable to conceal a held pane by decrementing a counter.
- **False orphaning currently relies on reversal for repair.** Strict terminality is safe only if uncertainty is kept nonterminal before removing readoption. The liveness PR must land both changes and the delayed-ack/duplicate-dispatch regression together. This does not authorize a wider liveness or power rewrite.
- **Declared blocked versus waiting for input is intentionally different.** The former frees resources; the latter retains them. Worker instructions must make that distinction explicit, including the fact that marker-only blockers do not promise release.
- **Final-result commands can stop their callers.** Review, final answer, and automation submissions must be documented as last actions and locally validate their execution binding. Generic proposal/comment submission must never inherit this behavior by kind-name similarity.
- **The old declaration-before-push instruction must change atomically with behavior.** The prerequisite is settled; the implementation must integrate it rather than leave workers taught to perform a push after they have surrendered execution authorization.
- **Removal estimates have uncertainty.** The six large files also contain real acceptance policy. Preserve necessary domain behavior, count relocated code as retained, and report a shortfall explicitly instead of meeting the estimate by weakening tests or hiding code elsewhere.
