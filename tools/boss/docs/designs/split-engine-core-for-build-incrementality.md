# Engine incrementality requires one-way crate boundaries, not more test shards

- Date: 2026-10-27
- Status: proposed; no runtime implementation ships with this document
- Source revision measured: `52ff4706`
- Related design: [Hub-and-spoke distributed engine](hub-and-spoke-distributed-engine.md)
- Earlier measurement: [Native Rust test sharding](../../../../docs/investigations/rust-test-sharding-engine-lib-test.md)

The contested property is that engine subsystems can become independently compiled crates without changing their transaction, dispatch, or completion semantics. Test relocation helps, but cannot eliminate the second whole-core compile while private unit tests still compile the core as their crate root.

## Verdict

Extract storage first after removing its upward policy dependencies, then separate dispatch, completion, merge polling and RPC handling behind consumer-owned interfaces. Keep genuine private tests with their owning small crate; move public behavior tests into independent `rust_test(srcs = ..., deps = [...])` targets. Do not promise a twofold wall-time improvement from moving a subset of tests.

## Goals

- An implementation edit recompiles its owning subsystem and actual dependents, rather than all 726 core inputs in both production and test modes.
- Preserve observable behavior, including database atomicity, commit-before-publication, execution identity, pool admission, completion retries, and shutdown order.
- Make each extraction independently reviewable and keep the repository's Bazel build and test graph valid at each landing.
- Reuse existing leaf crates and align host execution ownership with the hub-and-spoke design.

## Non-goals

No runtime redesign, schema format change, new transport, new build system, Cargo workflow, cache bypass, replacement test framework, or larger test-shard count. This design neither implements spoke execution nor relocates WorkDb into a spoke. It does not expose raw SQLite access as a public API merely to relocate tests.

## Measurement method and results

This study validates the present compilation-cost premise and inventories candidate seams. It does **not** experimentally compare completed extraction architectures: none was prototyped. Predictions below are structural or explicitly labeled estimates.

The checkout began clean at the revision above. “Clean build” here means an unmodified source checkout and the existing normal cache configuration, not empty caches. The initial Bazel server started for this workspace; dependency actions could use the shared disk cache. No cache was cleared, disabled, replaced, or bypassed. Each subsequent run appended one behavior-preserving comment line to exactly one file, built both targets, then restored the original bytes before the next edit. Temporary profiling edits were approved by the repo owner on 2026-10-27. Source restoration is required before publication.

Commands, with `PROFILE` an absolute output path in ignored scratch space:

```sh
bazel build //tools/boss/engine/core:engine_lib //tools/boss/engine/core:engine_lib_test --profile="$PROFILE"
```

The host reports Darwin arm64, Mac14,6, 12 CPUs and 64 GiB RAM; repository build concurrency is `--jobs=200`. The installed Bazel is 9.1.0. `bazel analyze-profile PROFILE` returns `Command 'analyze-profile' not found`; use the emitted gzip JSON trace instead. For each row, action processing time is the `dur / 1e6` of the `action processing` event naming the relevant Rust compile, and critical path is the sum of `critical path component` durations. These are elapsed action durations, including action overhead and executable linking for the test target, **not CPU time**. Concurrent library/test actions overlap; never add their durations to predict build wall time. Wall time is Bazel's reported `Elapsed time`.

```python
for event in events:

        print(event["name"], event.get("dur", 0) / 1_000_000)
print("critical path", sum(event.get("dur", 0) for event in events
                           if event.get("cat") == "critical path component") / 1_000_000)
```

The source inventory contains 727 Rust files under `core/src`, including `main.rs`; the two measured compile actions declare 726 inputs. Input count is not the count rustc actually parses in each configuration: the glob includes private test sources even for the production library. Consequently, an edit in a test-only file can still invalidate the production action until test sources are removed from its declared inputs. Preserve complete declarations of production modules; do not replace the glob with a manually maintained list.

### What the evidence can support

The baseline performed both core compilations, rather than merely reporting a cache hit. A repeated no-edit build may be much faster and is not evidence that splitting a crate has helped. Comment edits measure Bazel invalidation of the crate, not a representative LLVM optimization change. One observation per area cannot establish a median or a tail latency on a shared development machine.

The upper bound on eliminating the old test-mode core action is its measured action duration. The actual wall saving is bounded by the new critical path, including the library and new test compilation/link actions. Relocating ten public tests while retaining thousands of private tests removes **zero** whole-core compilation actions. For a pure relocated-test edit, once its source is excluded from the production crate's inputs, both old core compile actions can be avoided; only the new small test target recompiles.

## Test placement

### Measured inventory and access limits

The comment/string-masked source census finds **6,570** `#[test]` / `#[tokio::test(...)]` attributes. This is a static cross-platform count, not a promise about the number executed on this host. A raw text search gives 6,585 because it also sees examples in strings/comments. Top-level ownership gives WorkDb 1,877, app 942, coordinator 279 (including its 22-file external test directory), completion 341, runner 285 and merge polling 218; the remaining 2,628 belong to other modules.

At least **612 named tests directly call `db.connect()`**, whose definition in `work/connection_wait.rs` is `pub(crate)`. They require private access as written. This is a conservative lower bound: other receiver names, private fields, helper calls, and non-storage internals add more. The remaining 5,958 are **not** automatically public-API tests.

An item-level audit of small relocation candidates establishes **10 tests usable through existing public APIs without widening visibility**: four in `cost_pricing.rs` and six in `merge_mechanism.rs`. All called functions, enum variants and model-price fields are public. Move them together into a small independent policy-contract test target first; their old `super::*` imports become explicit crate imports.

The 11 tests in `work/exec_tail_tests.rs` illustrate the difference between test behavior and fixture implementation. Nine assert public WorkDb/event-bus behavior; two also call crate-private `content_checksum`. The shared `create_test_product` and `create_test_chore` helpers transitively insert host capabilities through `db.connect()`. Thus none of those nine is a literal import-only move today. Rebuild that fixture using the existing public `replace_auto_host_capabilities` operation, preserve the same seeded capability, and relocate those nine without exposing raw SQL. Keep the two checksum tests beside their implementation. Do not weaken their assertions to make relocation pass.

These are measured lower bounds, not an exhaustive symbol-resolution classification of all tests. For planning, retain the other **6,549** tests with their owner until each extraction classifies its own suite. The design's saving calculation uses the verified ten, not an invented percentage of 6,570. This uncertainty changes the expected benefit of test relocation, but does not change the need to break production cycles.

### Target layout

Use `rust_test(srcs = [...], crate_root = ..., deps = [":library"])` for external API tests, as existing `background_work_rpc_test` does. Do not use `crate = ":engine_lib"` for those targets: that recompiles the crate under `cfg(test)`. Share fixtures in a `testonly` library with only declared consumers visible and no dependency from production code to test support. Do not move all of `test_support.rs` wholesale; it imports coordinator and runner implementations and has raw SQL helpers.

Private SQL/migration tests stay in `work-db`'s private unit target; private dispatch tests stay in dispatch's target. Test modules must move with their implementation, preserving assertions and platform gates. This permits a small owning crate to compile twice without causing all other subsystems to compile twice. Public RPC behavior tests should use the real socket/server path, following `tests/common`, while private handler tests remain with the RPC crate.

Keep native sharding where suite execution warrants it. The [earlier investigation](../../../../docs/investigations/rust-test-sharding-engine-lib-test.md) established why eleven separate full-crate test targets are worse than one sharded target. Its cache-clearing experiments are historical evidence only; this study does not repeat that method. No recorded rationale was found for keeping every public-API test inside the core; do not infer that this placement was an intentional requirement.

## Chosen approach

### Ownership and interface rules

Existing dependencies already provide GitHub transport, metrics, live-status redaction, gh invocation, CI-log reading, planner validation, automation scheduling and PR-review parsing. `external_tracker/mod.rs` re-exports `boss_github_tracker` while retaining WorkDb-coupled reconciliation policy. Reuse that transport/policy split; do not repeat the leaf extractions.

Use narrowly visible crates under `tools/boss/engine`, following the existing leaf extractions. Proposed packages are `domain`, `work-db`, `execution-contracts`, `execution-runner`, `dispatch`, `completion`, `merge-poller` and `app`; retain the core package for residual runtime and compatibility targets. Rust `pub` is permitted for actual cross-crate consumers, with Bazel visibility restricted to named packages. It is not a reason to export every current `pub(crate)` helper. Re-export stable public paths from the compatibility facade where that creates no dependency cycle.

The final dependency direction is facade → app/composition → residual runtime and services → storage and shared contracts → existing leaf crates/protocol. Composition constructs the services, registers metrics, starts/stops loops and supplies adapters. No storage, transport or policy contract imports composition or the compatibility facade. Extracted execution services must not depend on the residual runtime implementation; app may consume that runtime because it is the actual upper-level caller. Place internal contracts in `engine-domain` or `execution-contracts`; use `boss-protocol` only for data already part of a shared wire/domain contract, not engine implementation traits.

Preserve these properties at every intermediate landing:

1. A transaction's events publish only after successful commit; no callback performs network/process work while holding the SQLite connection lock.
2. Each extracted trait preserves the original result/error, cancellation, ordering and durability semantics. An async callback is not equivalent to a durable queue merely because both return eventually.
3. Execution identity, pool admission and branch validation have one implementation each. Old module paths may re-export that implementation during migration.
4. Private tests exercise the same production implementation, and real socket/integration tests retain the same sandbox and declared tools. Test duplication is measured by executed test names, not merely target count.
5. All production source files are declared Bazel inputs. Test-only files are removed from production inputs only when physically separated from the production module tree.

The six inventoried ownership groups total **440 of 726** inputs (60.6%). They are not all production code and their costs are not additive. The remaining core modules are real dependents or composition/support code; this plan does not invent a separate crate for every small sweep. Lower-level service interfaces prevent those retained modules from becoming reverse dependencies of extracted subsystems.

A simple linear input-count model would associate WorkDb removal with 0.248 times each measured old action duration, and all six groups with 0.606 times it. Use this only as a sizing proxy; parsing, monomorphization, linking and concurrent contention are not uniform per file. Each extraction must repeat the four-area profile matrix and report actual action membership and times. The acceptance property is the absence of unrelated compile actions, not meeting an unsupported seconds target.

### Alignment with host execution work

The [hub-and-spoke ownership section](hub-and-spoke-distributed-engine.md#ownership-crates-and-load-bearing-invariants) assigns cube/recovery and tmux/driver operations to `host-execution`, with no dependency on core, WorkDb or coordinator policy. Honor that ownership when relocating `CubeClient`, local host execution and runner wiring. Do not create a second cube transport or a competing host execution crate. Reuse `CubeJsonTransport`, the existing HostAdapter abstraction, driver, recovery, command-runner and telemetry crates.

This incrementality work can land shared contracts and storage before the spoke project. If the host executor lands first, runner extraction consumes its API; if it has not landed, leave its existing implementation in the upper composition layer behind the same interface. Neither ordering requires implementing a spoke here. Coordinate edits to `coordinator.rs`, `host_adapter.rs`, `runner`, and `spawn_flow` by forward-porting the earlier changes rather than restoring an older version.

## Alternatives considered

| Alternative                                         | Why not chosen                                                                                                                                                                                                                                                                                                           |
| --------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| More modules or more native shards                  | Already used successfully for file size and execution duration. Neither changes the crate root or Rust compilation boundary. The profile still names 726 inputs in each compile action. Keep these techniques for their existing purposes.                                                                               |
| Move every test to an external crate immediately    | At least 612 tests directly need crate-private DB access; many more use private fixtures. Publishing the connection mutex or duplicating implementation source in tests defeats encapsulation or the compile goal. External tests are chosen where the API supports them, as existing RPC integration tests demonstrate. |
| Extract WorkDb immediately by copying its directory | Fails on concrete upward references to coordinator, completion, host registry, review validation and lifecycle policy. A temporary storage → core edge is a cycle, not an independent landing. Resolve those seams first.                                                                                                |
| One large “engine-services” crate                   | Easier first move, but completion, dispatch and RPC edits still invalidate each other and repeat the same test-mode compile. A small residual composition crate is useful; a renamed large crate does not meet subsystem incrementality.                                                                                 |
| Extract every leaf helper before storage            | Prior utility extractions are valuable and remain dependencies. They have not removed the large storage/app inputs. Limit new helper extraction to demonstrated cycle cuts, rather than an open-ended cleanup campaign.                                                                                                  |

## Risks / open questions

- **Test-access classification is conservative.** Only the stated lower bounds and audited candidates are established. Each owning-crate extraction must retain unclassified tests privately until compile evidence proves external placement; there is no blanket relocation estimate.
- **High-fanout interfaces still invalidate consumers.** Storage API and protocol edits naturally rebuild more than handler implementation edits. The goal does not promise isolation from actual dependencies.
- **WorkDb has inherent impls outside `work/`.** `host_registry` is one example. `local_worker_quarantine` and `coordinator_handoff` also contain inherent implementations. Rust prohibits adding inherent impls to another crate's type. Move storage impls into the owning crate and retain OS/process orchestration in a caller; do not discover this only after the large mechanical move.
- **Size estimates depend on doing seam work first.** Large moves below may exceed 25 files only as mechanical relocation. Non-mechanical boundary work is separately scoped and should normally stay below roughly 1,500 changed lines. Do not combine an unresolved redesign with a claimed mechanical move.
- **Facade ownership matters.** An RPC crate cannot depend on the legacy facade if that facade re-exports RPC. Split the current target into a residual runtime library and a thin facade. App consumes runtime and extracted service crates; the facade consumes app and runtime. Preserve existing CLI/client consumers deliberately.
- **No runtime activation is proposed.** The document ships inert; implementation requires separately reviewed PRs. There is no default-off feature to enable or deployment migration to approve.

## Proposed implementation task breakdown

Breakdown size: 15 entries (15 in-scope, 0 deferred) — public-test relocation, four concrete storage cycle cuts, storage-orchestration test separation, the storage move, execution contracts, runner, dispatch, completion and merge boundaries, and RPC composition/handler separation are independently reviewable seams.

The two public-test moves and the value-contract work may begin in parallel because their substantive edits are in different files. Serialize storage policy, host storage and review boundary work in the order below because they share WorkDb re-exports and lifecycle call sites. Later service moves follow their interface dependencies. Every later task must preserve and forward-port earlier edits to shared BUILD files, `lib.rs`, app wiring and host-adapter code; incidental registration edits alone do not justify further serialization. Every entry includes focused Bazel tests and `checkleft run`; extraction entries additionally require `bazel test //...` and profiles showing the intended invalidation boundary, without cache bypasses.

### Relocate public policy tests

Move the four cost-pricing and six merge-mechanism tests into one external policy-contract `rust_test`, preserving assertions. Remove their source from the production module tree and use explicit public imports. This is the smallest exercised proof of the test target shape, not a claim to eliminate the core unit compile.

- Deliverables: independent test target; unchanged test-name/assertion manifest; profile of a test-only edit showing no core Rustc action.
- Effort: small
- Dependencies: none
- Size: fewer than 10 files and 500 non-move lines.

Scope: in-scope

### Relocate public storage behavior tests

Move the nine public-behavior tests from `work/exec_tail_tests.rs` into an external WorkDb test target. Retain the two private checksum tests. Provide only the required fixtures through public construction and `replace_auto_host_capabilities`, preserving capability values and event assertions.

- Deliverables: external storage test target and minimal reusable fixture; private checksum tests retained; Bazel evidence that the same events and persisted state are asserted.
- Effort: small
- Dependencies: none
- Size: fewer than 10 files and 800 non-move lines.

Scope: in-scope

### Extract storage value contracts

Move storage-facing audit, run-cost, reconciliation-verdict, handoff and semantic-progress owned values into a narrow engine domain crate with their actual DB and service callers. Preserve existing public paths through re-exports; keep calculation and I/O implementations in their current owners. This is an exercised type boundary, not a speculative common-types crate.

- Deliverables: lower-level value types; migrated mapper/caller signatures; serialization and mapping tests preserving existing representations.
- Effort: medium
- Dependencies: none
- Size: approximately 10–20 files, below 1,500 non-move lines.

Scope: in-scope

### Extract storage policy dependencies

Move pure branch identity, pool-kind selection, attention kinds/lifecycle data, CI contract classification and postmortem brief composition out of higher service implementations. Reuse existing protocol/validation crates where the concept already belongs; place remaining internal policy in the domain crate. Include existing callers so there is one implementation of each policy.

- Deliverables: removal of WorkDb's upward pure-policy imports; compatible re-exports for coordinator/completion/sweeps; unchanged branch, pool, attention and CI policy tests.
- Effort: large
- Dependencies: Extract storage value contracts
- Size: up to 25 caller files and roughly 1,500 non-move lines; pure policy bodies move mechanically.

Scope: in-scope

### Separate host storage from host probing

Move WorkDb inherent implementations and connection-based host/quarantine helpers under storage ownership. Keep local host initialization inside schema setup, while injecting PID/capability observations from the existing host services. This removes storage's dependence on OS probes without moving WorkDb into host execution.

- Deliverables: storage-owned host/quarantine SQL; migrated probe callers preserving initialization order; schema and host-reconcile tests.
- Effort: medium
- Dependencies: Extract storage policy dependencies
- Size: fewer than 20 files and 1,500 non-move lines; host SQL bodies may move mechanically.

Scope: in-scope

### Separate review validation from storage transactions

Make review-guide workspace validation, merge-parent signoff observation, publication and reconciliation audit orchestration operate above WorkDb. Storage accepts validated owned inputs and returns existing domain outcomes; preserve durable rejection and retry behavior. Move the publication trait down with its callers, and pass build identity to the existing explicit-identity operations so storage does not import core provenance state. Move connection-local audit updates with storage rather than implementing callbacks that reacquire its mutex.

- Deliverables: exercised review/storage boundary without upward service imports; migrated submission/verdict/job callers; transaction, rejection and post-commit publication tests.
- Effort: large
- Dependencies: Separate host storage from host probing
- Size: up to 25 files and roughly 1,500 non-move lines; reuse existing validators rather than reimplementing them.

Scope: in-scope

### Separate storage orchestration tests

Move tests that exercise upper engine services out of the future storage unit-test crate, leaving private SQL/schema assertions with storage. Concrete callers include `work/project_postmortem_tests.rs`, `tests/t09.rs`, `board_mutation_events.rs`, `review_two_leaf_tests.rs`, `review_verdict_apply_tests.rs`, `ai_review_state_tests.rs`, `tests/t14.rs`, `tests/t31.rs` and `personas/tests.rs`. Update the fixture boundary while preserving every assertion; do not introduce a test dependency back from storage to core.

- Deliverables: upper-service tests owned by core/integration targets; minimal public-API fixtures (explicit isolated database seeding only where a corruption fixture needs it); test-name accounting and passing Bazel targets before the storage move.
- Effort: large
- Dependencies: Separate review validation from storage transactions
- Size: roughly 15–25 test files; assertion bodies move mechanically, with fixture/import changes below 1,500 lines.

Scope: in-scope

### Extract WorkDb and migrations

Move WorkDb, its full module tree, schema/migrations, dependency SQL and commit-publication helpers into `engine/work-db`. Move all remaining inherent storage implementations with it, including coordinator handoff metadata methods; receive the existing token generator at the caller boundary. Move population timing with its existing users into the existing metrics infrastructure, preserving span names and timing behavior. Retain compatibility exports and restrict visibility to actual engine/CLI consumers. Keep private SQL tests in the new crate and direct public storage tests to its production library.

- Deliverables: one-way storage crate with no core dependency; mechanical implementation/test relocation and complete Bazel inputs; full-suite and four-area profile evidence.
- Effort: large
- Dependencies: Relocate public storage behavior tests; Separate storage orchestration tests
- Size: more than 180 files, explicitly a mechanical-move exception; boundary changes must have landed in the preceding entries, with remaining non-move glue below 1,500 lines.

Scope: in-scope

- Effort: large
- Dependencies: Extract WorkDb and migrations
- Size: up to 25 files and 1,500 non-move lines; contract definitions may move mechanically.

### Extract app RPC and engine facade

Move app request handling and its private tests into an app crate. Keep its existing startup, sweep launch, metrics registration and shutdown together as the composition root; do not invent another crate for that thin wiring. Split the old core target into a residual runtime library without app and a thin `boss_engine` compatibility facade that re-exports app and runtime. App consumes runtime and the extracted services directly, never the facade. Remove remaining app-only constants/process-probe backedges as part of this exercised boundary. This preserves the CLI/client surface while preventing an app edit from rebuilding runtime.

- Deliverables: app crate, acyclic runtime/facade targets and migrated callers; real socket tests plus preserved handler tests; full-suite and final four-area profiles showing unrelated subsystems remain cached.
- Effort: large
- Dependencies: Relocate public policy tests; Extract merge polling service
- Size: 148 app-owned files are a mechanical-move exception; non-move facade/startup changes must stay below roughly 1,500 lines; mechanical path qualification may touch more lines, but handler behavior and interfaces are not redesigned.

Scope: in-scope
