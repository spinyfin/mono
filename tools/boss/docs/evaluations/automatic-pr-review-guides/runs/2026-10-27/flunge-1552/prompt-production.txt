### PR description

## Summary

This PR speeds up the Bazel Jest target by using a transpile-only `ts-jest` transform and partitioning it into four Bazel-owned shards. The original profiling identified repeated per-file TypeScript program construction as the dominant cost; the transform avoids that duplicate work while CI's Frontend Build and Test step still type-checks all of `src`, including test files.

The branch is rebased onto current `main`. It preserves main's `jest.setup.cjs` TextEncoder/TextDecoder polyfill in both Jest configuration and Bazel runfiles, so React Router remains loadable in jsdom.

- Adds a conditional shard sequencer for Bazel's runtime shard environment and retains Jest's default sequencer for bare local runs.
- Keeps Jest in-band within each Bazel shard; Bazel owns the four-way parallelism.
- Stores Bazel-run Jest cache data under `TEST_TMPDIR`, avoiding host temporary-directory accumulation while retaining Jest's default cache location for bare runs.
- Covers failed-test selection so an already-sharded list is ordered but never partitioned a second time.

## Measurements

The rebased target now runs 58 suites and 449 tests. The current four shards contain 15/15/14/14 suites and 107/160/93/89 tests, respectively, for an exact 449-test partition.

Worker configuration was measured by alternating the shipped in-band configuration with `--maxWorkers=4` after removing `--runInBand`. On this machine, in-band Bazel shards completed in 39.6–43.3s; allowing four Jest workers inside every shard took 97.9–102.4s. The latter oversubscribes the four concurrently scheduled Bazel shards, so this PR deliberately keeps `--runInBand`.

## Scope

Jest-level sharding for local `npm test` runs remains explicitly out of scope; Jest already supports `--shard=N/M` for that separate workflow.
