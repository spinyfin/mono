### PR description

## Summary

Share recipient pages used one error card for every failed view fetch: "This link isn't available." That copy is correct when the backend has answered that the token is missing, unknown, revoked, expired, or malformed. It is wrong when the backend never answered — the mid-deploy restart window that produces connection refused, timeouts, or 502/503/504 — because it tells the recipient the link is bad when it is fine and will work in a minute.

This PR classifies the failed request from status / error class and renders different copy:

- **Permanent** (404, 410, other 4xx except 408/429): "This link isn't available." / "Check the link with whoever shared it." No retry action.
- **Transient** (5xx, 408, 429, network errors, anything without a status): "Couldn't load this right now." / "Try again in a moment." plus a **Try again** button that `refetch()`es the view query. No background polling.

Ambiguous failures (no response, unknown error) are treated as transient. A missing token in the URL is permanent.

The results share page (`/r/:token`) is wired to the new card. The owner-side share dialogs are untouched.

### Shared presentation

Classification and copy live in `shareLoadFailure.ts`. The card is `ShareLoadFailureState` (same `LinkOff` icon, `StateCard` layout, and placement as before; only copy and the transient action changed).
