### PR description

## Summary

This PR speeds up the Bazel Jest target by using a transpile-only `ts-jest` transform and partitioning it into four Bazel-owned shards. The original profiling identified repeated per-file TypeScript program construction as the dominant cost; the transform avoids that duplicate work while CI's Frontend Build and Test step still type-checks all of `src`, including test files.

The branch is rebased onto current `main`. It preserves main's `jest.setup.cjs` TextEncoder/TextDecoder polyfill in both Jest configuration and Bazel runfiles, so React Router remains loadable in jsdom.

- Adds a conditional shard sequencer for Bazel's runtime shard environment and retains Jest's default sequencer for bare local runs.
- Keeps Jest in-band within each Bazel shard; Bazel owns the four-way parallelism.
- Stores Bazel-run Jest cache data under `TEST_TMPDIR`, avoiding host temporary-directory accumulation while retaining Jest's default cache location for bare runs.
- Covers failed-test selection so an already-sharded list is ordered but never partitioned a second time.

## Measurements

The rebased target now runs 58 suites and 449 tests. The current four shards contain 15/15/14/14 suites and 107/160/93/89 tests, respectively, for an exact 449-test partition.

Worker configuration was measured by alternating the shipped in-band configuration with `--maxWorkers=4` after removing `--runInBand`. On this machine, in-band Bazel shards completed in 39.6–43.3s; allowing four Jest workers inside every shard took 97.9–102.4s. The latter oversubscribes the four concurrently scheduled Bazel shards, so this PR deliberately keeps `--runInBand`.

## Scope

Jest-level sharding for local `npm test` runs remains explicitly out of scope; Jest already supports `--shard=N/M` for that separate workflow.

+"use strict";

+const fs = require("node:fs");
+
+// Translates Bazel's test-sharding protocol into a jest test partition.
+//
+// Bazel sets TEST_TOTAL_SHARDS / TEST_SHARD_INDEX on each sharded test action
+// and expects the runner to (a) run only its own slice of the tests and
+// (b) touch TEST_SHARD_STATUS_FILE to advertise that it understood the
+// request. A runner that ignores the variables would run the whole suite
+// once per shard; one that never touches the status file fails the action
+// outright with "Sharding requested, but the test runner did not advertise
+// support for it".
+//
+// jest's own `--shard=i/n` cannot be used here because the flag has to be
+// baked into the rule's `args` at analysis time, while the shard index is
+// only known at run time. A custom sequencer is the supported hook that can
+// read the environment instead. jest.config.cjs only installs this sequencer
+// when TEST_TOTAL_SHARDS is present, so unsharded and bare `npx jest` runs
+// keep jest's default sequencer (and its timing-cache ordering) untouched.
+
+const statusFile = process.env.TEST_SHARD_STATUS_FILE;
+if (statusFile) {
+  fs.writeFileSync(statusFile, "");
+}
+
+function fileSize(test) {
+  try {
+    return fs.statSync(test.path).size;
+  } catch {
+    return 0;
+  }
+}
+
+function bySizeThenPath(a, b) {
+  return fileSize(b) - fileSize(a) || a.path.localeCompare(b.path);
+}
+
+class BazelShardSequencer {
+  // Largest-first, then round-robin across shards. Without jest's timing
+  // cache (which never survives a bazel sandbox) file size is the best
+  // available proxy for cost, and dealing the sorted list out round-robin
+  // keeps the shards balanced rather than giving one shard every slow file.
+  sort(tests) {
+    const total = Number(process.env.TEST_TOTAL_SHARDS);
+    const index = Number(process.env.TEST_SHARD_INDEX);
+    const ordered = [...tests].sort(bySizeThenPath);
+    if (!Number.isInteger(total) || total < 1 || !Number.isInteger(index)) {
+      return ordered;
+    }
+    return ordered.filter((_, i) => i % total === index);
+  }
+
+  allFailedTests(tests) {
+    return [...tests].sort(bySizeThenPath);
+  }
+
+  // jest persists per-file timings here to order later runs. Every bazel run
+  // gets a fresh sandbox path, so there is nothing to persist to.
+  cacheResults() {}
+}
+
+module.exports = BazelShardSequencer;
