# Per-run token usage

Hook ingress calls `engine/app/src/app/transcript_persist.rs::persist_transcript_and_capture_cost`, which tails the raw provider transcript through `engine/core/src/run_cost.rs::RunCostCapture::capture_and_persist`. `engine/work-db/src/run_rows.rs::set_run_cost_snapshot` assigns the cumulative observation to the execution's agent-session `work_runs` row. Repeated hooks and replay after restart do not increment the stored totals. Completion is not required to retain usage: interrupted and orphaned runs keep their observed tokens too.

Neither captured Grok nor Antigravity dialect reports cache creation or its TTL split. Those columns are NULL, not zero. Grok `agent_active_ms` is also NULL: `apiDurationMs` is API latency, not the whole-turn duration Claude and Codex record, and the cost tailer does not read `events.jsonl` `turn_started`/`turn_ended`. Missing, malformed, negative, or inconsistent counts remain unknown. If any response omits a category, the cumulative category remains NULL instead of presenting a partial sum as the complete measurement. Different observed models within one run leave the run model unknown rather than pricing all tokens as the last model.

Every newly created run starts with a `usage_unavailable` reason of `No provider token usage observed`, including runs whose transcript never arrives. A valid usage observation clears it. Native responses missing input, output, or cache reads replace it with an explicit incomplete-response reason. The migration labels historical unmeasured rows too; it does not invent or backfill tokens.

## Context shape

The same transcript pass that captures usage also records, per run, four nullable `work_runs` columns that say how large the run's context was rather than how much it spent: `first_call_context_tokens`, `first_call_cache_write_tokens`, `peak_context_tokens` and `compactions`. They are written by `set_run_cost_snapshot` beside the token columns and read back by `usage_records_for_window`. Usage totals cannot tell a run that starts with a large fixed prompt from one that grows into a large prompt; these can, which makes them the mechanism check for any change to what a worker starts with or to how its context is managed.

"Context" is the prompt a model call sent: fresh input, cache writes and cache reads. Output tokens are not part of it. The first call is the first call in transcript order. The peak is the largest prompt over every call, so it is NULL as soon as any one call's prompt size is unknown: the unseen call could have been the largest, and keeping the largest known size would present a lower bound as the peak. A repeated record of one call (Claude splits one response across several records, Antigravity and Grok rewrite a step or turn as it finishes) replaces the earlier observation instead of adding a call, so replaying a transcript after a restart gives the same figures.

NULL means the transcript did not expose the figure, and is never read as zero: a Grok run has no recorded zero compactions, and a run captured before this existed has none of the four. Nothing is backfilled. The columns are assigned verbatim whenever a snapshot observed any of them, so a figure can return to NULL when a later call makes it unknowable, and are left alone by a snapshot that carries only a usage reason or a duration.

`boss cost rows` (`GetTokenUsageRows`) carries the four figures on each run and `CallStats` on every task, execution, group and the reply's `overall_calls`, plus `inclusive_calls` on a chain root. The engine computes them in `engine/usage-report` with the rules that apply to every usage figure: each is read only over the runs that recorded it and names that count (`runs_with_rounds`, `runs_with_first_call_context`, `runs_with_peak_context`, `runs_with_compactions_recorded`), and a ratio is absent, not zero, when no run contributes to it.

- `rounds_per_run`: rounds summed over runs with a recorded round count, divided by their number. A recorded zero counts, so a run that made no call lowers the average.
- `tokens_per_round`: the normalised token classes each run reported, summed, over those rounds, restricted to the runs that have both tokens and rounds, so the numerator and denominator cover the same runs. For `gross`-input runs (Codex), `cache_read` is subtracted from `input` before summing so cached reads are not counted twice; runs with an unknown input convention are excluded from both numerator and denominator. It is absent when no such run exists or they made no rounds, and a floor when any contributing run is `partial`.
- `median_first_call_context`, `median_peak_context`, `max_peak_context`: over the runs that recorded them.
- `runs_compacted`: of the runs that record compactions, those with at least one.

The text output prints a `Calls:` line under the totals and under every group, and three columns on every row: `ROUNDS` (the run's own count, or `n/run` on a task or execution), `PEAK CTX` (the run's own peak, or `max n` on a task or execution) and `COMPACT` (the run's own count, or `compacted/recorded runs`). A dash is NULL. `boss cost rows --group-by execution_kind` shows them per kind of execution, and `--json` carries every field.

## Evidence and reports

`run_cost/testdata/grok_turns.jsonl` contains the two verbatim `turn_completed` rows from `investigations/ghostty-grok-pane-viability-artifacts/ghosttykit_host/evidence/esc_interrupt/session_telemetry_excerpt.md`. The headless CLI JSON in that investigation reports fresh `input_tokens` separately, whereas ACP's `inputTokens` includes cache reads. The parser deliberately handles the interactive transcript dialect. It does not read `_meta.totalTokens` from text chunks or estimate counts from text.

`run_cost/testdata/agy_planner.jsonl` copies `engine/driver/src/agy/testdata/tool_calls_1.5.9.jsonl`. Its three planner rows report 20,570 fresh input, 8,101 cache reads, and 109 output tokens. The Grok fixture reports 2,486 fresh input, 24,576 cache reads, and 115 output tokens. Fixtures require neither provider credentials nor a live CLI.

`boss cost window` includes a `by_driver` breakdown from the execution's recorded launch driver, not its current work-item preference. Unknown category totals serialize as null and print as `unknown`. `tokens_partial` is true only when a measured run lacks a category, so an unmeasured run in a bucket does not hide complete Claude or Codex category sums. A bucket with no measured runs leaves every category unknown rather than reporting zero. `usage_unavailable` lists recorded reasons. Run counts distinguish absent usage from observed zero. Task and top reports retain the same unknown-category semantics. Known tokens on a partially measured run still rank in `boss cost top`.

Grok and Antigravity report tokens only: no verified subscription/CLI rates are assumed, even when Antigravity names a model family present in the API pricing table. In `boss cost window`, `task`, and `top`, `--usd` leaves their estimated cost absent and lists the model in `pricing_gaps`. Other drivers with incomplete categories are likewise excluded from dollar estimates. The optional estimate remains separate from measured tokens.

`boss cost rows` (`GetTokenUsageRows`) returns the same figures at run grain as a task → execution → run tree, built by `engine/usage-report` over `engine/work-db/src/cost_report_db.rs::usage_records_for_window`. Each run carries its per-class tokens (a class the provider did not report is NULL, never zero), a coverage state (`measured`, `partial`, `zero`, `unmeasured`), its input convention (`net` for Claude, Grok and Antigravity; `gross` for Codex), its recorded `usage_unavailable` reason and a list of caveat codes. List totals sum each run once (direct); a chain root also carries an inclusive total over its revisions. Executions that have no task (answer agent, automation triage) are included, listed apart from the task tree. `--usd` prices only measured runs with net input, every class reported and a model in the rate table; Grok and Antigravity are excluded by driver (`subscription_unpriced`) and Codex by its gross input (`capture_unnormalised`); `subscription_unpriced` runs neither set `estimated_usd_partial` on enclosing aggregates nor appear in `pricing_gaps`. Where a run recorded the 5-minute and 1-hour cache-write split, `boss cost --usd` (`task`, `window`, `top`) and `boss cost rows`/`series --usd` price each lifetime at its own rate; runs with only an unsplit non-zero cache-write count — or models whose pricing entry has no separate 1-hour rate — keep the single 5-minute rate and carry the `unsplit_cache_write` label/caveat. The design is `docs/designs/token-usage-window.md`; `engine/usage-report/fixtures/token-usage-seed.sql` seeds an isolated engine with every case.

Every report counts every `work_runs` row in its range, whatever the run's execution is bound to. Three execution kinds are not bound to a `tasks` row: `answer_agent` (a comment), `automation_triage` (an automation) and `pr_review_guide` (a source comparison). A review guide run is reported under its own execution kind and charged to the task that owns the PR it explains, stored on the execution as `work_executions.owner_task_id` when the guide is created (copied from the comparison's series `root_task_id`). That stored owner is what `boss cost task <id>`, that task's row in `boss cost top`, that task in `boss cost rows`, and that task's completion cost in `boss cost series` use, so source retention deleting the comparison later does not move the spend. Answer agent and automation triage runs have no task: `boss cost window` counts them under their kind, `boss cost top` names them `(no task)`, and `boss cost rows` lists them as task-less executions. A guide is task-less only when its owner was never recorded — the comparison was already pruned before the owner column was backfilled, or the root task row no longer exists. A guide run that recorded no usage is counted as unmeasured like any other run. `boss cost sol` is unchanged: it compares the two arms of implementation work on a PR family and does not include guide runs.

`boss cost series` (`GetTokenUsageSeries`) buckets those same facts over time (`hour`, `day`, `week`, or `month`, chosen by the engine when omitted and coarsened at the 5,000-cell cap) via `engine/work-db/src/cost_report_db.rs::usage_series_records_for_window` and `engine/usage-report::series`. Each populated `(bucket, group)` cell carries per-class NULL-preserving totals, `executions_completed`, `tasks_completed` with full inclusive `tasks_completed_cost` (including out-of-window chain runs), `distinct_prs`, `share_of_bucket_total_tokens`, and five engine-computed ratios (`tokens_per_run`, `tokens_per_completed_execution`, `tokens_per_active_hour`, `tokens_per_completed_task`, `tokens_per_pr`) that return `None` on zero denominators or unmeasured numerators. `tokens_per_active_hour` restricts both numerator and denominator to measured runs with known `agent_active_ms` (excluding Grok and active-time-less Antigravity runs) and reports the excluded count in `UsageSeriesCoverage.notes`.
