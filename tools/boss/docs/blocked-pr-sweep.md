# Blocked-PR sweep: why a Review card is stuck, and what the engine does about it

An open Boss-tracked PR can sit in the Review column's **Blocked** section for hours with nothing on the card saying why. The blocked-PR sweep makes "blocked with no reason" impossible: on every merge-poller pass it diagnoses each Review-lane card, applies the one safe remediation it owns, and stores a one-sentence reason the card renders.

Code:

- `tools/boss/engine/blocked-pr-diagnosis/` — the pure rules (`BlockedFacts` → `Diagnosis { category, reason, action }`), unit-tested per category.
- `tools/boss/engine/core/src/blocked_pr_sweep.rs` — gathers facts from the DB, applies the action, stores the reason. Runs at the end of `merge_poller::run_one_pass_observed`.
- `tools/boss/engine/core/src/ci_transient_retry.rs` — the transient-CI job retry, run inside `ci_watch::on_ci_failure_detected_with` where the failing checks are known.
- `tools/boss/engine/ci-log-reader/src/transient.rs` — the transient-vs-deterministic classifier for a failed Buildkite job.
- `tools/boss/engine/core/src/work/blocked_pr.rs` — storage: `pr_blocked_diagnoses` (the card's reason) and `pr_blocked_remediations` (the ledger every budget is counted from).
- `Task::review_blocked_reason` / `review_blocked_category` on the wire; `WorkBoardCardTitleRow` renders the reason under the title as `Blocked: …`.

## Inventory: what blocks or stalls a Review-lane PR

`classify_review_section` puts a card in Blocked when any of: `status = blocked`, `blocked_reason` set, `ci_required_state = fail`, `pr_mergeable_state = conflicting`, or every open revision is itself blocked. The card also silently stalls (not Blocked, but never reaching merge) when a revision's worker dies with no successor, a revision never leaves dispatch, or the automated review is reaped at its generation cap. `Task::blocked_signals` is never populated on the wire (`mappers.rs` leaves it empty), and the card's blocked pill only renders when `status = blocked` — so an `in_review` card blocked by raw CI or mergeability facts showed only a red icon. That is the "blocked with EMPTY blocked_signals" symptom.

## Transient classification

`boss_ci_log_reader::transient::classify_job` consults evidence in order of how structured it is:

1. Buildkite job record: `signal_reason ∈ {agent_stop, agent_refused, process_run_error}` or `exit_status = -1` → `AgentLost`. `cancel` is deliberately not transient.
2. Any deterministic marker in the log (`FAIL: //`, `TIMEOUT: //`, `FAILED: Build did NOT complete`, `error[E…]`, a checkleft `error[<check>/<id>]:` finding other than the "could not be resolved" refusal) → `Deterministic`, vetoing everything below.
3. checkleft exit status 3 plus its `PR description surface: UNAVAILABLE` / `GitHub API call timed out` line → `CheckInputUnavailable` (the tool's own machine-readable statement that it did not evaluate the change). checkleft exits 3 for an undetermined changeset or a GitHub API timeout, but **not** for a PR-description lookup that answers HTTP 5xx: that refusal is still an error finding with exit 1, so the original 504 incident is classified by step 4 from the log text. A distinct exit for it is deferred (below).
4. An upstream-unavailable signature (`HTTP 502/503/504`, `Gateway Timeout`, `connection reset by peer`, DNS failure, or a Bazel `Error downloading […]` line that also names a retryable cause such as a timeout, connection reset or HTTP 5xx) → `UpstreamUnavailable`. A download that fails with a 404, 401/403, or checksum mismatch is a change-caused failure and is never retried: it is a deterministic marker, so it vetoes transient evidence anywhere else in the log and on the same line.
5. Otherwise `Indeterminate` — never retried.

The log window is the last 5,000 lines: a failing `bazel-build-test` job uploads every test log afterwards, so its `FAIL:` line sits 700–1,100 lines before the end (five sampled logs, 1,159–1,683 lines). A 400-line window would have called those "indeterminate" rather than "deterministic"; both are safe (neither retries), but the deterministic verdict is the one the card should show.

## When the transient retry runs

`ci_watch::on_ci_failure_detected_with` runs the retry only after every in-flight guard has passed (an active rebase or conflict attempt, an active CI remediation, an in-flight ci-fix revision, the suppression check), and never for a failure set that pre-triage would `retrigger` (every check `STARTUP_FAILURE` / `CANCELLED`; that existing path keeps owning those). The poller calls it once a minute while CI is red, so the step is idempotent per `(work item, head)`: a head whose budget is spent is skipped on the ledger's `budget_exhausted` row, and a head judged non-transient is remembered in memory so the build and its full job log are fetched once. Every `bk` call has a 60s timeout. The ledger row is written as `pending` before `bk job retry` runs and finished afterwards, so a crash between the two still counts against the budget, and a ledger write failure means no retry. The job-level path exists next to `retrigger` because it retries one job on log evidence with its own per-head budget, whereas `retrigger` re-runs a whole build on a GitHub conclusion alone.

Retry lineage is followed: the check's job is resolved to the newest job in its Buildkite retry chain. A running or passed retry means "handled"; a retry that failed again is classified like any other failure and consumes the next budgeted retry or falls to the fix path.

## Measurements behind the limits (mono pipeline, 2026-10-06 → 2026-10-21)

Read-only `bk api` over 2,323 builds (752 PR-branch, 1,571 `main`):

| What                                                          | Value                                                                                       |
| ------------------------------------------------------------- | ------------------------------------------------------------------------------------------- |
| PR jobs retried by hand                                       | 17 (11 `checks`, 6 `bazel-build-test`); 15 passed on retry, 2 failed again                  |
| …positively transient                                         | 1 — build 21619 `checks`, HTTP 504 resolving the PR description; cleared on its first retry |
| …checkleft findings retried after the human fixed the PR text | 10 (`pr-text-leakage`, `change/file-count`, a `format/bazel` toolchain provisioning error)  |
| …`engine_lib_test` shard failures (flaky tests)               | 6 — classified deterministic; must not be auto-retried                                      |
| checkleft exit 3 (inputs unavailable)                         | 2, both on `main` builds                                                                    |
| Still-failed PR jobs in the window                            | 175, all `exit_status = 1`, none with an agent `signal_reason`                              |
| Passed `checks` duration p50 / p90 / p99                      | 84s / 149s / 409s                                                                           |
| Passed `bazel-build-test` duration p50 / p90 / p99            | 190s / 280s / 503s                                                                          |
| Passed `mac-app-build` duration p50 / p90 / p99               | 89s / 203s / 417s                                                                           |

Constants **derived from the measurements above** (Buildkite retry only):

- **Transient retry budget**: 2 per `(work item, head SHA)`. Every observed transient failure cleared on its first retry and at most two jobs on one build were retried together, so this is one retry per failing job with a 2x margin. Past it the head takes the ordinary fix path and the card says the budget is spent.
- **"Retrying" freshness**: 30 minutes. A retried job passes within 409s / 503s (p99); a retry the poller has not seen clear after 30 minutes is reported as "has not cleared; check the build".

Constants **inherited from existing engine constants, not measured** for this feature:

- **Sweep interval**: the merge poller's existing 60s pass. The sweep adds only DB reads per card (no GitHub or Buildkite calls).
- **Dead-revision re-dispatch budget**: 2 per PR head (plus 2 per revision), chosen to match the orphan sweep's three-consecutive-dead-runs guard (original dispatch plus two re-dispatches).
- **Dispatch-stall threshold**: 10 minutes, twice the engine's persistent-stall escalation threshold (`dispatch_stall_escalation`, 5 minutes). The only stall durations on record (12–168 minutes) come from the incident report, not from a sampled history.
- **Orphan-recovery grace**: 10 minutes before a dead `active` revision is reported as needing a human (the orphan sweep runs at 60s with a 90s minimum age).
- **Review generation cap**: the existing `MAX_AUTOMATIC_PRE_MERGE_BATCH_GENERATIONS`.

No frequency, clear-time or margin sample exists for review-batch reaps, dead revisions or dispatch stalls: they would come from the engine's database, which workers may not read. Until someone samples recent history (counts per category, time to clear, the window used, and the margin each limit leaves over the observed clear times), the limits in this second list are defaults, not measurements.

## Reading the ledger

```sql
SELECT created_at, category, signal, target, action, outcome, detail
FROM pr_blocked_remediations WHERE work_item_id = '<id>' ORDER BY id;
SELECT category, reason, action, updated_at FROM pr_blocked_diagnoses WHERE work_item_id = '<id>';
```

For a transient retry, `detail` begins with `<attempt>/<budget>` followed by the machine signal and the proving log line. Budgets are counted from this table, so an engine restart never resets them.

## Review-gate facts the sweep reads

- **Automated review owed**: the card is a candidate of `list_tasks_awaiting_pre_merge_review_admission` (held in PendingReview, an admission deferral on file, or a reaped batch). With no batch and a green head this reads `no automated review has been admitted` (or `Needs you` when batch review is off), whatever GitHub's human approval state says. The human gate (`review_required_state`) only produces the `required human approval is still missing` reason.
- **Stalled reviewer**: a `pr_review` execution of the head's live batch that has neither started nor finished after the dispatch-stall threshold reads `the automated reviewer has waited … for dispatch`. PendingReview roots (`active` with a live reviewer) are swept for this, and the Doing card carries the reason.
- **Findings successor**: a findings revision counts only while it is live (todo, active, blocked) or has delivered (the review badge's delivery rule); one archived without delivering leaves the findings unaddressed.
- **Retry timeout**: a `bk job retry` that times out is recorded `retry_unconfirmed` (it counts against the budget, the card says it awaits confirmation) and the next pass's retry-lineage walk settles whether Buildkite accepted it.

## Deferred (not in this change)

- Re-admitting a reaped review batch past the generation cap, or when the review fanout flag is off. The card now says so and asks a human (`Needs you: … start one by hand`); a bounded third generation, or admission without fanout, needs a product decision on reviewer cost.
- Re-kicking a `cube_workspace_lease_attempted` / `workspace_recovery` stall. The card shows the stall with the wait reason (for generic, CI-fix and conflict-fix revisions alike); the fix belongs in the dispatch pipeline, where the stage lives only in the dispatch JSONL.
- Persisting the probe's per-PR opt-out label (`boss/no-auto-rebase`) so a conflicting PR that carries it reads `Needs you: … automatic resolution is disabled` rather than `no resolution attempt is running yet`.
- Removing `Task::blocked_signals` or populating it from `task_blocked_signals` (it is an always-empty wire field).
- Sampling recent history for the review-reap, dead-revision and dispatch-stall limits (see "Measurements behind the limits").
- A distinct checkleft exit status (3) for the PR-description-unavailable refusal on a 5xx answer, so the 504 incident no longer rests on log-text matching. It needs a change to `checkleft` (`main.rs`, its tests and the README exit-code table), which would push this changeset past the repository's 30-file limit (it is already at 30; the exit-code change, its test and the README table add three more files).
- A pointer to this document from `AGENTS.md` (one more file than the 30-file limit allows).
